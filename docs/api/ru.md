# RosPanel REST API

**Интерактивный справочник:** [Swagger UI](reference.md) — все эндпоинты, отрисованные из того же OpenAPI-документа.


Внешний REST API позволяет окружающей системе — биллингу, магазину в Telegram,
скрипту провижининга — управлять панелью по HTTP с помощью ключа API. Он вызывает
ту же внутреннюю логику, что и админ-панель, поэтому эти два пути никогда не
расходятся.

## Включение API

Откройте панель → **Настройки → API**. Создание первого ключа включает этот
интерфейс и генерирует постоянный, непредсказуемый базовый URL:

```
https://<your-host>/<api_path>/v1
```

Сегмент `<api_path>` отделён от скрытого пути панели, поэтому смена секрета панели
никогда не ломает интеграции. Сменить или отключить путь API можно на той же
странице (при смене меняется базовый URL; ключи продолжают работать по новому).

## Интерактивная документация и машиночитаемая спецификация

API публикует собственную спецификацию OpenAPI 3.0, сгенерированную из кода
сервера (схемы отражаются из реальных типов Go, поэтому они никогда не
расходятся):

```
GET $BASE/openapi.json    → документ OpenAPI 3.0
GET $BASE/docs            → Swagger UI (эндпоинты можно вызывать в браузере)
```

Оба отдаются без ключа (сам базовый URL и есть секрет). Откройте `…/docs`, нажмите
**Authorize**, вставьте ключ и вызывайте любой эндпоинт вживую. Направьте Postman /
`openapi-generator` / любой генератор клиентов на `…/openapi.json`, чтобы получить
типизированный клиент. (Оболочка Swagger UI загружается с CDN; спецификация,
которую она отображает, полностью локальна.)

## Аутентификация

Каждый запрос должен нести ключ, созданный в **Настройки → API**. Сам ключ
показывается **один раз** при создании — сохраните его сразу; дальше хранится
только его префикс. Передавайте его как bearer-токен:

```
Authorization: Bearer rp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

(`X-API-Key: <key>` тоже принимается.) Отозванные ключи перестают работать сразу.

Отсутствующий или неверный ключ возвращает `401`. Для интерфейса действует
ограничение частоты запросов с одного IP.

Ключ получает **полный доступ** или **отмеченные для него методы API**
(`GET /v1/users`, `POST /v1/signup`, …) при создании; набор можно изменить позже. Он
вызывает ровно их; на всё остальное отвечает `403` с `"code": "forbidden"`, а
эндпоинт MCP перечисляет только эти инструменты. Никто не может отметить метод,
который не вправе вызывать сам, и только владелец даёт полный доступ (а также
бэкапы). Ключ, созданный до появления отметок методов, сохраняет доступ, который
открывают его права, пока его не отредактируют.
`PATCH /v1/settings` и `PATCH /v1/nodes/{id}` проверяют каждое поле по его разделу
(DNS и egress требуют `routing.manage`, доверенные сети и настройки проб —
`security.manage`).

Полный доступ открывает то, до чего в панели добирается только владелец, — включая
бэкапы (`/v1/backup`) и расписание локальных бэкапов, — поэтому создать или
отозвать такой ключ может только владелец.

## Обёртка ответа

Успех:

```json
{ "data": { ... } }
```

Ошибка:

```json
{ "error": { "code": "bad_request", "message": "name is required" } }
```

Общие коды: `bad_request` (400), `unauthorized` (401), `not_found` (404),
`unsupported_media_type` (415), `internal` (500).

Отклонённый панелью ввод несёт ещё два поля — причину отказа и параметры этой
причины:

```json
{ "error": {
    "code": "bad_request",
    "key": "err.planHasUsers",
    "message": "the plan is assigned to 12 users — move them to another plan first",
    "args": { "count": 12 }
} }
```

`code` остаётся грубым классом, по которому решают о повторе; `key` — конкретная,
стабильная причина, по которой решают о поведении, — никогда не сопоставляйте по
`message`, формулировку которого вольны менять. `message` всегда на английском
(панель переводит те же коды в браузере на язык, выбранный администратором);
`args` позволяет клиенту отрисовать свою формулировку, не разбирая текст. Оба
поля отсутствуют, когда за отказом нет кода (кривое тело запроса, неизвестный
путь).

## Тела запросов

Поле, которого эндпоинт не определяет, — это ошибка, а не то, что можно
проигнорировать:

```json
{ "error": {
    "code": "bad_request",
    "message": "unknown field \"groups\" — see GET /v1/openapi.json for the fields this endpoint accepts"
} }
```

Принять тело и молча выбросить поле хуже, чем отказать: вызывающий, отправивший
`{"groups": [2,4]}` на эндпоинт, который ждёт `group_ids`, получает успех и
отсутствие изменений в составе групп, а узнаёт об этом при следующем чтении
значения. Поэтому сверяйте написание со спецификацией — она генерируется из кода,
поэтому не может перечислить поле, которое панель не читает.

Только поля, которые эндпоинт действительно требует, помечены там `required`.
Всё остальное можно опустить — оно сохраняет задокументированное значение по
умолчанию; чтобы изменить одну вещь, полный объект отправлять никогда не нужно.

### Параллельные правки

У записей нет версии и `If-Match`: два вызывающих, меняющих один объект,
разрешаются по принципу «побеждает последняя запись», и ни одному об этом не
сообщают. Важнее всего это там, где запись несёт поля, которые менять не
собирались, — правка узла переотправляет узел целиком, поэтому изменение
маршрутизации, записанное отсюда, может перезаписать имя, которое кто-то задал в
панели секундой раньше.

На практике это кусается редко: эндпоинты, которые правят частично
(`PATCH /v1/settings`, `PATCH /v1/users/{id}`), применяют только поля из тела,
поэтому два вызывающих, трогающих *разные* поля, не конфликтуют. Если вы
автоматизируете правки одного объекта из нескольких мест, перечитывайте его после
записи, а не полагайтесь на то, что ваше значение сохранилось.

## Постраничная выдача

Каждый эндпоинт списка принимает `?limit` и `?offset` и отвечает блоком `meta`:

```json
{ "data": [ … ], "meta": { "total": 1043, "offset": 0, "limit": 100 } }
```

`limit` по умолчанию равен **100** и ограничен сверху **1000**; `limit=0` (или
отрицательное значение) означает «всё начиная с `offset`» — это осознанный запрос,
а не значение по умолчанию: неограниченный размер по умолчанию — это как раз то,
из-за чего интеграция год работает нормально, а потом упирается в таймаут на
выросшей панели. `total` считает строки после фильтрации и до окна, поэтому
вызывающий может листать, не гадая.

Журналы (`/v1/events`, `/v1/admin-audit`) листаются иначе — по курсору
(`?before=<oldest id held>`): их строки сдвигаются по мере поступления новых, и
offset пропустил бы или повторил записи.

## Эндпоинты

Базовый URL ниже записан как `$BASE` (например,
`https://vpn.example.com/ab12cd34/v1`).

### Состояние

```
GET $BASE/health → { "data": { "status": "ok" } }
```

#### Проба живости (без ключа API)

`GET $BASE/healthz` — единственный эндпоинт, которому не нужен ключ: направьте на
него монитор доступности или балансировщик. Он отвечает **503** (а не 200), когда
Xray не запущен: панель может быть в порядке, но нода не несёт VPN-трафик — и
именно об этом вы хотите получить оповещение.

```
GET $BASE/healthz
200 → { "data": { "status": "ok",       "xray": "running", "xray_started_at": 1752230400 } }
503 → { "data": { "status": "degraded", "xray": "down",    "xray_started_at": 0 } }
```

Он намеренно живёт под путём API, а не в корне сервера: неаутентифицированный
`/healthz` в корне отвечал бы JSON любому сканеру и выдавал панель, обесценивая
заглушку. Путь API не меняется при ротации секрета, поэтому монитор, направленный
сюда, продолжает работать.

### Пользователи

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/users` | Список пользователей (фильтр + постранично); `?telegram_id=`, `?sub_token=` или `?external_id=` находит одного. |
| `POST` | `/v1/users` | Создать пользователя. |
| `POST` | `/v1/signup` | Зарегистрировать клиента из внешней системы или своего бота по правилам самостоятельной регистрации (см. ниже). |
| `POST` | `/v1/users/bulk` | Применить одно действие ко многим пользователям сразу. |
| `GET` | `/v1/users/{id}` | Получить одного пользователя. |
| `PATCH` | `/v1/users/{id}` | Обновить имя / лимиты / срок или срок от первого подключения / лимит устройств / лимит скорости / `enabled` / `external_id` внешней системы / `mailing` (рассылки и автосообщения включены или выключены — переключатель в боте показывает то же) / `lang` (`ru`, `en`, `zh`, `ar` или `""` — то, что сообщает Telegram). |
| `DELETE` | `/v1/users/{id}` | Удалить пользователя. |
| `POST` | `/v1/users/{id}/reset` | Сбросить счётчики трафика пользователя. |
| `POST` | `/v1/users/{id}/reset-period` | Задать период автосброса. |
| `POST` | `/v1/users/{id}/rotate-sub` | Выпустить новую ссылку подписки (старая перестаёт работать). |
| `POST` | `/v1/users/{id}/plan` | Применить к пользователю тариф. |
| `POST` | `/v1/users/{id}/plan/cancel` | Отменить платную подписку сейчас. |
| `GET` | `/v1/users/{id}/connections` | Недавние исходные IP / устройства пользователя: `last_seen`, `count` (замечено, не чаще одного раза в 45 с), `approx_seconds` (нижняя граница времени активности) и `banned` (отброшено фаерволом сейчас). |
| `GET` | `/v1/users/{id}/devices` | Установки, привязанные по HWID, вместе с лимитом, в который они считаются. |
| `POST` | `/v1/users/{id}/devices/unbind` | Освободить одно привязанное устройство (или все), освободив слот. |
| `GET` | `/v1/users/{id}/events` | Собственный журнал пользователя (постранично). |
| `GET` | `/v1/users/{id}/abuse` | Совпадения пользователя с блоклистами (`limit`, по умолчанию 20). |
| `GET` | `/v1/users/{id}/happ-link` | Подписка пользователя в виде зашифрованной ссылки `happ://crypt4/`. |

**Создание** — `name` обязателен; всё остальное необязательно и применяется к
свежему аккаунту в том же вызове:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0,
  "device_limit": 3, "speed_limit": 20000, "plan_id": 2, "group_ids": [4] }
```

**Устройства** — это установки, привязанные по заголовку подписки `x-hwid` (см.
*Настройки → Подписки* в панели). Список несёт лимит рядом с составом устройств,
поэтому один вызов отвечает на вопрос «заполнен ли пользователь»:

```json
{ "data": { "devices": [ { "hwid": "…", "os": "iOS", "os_version": "26.5.2",
    "model": "iPhone 15 Pro Max", "app": "Happ/1.0", "ip": "203.0.113.7",
    "first_seen": 1786500000, "last_seen": 1786568000 } ],
  "limit": 3, "enabled": true } }
```

Отвязка принимает либо один id, либо все и отвечает, сколько слотов освобождено:

```json
{ "hwid": "…" }        →  { "data": { "removed": 1 } }
{ "all": true }        →  { "data": { "removed": 3 } }
```

Устройство, которое никогда не было привязано, — это `404`, а не молчаливый
успех. Освобождённый слот доступен сразу: следующее обращение с новой установки
будет принято.

`speed_limit` — это лимит полосы на пользователя в **кбит/с** (0 = без
ограничения), действующий в обе стороны. Его применяет ядро хоста к адресам, с
которых подключён пользователь, а не Xray, — поэтому все за одним NAT-адресом делят
один лимит, а с Hysteria2 лимит проявляется как потери пакетов, а не как плавное
замедление. Тариф несёт собственный `speed_limit` и при применении перезаписывает
пользовательский, точно как и с лимитами трафика и устройств. Группа доступа тоже
может нести `speed_limit`, и если он есть у одной из групп пользователя, **действует
лимит группы** — собственное поле пользователя (из тарифа или заданное вручную)
сохраняется, но перекрывается; см. *Группы*.

**Срок, начинающийся с первого подключения** — вместо `expire_at` отправьте
`hold_seconds`: длину срока, который не идёт, пока пользователь не подключится
впервые. Первое подключение, которое зафиксирует панель, ставит `expire_at` на этот
момент плюс `hold_seconds`, а `hold_seconds` возвращает в `0` (журнал пишет это как
`user.term_started`). Они взаимоисключающие — тело, где одновременно ненулевой
`expire_at` и `hold_seconds`, отклоняется. Ожидающий старта срок — не больше 3650
дней.

```json
{ "name": "gift-card-17", "hold_seconds": 2592000 }
```

В `PATCH` `hold_seconds` ставит пользователя на удержание (заменяя любую дату), а
`0` снимает ожидающий срок; `expire_at: 0` означает *никогда* и тоже снимает
ожидающий срок. `PATCH`, где не указано ни то ни другое, оставляет срок ровно как
есть — включая срок, начавшийся мгновение назад. `extend` в `/v1/users/bulk`
удлиняет ожидающий срок на заданные дни, а применение тарифа заменяет его
собственным сроком тарифа. Объект пользователя несёт ожидающий срок как
`hold_seconds` (0, когда его нет).

**Happ-ссылка** — `GET /v1/users/{id}/happ-link` отвечает
`{ "data": { "link": "happ://crypt4/…" } }`: ссылка подписки пользователя,
зашифрованная ключом, встроенным в приложение Happ, — Happ добавляет её, ни разу не
показав адрес. Ссылка равна `""`, пока `sub_happ_crypt` выключен (см.
*Конфигурация сервера*). Отдельный вызов, а не поле пользователя: каждая ссылка —
это шифрование RSA-4096 со случайным заполнением, поэтому два вызова возвращают
разные ссылки на одну подписку.

`plan_id` перезаписывает `data_limit` и `expire_at` значениями тарифа — тариф *и
есть* лимиты, — а явный `device_limit` применяется после и выигрывает. Если
что-то из дополнений не удаётся, аккаунт НЕ откатывается (учётные данные могут уже
быть у кого-то на руках): вызов возвращает ошибку, а пользователь остаётся таким,
каким успел стать. Отвечает `201` с пользователем в том виде, каким он в итоге
оказался.

**Отмена подписки** — сразу переводит пользователя на бесплатный тариф (теряя
оставшееся оплаченное время) или прекращает доступ, когда бесплатный тариф не
настроен. Отличается от применения бесплатного тарифа вручную: это записывается как
`plan.cancelled` — событие, на которое реагирует биллинговая интеграция.

**Список** — параметры запроса: `status` (`active` / `disabled` / `expired` /
`limited` / `device_limited`), `search` (подстрока имени), `limit`, `offset`
(`limit<=0` = всё начиная с `offset`). Ответ добавляет блок `meta`:

```json
{ "data": [ ... ], "meta": { "total": 42, "offset": 0, "limit": 20 } }
```

**Массовое действие** — тело:

```json
{ "ids": [1, 2, 3], "action": "extend", "days": 30 }
```

`action` — одно из `enable`, `disable`, `delete`, `reset`, `extend` (`days`
требуется только для `extend`). Ответ: `{ "data": { "affected": 3 } }`.

**Период сброса** — тело: `{ "period": "monthly" }` (`none` / `daily` / `weekly`
/ `monthly` / `yearly`).

**Создание** — тело:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0 }
```

`data_limit` — байты (0 = без ограничения); `expire_at` — метка Unix (0 =
никогда). `data` в ответе — полный объект пользователя, включая `sub_url`, ссылки
`vless` / `reality` / `hysteria2` встроенных лейнов и `links` — все лейны, которые
есть у пользователя на этом сервере, включая свои инбаунды, каждый с именем,
которое покажет клиент.

**Правка** — отправляйте только поля, которые хотите изменить:

```json
{ "name": "alice2", "data_limit": 107374182400, "expire_at": 1767225600, "device_limit": 3, "enabled": true }
```

**Применение тарифа** — тело:

```json
{ "plan_id": 2, "extend_from_current": false }
```

Тариф может назвать группы доступа, которые он выдаёт (`"group_ids": [3]`): тот,
кого ставят на тариф — платным заказом, через `POST /v1/users/{id}/plan` или при
регистрации, — вступает в эти группы и покидает их при смене тарифа. Членства,
назначенные напрямую через `POST /v1/users/{id}/groups`, сохраняются; отбирается
только то, что дал тариф. Пустой список означает, что тариф ничего не говорит о
доступе.

**Создание заказа** — тело `{ "user_id": 5, "plan_id": 2 }`. Ответ несёт заказ и,
когда настроен платёжный провайдер, ссылку `pay_url` на его платёжную страницу,
куда отправить пользователя:

```json
{ "data": { "order": { ... }, "pay_url": "https://..." } }
```

Ручной заказ — без `provider` или с `"manual"` — возвращает пустой `pay_url` и ждёт
`/confirm`; он отклоняется, пока ручная оплата выключена. Деньги, которые вы
принимаете сами, — Telegram Stars в своём боте, своя касса, — это
`"provider": "external"`, независимо от настройки ручной оплаты: `"paid": true`
подтверждает заказ в том же вызове, или `/confirm` позже; до тех пор он остаётся
неоплаченным, а `/cancel` его убирает; `external_ref` сохраняет id вашего платежа
как `provider_id`. В выручке он учитывается как любой платёж. Создание заказа
**не** идемпотентно по ключу, но и не плодит дубликаты: всё ещё неоплаченный заказ
на того же пользователя, тариф и провайдера переиспользуется вместо открытия
второго, поэтому повторённый вызов возвращает уже существующий заказ.

**Настройки биллинга** — объект целиком, заменяемый при записи (частичного
обновления нет: «бесплатного тарифа нет» — это настоящее состояние, и его нужно
отличать от «не указано»):

```json
{ "enabled": true, "free_plan_id": 1, "trial_plan_id": 2, "payment_note": "card 1234",
  "manual": true, "manual_label": "", "wallet": true, "topup_min": 100,
  "topup_max": 15000,
  "ref_mode": "percent", "ref_percent": 10, "ref_days": 7, "ref_first": false }
```

Назначение тарифа бесплатным или пробным также делает его бесплатным и заново
применяет ко всем, кто на нём уже находится, — то же правило, что соблюдает
панель. `manual` предлагает ручную оплату наряду с провайдерами, `manual_label` —
подпись её кнопки оплаты (пусто = формулировка по умолчанию), а `payment_note` —
текст, который видит пользователь, платящий вручную.

`wallet` позволяет пользователям держать баланс (пополнения, оплата тарифов с
него, продление с него); `topup_min` и `topup_max` — минимальное и максимальное
пополнение в рублях (`topup_max` по умолчанию 15000, не больше 1000000). `ref_mode`
— что получает приглашающий, когда приглашённый им человек платит деньги: `off`,
`percent` (`ref_percent` % от платежа, включая пополнения, на баланс приглашающего
— нужен `wallet`) или `days` (`ref_days` дней на его тариф, за тариф, купленный за
деньги); `ref_first` платит только за первый такой платёж. Если их не передать,
`wallet`, `topup_min`, `topup_max`, `ref_mode`, `ref_percent`, `ref_days` и
`ref_first` сохраняют записанные значения.

**Заказы и баланс** — `amount_rub` заказа — это всегда деньги, которые нужно
внести. Когда баланс пользователя покрывает часть цены, `balance_kop` — эта часть
(в копейках), а `amount_rub` — остаток; подтверждение заказа кладёт деньги на
баланс и снимает с него всю цену вместе с тарифом. `kind` — `plan` или `topup` (у
пополнения `plan_id` 0). Тариф, купленный только с баланса, выглядит как
оплаченный заказ с `provider` `balance` и `amount_rub` 0 — это не выручка.
`discount_rub` и `promo_code` показывают промокод.
Когда баланс покрывает всю цену, `POST /v1/billing/orders` отвечает
`err.payFromBalance`; вместо этого отправьте `"from_balance": true`, чтобы купить
тариф с баланса. Деньги, пришедшие по уже отменённому заказу (вытесненному более
новым оформлением с тем же промокодом, убранному как брошенный, отменённому
вручную), считаются как любой другой платёж, — а
`POST /v1/billing/orders/{id}/confirm` принимает и отменённый заказ: тариф
выдаётся, либо, при включённом кошельке, деньги уходят на баланс, когда тариф уже
нельзя выдать (другой тариф куплен тем временем, пожизненный тариф уже есть), и
заказ становится `topup`. У пользователя может быть не больше 3 неоплаченных
пополнений, открытых за последний час.

**Промокоды** — `kind` бывает `percent` / `amount` (скидка на следующий платёж
пользователя, `value` в процентах или рублях; `plan_ids` ограничивает его этими
тарифами, `first_only` — теми, кто никогда не покупал тариф), `days` (`value` дней
на `plan_id` или на активный платный тариф пользователя, когда `plan_id` 0) или
`balance` (`value` рублей на баланс). `max_uses` 0 — без ограничения, `expires_at`
0 — никогда; каждый пользователь может использовать код один раз. Регистр кодов не
важен.

**Несколько периодов** — `"periods": 3` в `POST /v1/billing/orders` покупает сразу
три периода тарифа со скидкой, которую называет `periods` в настройках биллинга
(`[{"periods": 3, "percent": 10}]`); число, для которого нет предложения,
отклоняется. Срок — это столько периодов, а квота, которую тариф не восполняет на
своём цикле, восполняется каждый период.

**Возврат** — `POST /v1/billing/orders/{id}/refund` с `{ "cancel_plan": false }`
возвращает цену заказа (деньги и часть с баланса) на баланс пользователя один раз;
`cancel_plan` ещё и снимает со срока дни, за которые заплатил заказ (тариф
заканчивается, только когда не осталось ни одного). Требует включённого кошелька.
Возврат или чарджбэк, о котором сообщает платёжная система, сам помечает заказ
`refund_source: "provider"`: он уходит из выручки, забирает назад то, что купил, и
больше не может быть возвращён на баланс.

**Win-back** — `"winback": {"enabled": true, "after_days": 7, "percent": 20,
"valid_days": 7}` в настройках биллинга: через столько дней после окончания
оплаченного срока пользователь получает одноразовый код на такую скидку,
прикреплённый к его следующему платежу и отправленный в боте.

**Опрос при уходе** — `"churn_survey": true` в настройках биллинга: через день
после окончания оплаченного срока бот спрашивает пользователя, почему тот не
продлил, и страница подписки спрашивает то же, пока срок остаётся истёкшим.
Причины: `price`, `quality`, `not_needed`, `competitor`, `other` (с комментарием).
Один ответ на одно окончание. Свой кабинет тоже может его задать:
`GET /v1/users/{id}/subscription` несёт `churn`, пока есть что спросить, а
`POST /v1/users/{id}/churn` принимает ответ (`source` `api`; более поздний ответ
заменяет причину). `GET /v1/billing/funnel` несёт их под `churn`:
`{"total": 12, "reasons": {"price": 5, ...}, "comments": [{"user_id": 7, "user_name": "...",
"reason": "other", "comment": "...", "source": "bot", "created_at": ...}]}`.

**Баланс** — `POST /v1/users/{id}/balance` принимает
`{ "amount_kop": 10000, "note": "..." }` (с любым знаком; баланс не может уйти
ниже нуля) и отвечает `{ "balance_kop": ... }`. `GET /v1/users/{id}/wallet`
отвечает `{ "wallet": {...}, "history": [...], "ref_link": "..." }` — `ref_link`
это пригласительная ссылка пользователя, пока включены реферальная программа и
пользовательский бот.

**Продажи из своего бота** — `GET /v1/users/{id}/quotes` перечисляет, что
пользователь может купить сейчас (только текущий тариф, пока идёт платный), с
ценой на каждый срок: `total_rub` после его промокода, `balance_kop`, который
покрывает баланс, и `money_rub`, который остаётся заплатить. Затем
`POST /v1/billing/orders` с `from_balance`, когда `money_rub` равен 0 (добавьте
`expect_expire_at` — тот `expire_at`, который вы показали, — чтобы повторённый
запрос не купил второй период), либо с `provider` на остаток. Пополнение — это
`{"user_id": 5, "kind": "topup", "amount_rub": 300}` (плюс `provider` или без него
для ручного). Оба принимают `lang` (`ru`/`en`/`zh`/`ar`, для инструкций по ручной
оплате) и `return_url` (куда платёжная страница провайдера возвращает плательщика;
ссылка подписки пользователя, если не указано, — или ваша страница, когда она
задана).

**Свой бот или пользовательский кабинет** — ключ остаётся на вашем сервере и
никогда — в браузере. Отметьте методы, которые он вызывает: создание пользователей
и привязку Telegram, открытие заказов, промокоды, приглашающих, продление, — и не
отмечайте подтверждение заказа, корректировку баланса и возвраты, которые двигают
деньги без их поступления. На каждом сообщении находите пользователя:
`GET /v1/users?telegram_id=<id>` (поиск по индексу; пустой список означает
новичка). Новичок — это `POST /v1/users` с `plan_id` (пробный или бесплатный тариф
— пользователь без тарифа не получает блок оплаты), затем
`POST /v1/users/{id}/telegram` с `{"chat_id": <id>}` и, если их `/start` нёс код
приглашения, `POST /v1/users/{id}/referrer` с `{"ref_code": "r_…"}` (с `r_` или
без) — один раз, до их первого платежа. Собственный код приглашения пользователя —
это `ref_code` в `GET /v1/users/{id}/wallet` (и `ref_link`, пока включён
пользовательский бот панели). Кабинет, который авторизует людей по их ссылке
подписки, находит их по `?sub_token=`.
`GET /v1/users/{id}/subscription` содержит всё, что показывает страница подписки, —
статус, `blocks` (что добавляют на страницу плагины:
`{type: text|markdown|notice|button, text, label, url}`), трафик, срок, `sub_url`,
импорт в один тап для каждого приложения (`apps`), каждую конфигурацию (`links`),
скачивание Clash (`clash_url`), простые конфигурации WireGuard (`wg`:
`{name, conf_url, qr_url}`, так же `awg`), Telegram-прокси для каждого сервера
(`telegram`: `{name, link, web_link, qr_url}` — `link` это `tg://proxy`, который
добавляет его в один тап), устройства, блок оплаты (`billing`), цвета оператора
(`brand`), `terms_url` / `privacy_url` (документы оператора, пока у них есть текст
— сам текст есть в `GET /v1/legal`) и `tg_link` — ссылку пользовательского бота,
которая привязывает аккаунт к Telegram, в котором её открыли (переносит его туда
при `tg_linked`; отсутствует, пока переключатели в *Настройки → Telegram* ничего
не предлагают, и годна 15 минут) — с формулировками на `?lang`; действия идут
через эндпоинты выше. Он соблюдает те же настройки подписки, что и страница:
`links` пуст, пока страница не показала бы ни одной конфигурации (`show_configs`
выключен или требуется HWID — сырая ссылка обошла бы лимит устройств), `clash_url`
отсутствует, пока кнопка Clash на странице выключена или скрыта за обязательным
HWID, кнопка Happ — это зашифрованная ссылка, когда та включена, а `maintenance` —
режим обслуживания панели. `churn` — опрос при уходе, который нужно задать:
`{question, reasons: [{key, label}]}` с формулировками на `?lang`, присутствует,
только пока оплаченный срок пользователя истёк, а он не ответил; отправьте
выбранный `key` в `POST /v1/users/{id}/churn`.

**Юридические документы** — `GET /v1/legal` (любой ключ) возвращает
пользовательское соглашение и политику конфиденциальности оператора, написанные в
*Настройки → Брендинг → Документы*: `{"terms": {...}, "privacy": {...}}`, каждый с
`markdown`, `html` (отрендеренный; сырой HTML из источника отбрасывается), `url`
(его публичная страница, "" пока документ пуст) и `updated_at` (0 = не задан).
Показывайте их на своих страницах или ссылайтесь на `url`.

**Регистрация из внешней системы** — `POST /v1/signup` с
`{"external_id": "ann@example.com"}` регистрирует клиента по собственному id внешней
системы по правилам, которые соблюдает пользовательский бот: закрытая регистрация
отказывает (`err.signupClosed`), режим по приглашениям требует `invite`
(`err.signupBadInvite`), модерация заводит заявку, а аккаунт получает пробный или
бесплатный тариф, как при регистрации через бота. Один аккаунт на `external_id` —
сравнение точное, поэтому сначала приведите e-mail к нижнему регистру, — так что
повторная регистрация возвращает его (`200`, `"status": "existing"`, его `user_id`;
полный аккаунт — только ключу с `users.view`) вместо второго пробного периода.
Внешняя система должна передавать только тот id, который проверила сама
(подтверждённый e-mail): кто его передаст, тот и получит этот аккаунт. Новый
аккаунт отвечает `201 "created"` с аккаунтом, заявка — `202 "pending"` с
`request_id` (повторный запрос, пока она ждёт, ничего не создаёт). Необязательные:
`name` (внешний id, когда не указано), `source` (метка воронки), `ref` (код
приглашения; неизвестный игнорируется), `lang` (`ru`, `en`, `zh` или `ar`,
выдаётся аккаунту — сразу или когда оператор его одобрит) и `ip` — адрес клиента,
для ограничения в одну регистрацию в минуту на адрес (на /64 для IPv6) и на id, 20
в минуту всего; сверх этого ответ — `429` с `Retry-After`. Отметьте ключу внешней
системы `POST /v1/signup` (плюс то, что она показывает и продаёт) и не отмечайте
`POST /v1/users`: тогда она не сможет создать пользователя на своих условиях.
`user.registered` и `registration.rejected` несут `external_id`, а
`GET /v1/users?external_id=` находит аккаунт снова.

**Регистрация из своего бота** — `POST /v1/signup` с `{"telegram_id": 123456789}`
вместо `external_id` (одно или другое) регистрирует пользователя Telegram по
правилам, которые панель соблюдает для Telegram: его аккаунт возвращается
(`"existing"`), отвязанный восстанавливается, общий блоклист отказывает
(`err.signupBlacklisted`), пробный период — один на Telegram навсегда (удалённый
аккаунт не даёт права на второй), и Telegram привязывается к новому аккаунту.
`name`, `source`, `ref`, `invite` и `ip` работают как выше — одна регистрация в
минуту на Telegram, и общие 20 в минуту вместе с регистрациями по `external_id`;
при модерации заявка принадлежит Telegram, и её одобрение привязывает его.
**Передавайте только тот Telegram ID, который дал вам Telegram** — отправителя
сообщения вашему боту или проверенный вами `initData` Mini App, — никогда не
введённый клиентом: кто передал ID, тот регистрирует этот Telegram, тратит его
единственный пробный период и получает аккаунт, к которому тот привязан.

Клиент, пришедший из бота или Mini App, уже имеет аккаунт: привяжите логин внешней
системы к нему через `PATCH /v1/users/{id}` с `{"external_id": "ann@example.com"}`,
а не регистрируйте заново — со страницы, куда он попал по своей ссылке подписки
(`?sub_token=` находит аккаунт), так что id принадлежит ему. Id, который держит
другой аккаунт, отклоняется (`err.externalIDTaken`); `""` снимает его.

**Перенос** — тело `{ "to_plan_id": 3 }`, ответ `{ "data": { "migrated": 12 } }`.
Применяет лимиты, период и группы доступа целевого тарифа ко всем пользователям
исходного тарифа. Это единственный способ опустошить тариф перед удалением.

**Провайдеры** — `GET /v1/payments` возвращает каждого провайдера из реестра с его
формой настроек: какие поля он принимает, их текущие значения, какие секреты
заданы (но никогда их значения) и `webhook_url` для вставки в личный кабинет
провайдера. Список полей у каждого провайдера свой и генерируется из реестра,
поэтому состав этой нагрузки намеренно произволен. `POST /v1/payments` принимает
`{ "key": "yookassa", "enabled": true, "config": {...} }`; секрет, переданный
пустым, сохраняет записанное значение.

`GET /v1/billing/providers` динамичен — он возвращает те способы оплаты, которые
вы включили в панели (карты, СБП, крипта, …), каждый с `key`, и `manual` первым,
когда включена ручная оплата. Именно этот `key` вы передаёте как `provider`, когда
открываете заказ.

### Ноды

Управление парком серверов. Локальный сервер панели — это нода `0`; остальные —
удалённые **ноды**, которые держат исходящий long-poll к панели. Пользователи и
лимиты синхронизируются на каждую включённую ноду автоматически, и каждый сервер
можно править независимо.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/nodes` | Список серверов (локальная панель — нода `0`) со статусом и сегодняшним трафиком. |
| `POST` | `/v1/nodes` | Зарегистрировать ноду — возвращает однострочную команду установки (join-токен показывается один раз). |
| `GET` | `/v1/nodes/{id}` | Получить одну ноду. |
| `PATCH` | `/v1/nodes/{id}` | Изменить имя / хост / протокол / маршрутизацию / переопределения DNS и egress WARP-Opera. |
| `DELETE` | `/v1/nodes/{id}` | Удалить ноду (она перестаёт обслуживать пользователей). |
| `POST` | `/v1/nodes/{id}/enabled` | Включить или выключить ноду. |
| `POST` | `/v1/nodes/{id}/regen-join` | Выпустить новую команду установки (отзывает текущий токен ноды). |
| `POST` | `/v1/nodes/{id}/update` | Попросить ноду самообновиться до последнего релиза. |
| `POST` | `/v1/nodes/update-all` | Попросить все подключённые ноды самообновиться (последовательно). |
| `POST` | `/v1/nodes/{id}/proxy` | Настроить системный прокси этого сервера (`id` 0 = мастер). |
| `POST` | `/v1/nodes/{id}/placement` | Изменить размещение этого сервера и лимит трафика (`id` 0 = мастер). |
| `GET` | `/v1/nodes/{id}/health` | Самодиагностика одного сервера. |
| `GET` | `/v1/nodes/{id}/reach` | Последняя проверка сервера из других стран (Globalping; `at` 0 = ещё не проверялся). |
| `POST` | `/v1/nodes/{id}/reach` | Проверить сервер из других стран сейчас (занимает до минуты). |
| `GET` | `/v1/reach` | Страны, число проб на страну, интервал мониторинга и порог этой проверки. |
| `POST` | `/v1/reach` | Задать их; пропущенный `token` (Globalping) сохраняет записанный, `""` очищает его. |
| `GET` | `/v1/alerts` | Правила алертов; `firing` считает открытые сейчас алерты. |
| `GET` | `/v1/alerts/metrics` | Метрики, за которыми может следить правило, с единицами. |
| `GET` | `/v1/alerts/events` | История срабатываний, новые первыми (`limit`, `before` = id, ниже которого продолжить); `resolved_at` 0 = ещё срабатывает. |
| `POST` | `/v1/alerts` | Добавить правило: `name`, `metric`, `op` (`gt` / `lt`), `threshold`, `for_secs` (сколько условие держится до срабатывания), `node_id` (-1 — каждый сервер, 0 — мастер), `enabled`. |
| `POST` | `/v1/alerts/{id}` | Заменить настройки правила. |
| `DELETE` | `/v1/alerts/{id}` | Удалить правило; его история остаётся. |
| `GET` | `/v1/nodes/{id}/logs` | Последние строки лога сервера (0 — мастер). |
| `GET` | `/v1/logs` | Последние строки лога самой панели. |

**Регистрация ноды** — тело `{ "name": "NL #1", "host": "nl1.example.com" }`. Ответ
несёт id ноды, одноразовый join-токен и готовую команду установки для свежего
сервера Ubuntu:

```json
{
  "data": {
    "id": 3,
    "join_token": "rpn_…",
    "install_command": "curl -Ls https://.../install.sh | sudo bash -s -- --join '…#rpn_…'"
  }
}
```

Join-токен встроен один раз и истекает через 24 ч; `/regen-join` выпускает новый.

**Размещение** — где сервер стоит в подписках и сколько трафика он может нести.
Частичная правка: меняются только отправленные поля. Те же поля принимает
`PATCH /v1/nodes/{id}`; этот маршрут достаёт и мастер (`id` 0), у которого нет
строки ноды. Ответ — размещение в сохранённом виде.

```json
{ "country": "NL", "sort_weight": 10, "capacity": 300, "hide_when_full": true,
  "traffic_limit": 1099511627776, "traffic_period": "month", "traffic_reset_day": 14,
  "hide_when_over": false }
```

`traffic_limit` — байты на `traffic_period` (`month` или `day`; 0 = без лимита).
`traffic_reset_day` (1–31) — день, с которого начинается заново месячный лимит,
чтобы совпасть с днём, с которого считает хостинг; месяц без такого дня начинается
с последнего дня, а `1` хранится как значение по умолчанию `0`. Очистка лимита
очищает вместе с ним его период, день сброса и `hide_when_over`.

**Системный прокси** — слушатель SOCKS5 и/или HTTP forward на этом сервере для
трафика, который не является VPN-клиентом: скрапер, бот, другая панель,
направляющая сюда свой egress. Его не открывает ни один учёт пользователя, его не
ограничивает ни одна группа доступа, и он никогда не появляется в подписке.
Трафик уходит по маршрутизации этого сервера, поэтому WARP, Opera и прокси-лейны
применяются точно так же, как для VPN-клиентов.

```json
{ "socks_enabled": true, "socks_port": 1080,
  "http_enabled": true,  "http_port": 3128,
  "accounts": [ { "user": "scraper", "pass": "…" },
                { "user": "bot",     "pass": "…" } ] }
```

`accounts` — всегда полный список: чтобы удалить одну запись, отправьте список без
неё. Логины должны быть уникальными и не содержать двоеточия или пробела
(двоеточие — разделитель в `user:pass`), и хотя бы один полный аккаунт требуется,
когда включён любой из слушателей: открытый прокси на публичном порту сканеры
находят за часы, и дальше это чужой спам-релей с IP этого сервера. Протокол,
включённый без порта, получает 1080 (SOCKS) / 3128 (HTTP). У каждого сервера СВОИ
аккаунты и порты — нода никогда не наследует мастерские, поэтому утёкший логин
открывает одну машину. Ответ — сохранённая конфигурация, поэтому вызывающий,
отправивший только `{"socks_enabled": true}`, узнаёт, какой порт ему достался.

### Свои инбаунды

Инбаунды, задаваемые оператором сверх трёх встроенных лейнов, по одному набору на
сервер (сервер `0` = мастер). Каждый — публичный слушатель, поэтому
создание/обновление проверяется **на целевой машине** (`xray -test` + проба
привязки порта), прежде чем сохраниться.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/servers/{id}/inbounds` | Перечислить свои инбаунды одного сервера (`id` = id сервера, `0` = мастер). |
| `POST` | `/v1/servers/{id}/inbounds` | Создать свой инбаунд на этом сервере. |
| `POST` | `/v1/inbounds/{id}` | Обновить свой инбаунд (по собственному id инбаунда). |
| `DELETE` | `/v1/inbounds/{id}` | Удалить свой инбаунд. |

**Создание / обновление** — тело повторяет редактор инбаундов в панели: `name`,
`protocol` (`vless` / `trojan` / `hysteria2` / `shadowsocks` / `turn-vk` / `wg`),
`transport` (`tcp` / `ws` / `xhttp` / `grpc` / `httpupgrade`), `port`, `security`
(`none` / `tls` / `reality`) с соответствующими ключами (dest и ключи REALITY,
fingerprint, path/host, диапазон hop у Hysteria2), плюс необязательные
дополнительные блоки (XHTTP `extra`, HTTP-маскировка TCP, `sockopt`, доп. ключи
TLS). Полный список полей — и то, какие комбинации допустимы, — в `openapi.json` /
Swagger. `shadowsocks` — это Shadowsocks-2022 (`method` выбирает AEAD; ключ сервера
генерируется, ключ пользователя выводится из UUID) — многопользовательский, поэтому
статистика и квоты по каждому пользователю работают, но говорят на нём только современные
клиенты (sing-box, mihomo, v2rayN, Shadowrocket, Streisand).
`turn-vk` (ранее `wireguard`, на входе по-прежнему принимается) — это WireGuard за
релеем TURN: `port` — публичный UDP-порт, который слушает релей, `turn_link` —
необязательная ссылка на звонок VK (`https://vk.com/call/join/…`), выдаваемая
приложениям пользователей; ключ сервера, loopback-порт, который слушает Xray
(`wg_public_key`, `wg_local_port` в ответе), и ключ маскировки Free Turn Proxy
(никогда не возвращается) генерируются. Он не входит ни в один формат подписки —
пользователи импортируют его в приложение со страницы подписки
(`vkturnproxy://`, `freeturn://`, `wingsv://`) или скачивают
`<sub>/wg/<inbound id>.conf` со страницы подписки.
`wg` — это простой WireGuard: собственный WireGuard-инбаунд Xray на публичном UDP
`port`, куда напрямую ходит любой стандартный клиент WireGuard. Ключ сервера
генерируется (`wg_public_key` в ответе); transport и security фиксированы, а
`turn_link` не применяется. Пользователи становятся пирами по тому же тождеству
туннеля, какое у них есть для AmneziaWG. Он тоже не входит ни в один формат подписки —
пользователи скачивают `<sub>/wg/<inbound id>.conf` (или `.png`, тот же текст в
виде QR) со страницы подписки.
`enc_mode` включает VLESS Encryption на инбаунде `vless` — `native`, `xorpub` или
`random` (то, как рукопожатие выглядит в трафике), пусто — выключено; ключи
генерируются (`encryption`, половина клиентов, есть в ответе). С ним `tcp` может
идти с `security: none`.
`cdn_host` (и `cdn_port`, 443 при 0) ставит инбаунд `vless` / `trojan` на `ws` /
`httpupgrade` / `xhttp` за CDN: ссылки указывают на этот домен по TLS, CDN
доходит до собственного порта инбаунда (открытым текстом при `security: none`), а
инбаунд доверяет его X-Forwarded-For.
`pin_cert` (TLS, не за CDN) велит клиентам проверять сертификат сервера по его
отпечатку, а не по имени, поэтому `sni` может быть любым доменом — например, из
белого списка оператора.
Два формата, которые схема может назвать только `string`: `reality_dest` — это
голое имя хоста (`www.microsoft.com` — форма `host:port` отклоняется), а
`hop_interval` — диапазон в секундах (`"5-10"`, а не `"30"`).
`data` в ответе — сохранённый инбаунд; отклонённая конфигурация (порт уже занят,
недопустимая комбинация, нода офлайн) возвращает `400` с причиной. Инбаунды,
которые клиент не умеет представить, молча выпадают из подписок Clash/sing-box,
вместо того чтобы попасть туда сломанными.

Инбаунд можно адресовать из группы доступа через грант-токен `inbound:<id>` (см.
**Группы**).

`GET /v1/inbounds/catalog` публикует, что с чем можно сочетать, — каждый
протокол × транспорт, какие режимы `security` каждый допускает, какие форматы
подписок не могут его нести и какие значения перечислений принимают
дополнительные поля. Это та же таблица, которой пользуется редактор в панели,
поэтому клиент, собирающий инбаунды по ней, не сможет построить такой, который
валидатор отклонит.

### Группы

Группы доступа решают, какие подключения может использовать пользователь.
Пользователь **без** группы достаёт всё; пользователь в одной или нескольких
группах достаёт **объединение** грантов своих групп. Участвуют только группы,
которые **ограничивают доступ** (`limits_access`, ниже): пользователь, все группы
которого оставляют доступ открытым, тоже достаёт всё. Применение — **на стороне
сервера**: учётные данные запрещённого лейна не отдаются Xray, а не просто
скрываются, — поэтому `links` в объекте пользователя, подписка и собранная вручную
ссылка показывают только выданное.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/groups` | Перечислить группы, каждую с её `grants`, `member_ids` и числом участников. |
| `POST` | `/v1/groups` | Создать группу. |
| `POST` | `/v1/groups/{id}` | Обновить группу (имя, гранты, лимит скорости). |
| `DELETE` | `/v1/groups/{id}` | Удалить группу (участники, оставшиеся без группы, ограничивающей доступ, возвращаются к неограниченному доступу). |
| `POST` | `/v1/groups/{id}/members` | Заменить состав участников группы. |
| `POST` | `/v1/users/{id}/groups` | Заменить членство одного пользователя в группах. |

**Создание / обновление** — тело:

```json
{ "name": "VIP", "grants": ["builtin:0:vless", "builtin:0:reality", "inbound:7"],
  "speed_limit": 20000 }
```

`speed_limit` ограничивает скорость участников в **кбит/с** (0 = группа не задаёт).
Когда он задан, он **приоритетнее** лимита, который даёт участнику его тариф или
карточка; участник нескольких групп с лимитами получает **наибольший** из них.
Троттлинг от блоклиста он никогда не ослабляет — действует более строгий из двух.
Если в обновлении его не передать, лимит сохраняется.

**Грант-токен** называет одно подключение:

- `builtin:<server_id>:<lane>` — встроенный лейн, где `<lane>` — это `vless`,
  `reality`, `hysteria2`, `naive`, `trusttunnel`, `anytls`, `mieru`, `awg` или `mtproto`, а
  `<server_id>` — `0` для мастера или id ноды из `GET /v1/nodes`.
- `inbound:<id>` — свой инбаунд, по id из `GET /v1/servers/{id}/inbounds`.

Пустой массив `grants` означает, что группа **не ограничивает доступ**: сохранённая
так, она — тариф только по лимиту скорости, и её участники сохраняют все
подключения. Ответ несёт это как `limits_access` — это решается при сохранении
группы, а не считывается со списка грантов. Гранты также вычищаются автоматически,
когда удаляется инбаунд, нода или внешний сервер, который они называют, и группа,
потерявшая так последний грант, сохраняет `limits_access: true`: её участники не
достают ничего, вместо того чтобы внезапно достать всё. Сохраните её снова без
грантов, чтобы открыть. Группы, существовавшие до этого поведения, продолжают
ограничивать доступ, пока их не сохранят снова. `data` в ответе — группа.

**Задать участников** — тело `{ "user_ids": [1, 2, 3] }`; заменяет весь набор
участников.

**Задать группы пользователя** — тело `{ "group_ids": [4, 5] }`; заменяет всё
членство пользователя. Пустой массив убирает пользователя из всех групп (→
неограниченный доступ).

Гранты, ссылающиеся на удалённый инбаунд или ноду, вычищаются автоматически и до
тех пор безвредны.

**Откуда берутся токены** — `GET /v1/groups/targets` перечисляет каждый сервер с
подключениями, которые группа может выдать, каждое с готовым токеном:

```json
{ "data": [
  { "server_id": 0, "server_name": "Мастер",
    "lanes": [ { "lane": "vless", "label": "VLESS-TCP-TLS",
                 "token": "builtin:0:vless", "enabled": true } ],
    "inbounds": [ { "id": 7, "name": "WS резерв",
                    "token": "inbound:7", "enabled": true } ] }
] }
```

Выключенные лейны и инбаунды тоже включаются, поэтому грант можно подготовить до
включения подключения. Собирать такие токены вручную тоже можно, но опечатка
ничего не выдаёт — молча, — и именно этого и позволяет избежать этот эндпоинт.

### Конфигурация сервера

Эндпоинты выше управляют панелью; эти её настраивают. Всё здесь повторяет экран в
панели и вызывает тот же код за ним, поэтому значение, которое отклоняет
интерфейс, отклоняется и здесь.

Двух вещей намеренно нет. У **администраторов и ключей API** нет эндпоинтов:
ключ, способный создавать ключи, превращает одну утечку в постоянный,
самовозобновляемый доступ, а такое решение должно приниматься за сессией с
запросом пароля. **Секретный путь панели** не возвращается ни одним маршрутом
`/v1` — это слой неочевидности перед панелью, а не настройка для чтения.

```
GET   $BASE/v1/settings                        → рабочие настройки
PATCH $BASE/v1/settings                        → изменить часть из них
GET   $BASE/v1/servers/{id}/routing            → маршрутизация, DNS и egress-бэкенды
POST  $BASE/v1/servers/{id}/routing            → изменить их
POST  $BASE/v1/servers/{id}/xray-restart       → перезапустить Xray этого сервера
GET   $BASE/v1/config/snapshots                → точки сохранения конфигурации
POST  $BASE/v1/config/snapshots                → сделать одну
POST  $BASE/v1/config/snapshots/{id}/rollback  → восстановить конфигурацию сервера из неё
DELETE $BASE/v1/config/snapshots/{id}          → забыть её
```

`PATCH /v1/settings` применяет **только поля, которые несёт тело**. Всё
отсутствующее остаётся как есть, и именно поэтому безопасно прочитать объект,
изменить одно значение и отправить обратно одно значение — повторная отправка
всего объекта заодно применила бы то, что другой оператор изменил тем временем.
Сгруппированные поля (`hwid_*`, `local_backup_*`) внутри сохраняются одной записью,
поэтому накладываются на текущую строку, а не сбрасывают соседей в ноль.

```bash
curl -X PATCH $BASE/v1/settings -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"maintenance_mode":true}'
```

```json
{ "data": {
  "xray_dns": "https://dns.example/dns-query\n1.1.1.1",
  "decoy_template": "coming-soon",
  "decoy_templates": ["coming-soon", "YouTube", "…"],
  "maintenance_mode": true,
  "probe_detect": true, "probe_block": false,
  "watchdog_enabled": true, "watchdog_restarts": 0,
  "user_autodelete_days": 0,
  "hwid_enabled": false, "hwid_require": true,
  "hwid_fallback_limit": 0, "hwid_ttl_days": 30,
  "device_count_mode": "auto",
  "local_backup_cron": "", "local_backup_keep": 7,
  "sub_path": "sub", "warp_enabled": false, "warp_registered": true,
  "sub_order_mode": "manual", "sub_happ_crypt": false, "sub_page_url": "",
  "trusted_nets": ["198.51.100.0/24", "203.0.113.10/32"]
} }
```

`sub_order_mode` — как подписка упорядочивает серверы: `manual` (вес, затем
список), `nearest`, `load`, `nearest_load` или `random` — новый порядок при каждом
получении, поэтому клиенты, подключающиеся к первой записи, расходятся по парку;
скрытие при заполнении и при превышении при этом действуют. `sub_happ_crypt`
заставляет кнопку Happ на странице подписки и `GET /v1/users/{id}/happ-link`
выдавать зашифрованную ссылку `happ://crypt4/` вместо простого адреса.
`sub_page_url` — ваша собственная страница подписки: браузер, открывший ссылку
подписки, перенаправляется туда (`302`), `{token}` заменяется токеном
пользователя — например, `https://example.com/cabinet?sub={token}`, после чего
`GET /v1/users?sub_token=` находит пользователя. Приложения, получающие подписку, и
скачивания с `?format=` не перенаправляются; `""` возвращает страницу панели.
Ссылка на собственный путь подписки этой панели отклоняется (`err.subPageLoop`) и не
переходит ни под каким именем, по которому доступна панель; неизвестный токен
никогда не перенаправляется; а кнопка «открыть страницу подписки» в карточке
пользователя открывает собственную страницу панели через подписанную ссылку на час.
`trusted_nets` — это IP и сети, которые панель никогда не банит сама: ни за подбор
пароля SOCKS/HTTP, ни за сканирование панели, ни по политике источников (отказ при
этом всё равно попадает в журнал). Отправка заменяет весь список; записи хранятся
как префиксы (`198.51.100.7/24` становится `198.51.100.0/24`), сети шире IPv4 /8
или IPv6 /32 отклоняются, а баны, уже действующие внутри списка, снимаются.
Неизвестный `sub_order_mode`, плохой `sub_page_url` или запись `trusted_nets`
отклоняются до того, как записано хоть одно поле тела.

`device_count_mode` решает, что считает лимит устройств пользователя. `auto` (по
умолчанию) считает различные исходные адреса, замеченные за последние две минуты, —
единственное, что ограничивает, в скольких местах одна подписка используется
*одновременно*, — и отключает пользователя, только когда он непрерывно превышал
лимит две с половиной минуты, чтобы смена сети или ротация адреса у оператора
прошли, не задев его. `hwid` вообще перестаёт считать адреса, оставляя единственным
ограничением состав привязанных установок, и ради этого отказывается от контроля
одновременности: HWID ограничивает тех, кто может получить подписку, а не тех, кто
может подключиться. `both` принимается для строк, записанных до того, как два
режима слились, и ведёт себя как `auto`. Всё остальное отклоняется, а не молча
проваливается в значение по умолчанию.

`active_devices` у пользователя — это сырое число адресов, замеченных в окне, и оно
сообщается независимо от того, применяется ли что-то; `status` становится
`device_limited`, только когда отключение реально произошло.

Три из этих настроек имеют эффект, которого не несёт одна лишь база данных, —
шаблон маскировки, обнаружение сканеров и режим обслуживания проверяются на каждом
запросе, — поэтому API подменяет их вживую точно как панель. Неизвестный
`decoy_template` отклоняется до записи чего-либо; запись `xray_dns`, которая не
является IP, `host:port`, URL или `localhost`, отклоняется так же, как её
отклоняет панель, потому что DNS-сервер, который Xray не может разобрать, ломает
каждую следующую перегенерацию конфигурации.

**Маршрутизация** задаётся по серверам, и сервер `0` — собственная машина панели:
та же нумерация, что у `/v1/servers/{id}/inbounds`. `GET` и `POST` говорят одной формой:

```json
{ "data": {
  "routing": { "block_ads": true, "block_bittorrent": false, "lanes": [], "…": null },
  "xray_dns": "1.1.1.1",
  "warp_enabled": false,
  "opera_enabled": false,
  "opera_country": "EU"
} }
```

Пропущенное поле **остаётся без изменений**; `routing`, когда он присутствует,
заменяет набор правил целиком. Разделение намеренное: слияние *списков* правил не
имеет предсказуемого для вызывающего смысла (короткий список удаляет правила или
оставляет их?), а молчаливое выключение egress-бэкенда из-за того, что тело его не
упомянуло, — это как раз то, из-за чего туннелируемый трафик начинает уходить с
собственного IP сервера. Поэтому отправляйте `routing`, чтобы менять правила, и
называйте только те бэкенды, которые действительно собираетесь двигать.

**Каскад** — это лейн, у которого апстримы — наши собственные серверы вместо
прокси: пользователи подключаются к этому серверу и выходят через серверы из
`via`, каждый по одному из его встроенных подключений.

```json
{ "id": "nl", "name": "Through NL", "enabled": true,
  "urls": [], "manual": [], "domains": [], "ips": [],
  "via": [ { "server": 0, "bridge": "reality" }, { "server": 3, "bridge": "hysteria2" } ] }
```

`server` — id сервера (`0` — собственная машина панели), никогда не этот сервер.
`bridge` — подключение выхода, по которому каскад до него доходит: `reality` (по
умолчанию), `vision` или `hysteria2`, и оно должно быть там включено. Каждый сервер
в `/v1/nodes` (и `/v1/nodes/{id}`) перечисляет их:

```json
"bridges": [
  { "bridge": "reality",   "name": "VLESS-XHTTP-REALITY", "enabled": true },
  { "bridge": "vision",    "name": "VLESS-TCP-TLS",       "enabled": true },
  { "bridge": "hysteria2", "name": "HYSTERIA-UDP",        "enabled": false }
]
```

`name` — то, как этот сервер называет подключение (оператор мог его
переименовать); использовать можно только `enabled`. Поставьте лейн последним в
`routing_order`, чтобы через него шло всё остальное.

Панель сама выводит учётные данные моста и пускает его на выходы только с адресов
этого сервера; трафик пользователя считается один раз, здесь. Трафик лейна никогда
не уходит с этого сервера: если ни один выход не признан живым, он всё равно идёт
на один, а если выходов нет вовсе — отбрасывается. Каскадный лейн не принимает
`urls` или `manual`: его апстримы — только выходы. Отказы: `err.cascadeSelf`,
`err.cascadeNoServer`, `err.cascadeLaneOff` (подключение выключено на этом выходе),
`err.cascadeLoop` (собственные каскады выхода ведут обратно сюда),
`err.laneBadBridge`. Проверяются только лейны, новые или изменённые сохранением,
поэтому выход, исчезнувший позже, не блокирует другие правки. На выходе выключение
подключения, которое использует каскад, отклоняется с `err.cascadeExitLaneOff`, а
выключение сервера или его удаление — с `err.cascadeExitInUse`.

**Снимки** захватывают конфигурацию сервера целиком — протоколы, порты, REALITY,
маршрутизацию, egress, DNS, заглушку и свои инбаунды — как одну точку сохранения.
Откат восстанавливает всё это, *кроме* сертификата и домена, поэтому отмена никогда
не сломает живой сертификат, и сначала делает автоматическую точку сохранения
текущего состояния, чтобы сам откат можно было отменить. Он перегенерирует и
перезапускает Xray; поскольку ноды наследуют поля мастера, этот перезапуск — на весь
парк, и все живые подключения обрываются.

```bash
curl -X POST $BASE/v1/config/snapshots -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"label":"before the egress change"}'
```

Ответ несёт ту точку сохранения, которую сделал этот вызов, по id — а не
«самую новую», которая была бы чьим-то снимком, если между ними успело пройти
чужое создание.

`xray-restart` выполняется сразу для сервера `0` и ставится в очередь для ноды,
которая подхватывает его на следующей синхронизации, — `200` там означает
*принято*, а не *сделано*.

### Статистика

```
GET $BASE/v1/stats/series?user_id=5&from=2026-01-01&to=2026-01-31        → трафик по дням
GET $BASE/v1/stats/nodes?user_id=5&from=2026-01-01&to=2026-01-31         → итоги по серверам
GET $BASE/v1/stats/nodes/series?user_id=5&from=2026-01-01&to=2026-01-31  → по дням, по серверам
GET $BASE/v1/stats/users?from=2026-01-01&to=2026-01-31                   → итоги по пользователям
```

`user_id` сужает `series`, `nodes` и `nodes/series` до одного аккаунта; пропустите
его для цифры по всей панели. У `users` нет `user_id` — он и так отвечает по
пользователям. `from`/`to` — `YYYY-MM-DD` в часовом поясе, настроенном в панели, и
оба по умолчанию — **последние 30 дней**: пропущенное окно — это окно, а не запрос
ничего. Кривой или перевёрнутый диапазон — это 400, а не пустой ответ.

Присутствует каждый день диапазона, включая те, что ничего не несли:

```json
{ "data": [
  { "day": "2026-01-01", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-02", "up": 0, "down": 0 },
  { "day": "2026-01-03", "up": 46059475, "down": 1488367869 }
] }
```

Тихий день не пишет строки внутри, поэтому сохранённая история — это список
занятых дней, а не ряд; эти эндпоинты заполняют пробелы, потому что дыра и ноль —
разные формы для всего, что считает скользящее среднее.

`nodes` разбивает тот же трафик по серверу, который его нёс, начиная с самого
загруженного: `series` говорит сколько, а это говорит где. `node_id` равен `0` для
собственного сервера панели; имена подставляются за вас, включая серверы, удалённые
с тех пор (их строки трафика переживают их).

```json
{ "data": [
  { "node_id": 2, "name": "NL", "up": 46059475, "down": 1488367869 },
  { "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 }
] }
```

`nodes/series` — оба измерения сразу: одна строка на день на сервер, поэтому один
вызов рисует линию на каждый сервер:

```json
{ "data": [
  { "day": "2026-01-01", "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-01", "node_id": 2, "name": "NL",     "up": 46059475, "down": 1488367869 },
  { "day": "2026-01-02", "node_id": 0, "name": "Мастер", "up": 0,        "down": 0 },
  { "day": "2026-01-02", "node_id": 2, "name": "NL",     "up": 12000000, "down": 340000000 }
] }
```

Серверы, не несшие ничего за всё окно, отсутствуют вовсе; у тех, что есть, строка
на каждый день.

Откуда пришли подключения, а не сколько они принесли:

```
GET $BASE/v1/stats/countries  → недавние подключения по странам
GET $BASE/v1/stats/asns       → то же, по операторам сети
```

Оба считают **различные исходные IP** и их активность за окно хранения
подключений, начиная с самых активных. `asn` равен `0`, а `org` пуст для адреса,
который не покрыт ни одной таблицей маршрутизации (частного или немаршрутизируемого):

```json
{ "data": [
  { "asn": 15169, "org": "GOOGLE", "ips": 23, "hits": 2548 },
  { "asn": 13335, "org": "CLOUDFLARENET", "ips": 4, "hits": 61 }
] }
```

Каждый ответ считается по всей таблице подключений, поэтому оба мемоизируются
примерно на полминуты: два вызова в секунду получают одни и те же цифры, а панель
сохраняет своё единственное подключение к базе для всего остального.

### Какие итоги что значат

Существуют два семейства счётчиков, и они отвечают на разные вопросы. Перепутать
их — выглядит в точности как баг двойного счёта:

| Число | Источник | Сбрасывается |
|---|---|---|
| `total_up` / `total_down` в `/v1/summary` | счётчики квоты пользователей | сбросом трафика или сменой периода тарифом |
| `/v1/stats/series`, `/v1/stats/nodes` | дневная история трафика | ничем — она накапливается |

Итак, итоги в `/v1/summary` — это **расход в текущем периоде квоты**, с которым
сравнивается лимит трафика, и они регулярно *меньше* истории за тот же промежуток.
Это не пропавший трафик: это счётчики пользователя, сброшенные, пока его история
осталась. Считайте деньги по счётчикам квоты, отчитывайтесь по истории и не ждите,
что эти двое сойдутся.

```
GET $BASE/v1/stats/abuse?limit=50   → недавние совпадения с блоклистами по всему парку
```

### Журналы

Два следа только для чтения. **События** — это то, что произошло с пользователями;
**журнал администраторов** — это то, что администраторы и ключи API сделали с
панелью, включая всё сделанное через этот API, с указанием имени ключа.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/events` | События пользователей с фильтрами. |
| `GET` | `/v1/events/catalog` | Ключи событий, которые может нести строка. |
| `GET` | `/v1/admin-audit` | Журнал администраторов. |
| `GET` | `/v1/admin-audit/catalog` | Его категории и действия в каждой. |

Оба листаются **назад**: передайте
`before=<id самой старой строки, которая у вас есть>` и читайте `next_before` из
ответа — `0` означает, что вы дошли до конца. Id
монотонны, поэтому курсор остаётся стабильным, пока новые строки ложатся сверху.

```json
{ "data": { "events": [ { "id": 812, "user_id": 5, "action": "plan.cancelled", … } ],
            "next_before": 780 } }
```

`/v1/events` принимает `action` (один ключ из каталога), `actor` (`admin` / `user` /
`system` / `api`), `user_id` и пару для листания. `/v1/admin-audit` принимает
`category` (разворачивается в действия, которые в неё входят), `action`, `actor` и
пару для листания. Неизвестный `action` или `category` — это `400`, а не пустая
страница: фильтр, который тихо ничего не находит, неотличим от тихого периода.

### Вебхуки

Push-половина интеграции, настраиваемая из самой интеграции.

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/webhooks` | Перечислить настроенные эндпоинты. |
| `GET` | `/v1/webhooks/events` | Ключи событий, на которые может подписаться вебхук. |
| `POST` | `/v1/webhooks` | Добавить эндпоинт. |
| `POST` | `/v1/webhooks/{id}` | Обновить один (объект целиком). |
| `DELETE` | `/v1/webhooks/{id}` | Удалить один. |
| `POST` | `/v1/webhooks/{id}/test` | Отправить тестовую доставку. |

Тело: `{ "url": "https://…", "events": ["user.created"], "enabled": true }`. Пустой
массив `events` означает **все** события. `enabled` необязателен при создании (по
умолчанию включён). Формат доставки, подпись и политика повторов описаны ниже в
разделе **Вебхуки**.

Тестовая доставка отвечает `200`, даже когда эндпоинт падает: вызов удался,
доставка — это результат:
`{ "data": { "status": 502, "ok": false, "error": "…" } }`.

### Заявки на регистрацию

Очередь регистраций под модерацией (имеет смысл, только пока самостоятельная
регистрация в режиме модерации — `moderation` говорит, так ли это). Заявка
принадлежит чату Telegram (`chat_id`) или клиенту внешней системы (`external_id`,
из `POST /v1/signup`).

| Метод | Путь | Описание |
| --- | --- | --- |
| `GET` | `/v1/registrations` | Заявки в ожидании. |
| `POST` | `/v1/registrations/{id}/approve` | Создать аккаунт и привязать его чат Telegram или id внешней системы. |
| `POST` | `/v1/registrations/{id}/reject` | Отклонить заявку. |

### Мониторинг

```
GET $BASE/v1/summary          → итоги по пользователям / онлайну / трафику, статус Xray и сертификата
GET $BASE/v1/system           → живой CPU / RAM / диск / сеть / пропускная способность VPN
GET $BASE/v1/system/auto-update       → {"cron": "0 4 * * *", "nodes": true, "last_at": …, "last": "latest"}
POST $BASE/v1/system/auto-update {"cron": "0 4 * * *"}  ("" выключает; ноды всегда следуют)
GET $BASE/v1/health/report    → полная самодиагностика (xray, конфигурация, TLS, geo, egress-лейны)
GET $BASE/v1/nodes/{id}/health → диагностика одного сервера (id 0 = мастер)
POST $BASE/v1/nodes/{id}/reach → {"host": …, "port": 443, "countries": [{"code": "RU", "ok": 9, "blocked": 1, "failed": 0, "probes": […]}]}
POST $BASE/v1/reach {"countries": ["RU", "CN", "IR"], "probes": 10, "every": 60, "threshold": 50}  (every 0 = только по запросу)
GET $BASE/v1/nodes/{id}/logs   → последние строки лога ноды
GET $BASE/v1/logs              → строки лога самой панели
GET $BASE/v1/backup/info       → что содержал бы бэкап, сделанный сейчас
GET $BASE/v1/backup            → скачать этот бэкап (тело .tar.gz, не JSON)
GET $BASE/v1/metrics           → выдача для Prometheus (текст, не JSON)
```

#### Инциденты и работы (статус-страница)

```
GET    $BASE/v1/incidents                → {"incidents": [...], "servers": [{"id": 0, "name": "Main"}, ...]}
POST   $BASE/v1/incidents                {"kind": "maintenance", "title": "Works on NL", "body": "…",
                                          "node_ids": [2], "starts_at": 1767225000, "ends_at": 1767236000,
                                          "notify": true, "lang": "en"}          → 201 {"incident": {...}}
POST   $BASE/v1/incidents/{id}           то же тело: переписать запись (признак «разрешён» сохраняется)
POST   $BASE/v1/incidents/{id}/updates   {"stage": "identified", "body": "Found it", "notify": true}
POST   $BASE/v1/incidents/{id}/resolve   {"note": "Fixed", "notify": true}       (тело необязательно)
POST   $BASE/v1/incidents/{id}/compensate {"hours": 3, "notify": true}         (users.manage)
DELETE $BASE/v1/incidents/updates/{id}
DELETE $BASE/v1/incidents/{id}
```

`kind` — `incident` (открыт до разрешения) или `maintenance` (запланирован до
`starts_at`, идёт до `ends_at` — 0 означает «до разрешения»). Пустой `node_ids`
означает весь сервис; id — те, что в списках `servers`. `hide_in_sub` (только для
работ) убирает названные серверы из подписок, пока идёт окно, — если только это не
оставит подписку без единого сервера. `stage` у обновления — `investigating`,
`identified` или `monitoring` (только для инцидентов) либо `update` (для обоих, по
умолчанию); `note`, данный при разрешении, закрывает ход как шаг `resolved`.
`notify` рассылает его каждому пользователю с активной подпиской через
пользовательского бота и требует права на рассылки; когда отправить не удалось,
инцидент всё равно сохраняется, а `notify_error` говорит почему. Работы, которые ещё
не начались, разрешить нельзя — перенесите их или удалите.

`compensate` возвращает время за завершённую запись один раз: `hours` (1–2160)
добавляются к подписке каждого включённого пользователя, у которого шёл срок, когда
запись началась, и который может пользоваться названным ею сервером. Кто имел
идущий срок, записывается в начале записи (когда она опубликована или когда
открывается окно работ; `snapshot_at`), поэтому пользователь, продливший позже,
ничего не получает. Срок, истёкший с тех пор, получает часы от текущего момента;
сроки без конца не трогаются. После этого инцидент несёт `compensated_at`,
`compensated_seconds` и `compensated_users`; `notify` сообщает каждому из этих
пользователей через пользовательского бота и требует права на рассылки.

`/v1/metrics` — цель сбора для Prometheus, аутентифицируемая тем же ключом API:

```yaml
scrape_configs:
  - job_name: rospanel
    scheme: https
    metrics_path: /<api-path>/v1/metrics
    authorization:
      credentials: rp_...
    static_configs:
      - targets: ["vpn.example.com"]
```

Он публикует число пользователей, трафик за всё время и за день, живую пропускную
способность, состояние Xray и сертификата, а также CPU/RAM/диск самого хоста панели.

Каждый сервер также получает собственные ряды с метками `node` и `node_id` (мастер —
`node_id="0"`): `rospanel_node_online`, `rospanel_node_enabled`,
`rospanel_node_xray_running`, `rospanel_node_last_seen_seconds`,
`rospanel_node_traffic_today_bytes{direction=…}`, плюс машина под ним —
`rospanel_node_cpu_percent`, `rospanel_node_memory_bytes{state=…}`,
`rospanel_node_disk_bytes{state=…}` и `rospanel_node_host_uptime_seconds`. У ноды,
которая никогда не отчитывалась (или чей агент старше этих полей), просто нет
замеров — именно это и должен означать разрыв на графике, а не ряд нулей, который
читается как простаивающая машина.

Рядов **по пользователям** намеренно **нет**: панель с тысячей пользователей
породила бы тысячу временных рядов на каждую метрику.

`/v1/nodes/{id}/logs` отдаётся по следующему long-poll ноды, поэтому только что
проснувшаяся нода может вернуть предыдущую пачку — `at` это время Unix, когда
строки были собраны.

`/v1/backup` отдаёт сам архив потоком (`Content-Type: application/gzip`), поэтому
это единственный эндпоинт вне обёртки `{"data": …}` — направьте на него планировщик,
чтобы держать копии вне машины. **Восстановление намеренно не выставляется**: оно
готовится на диске и применяется при следующем запуске, поэтому через API это был
бы запрос, который молча заменяет всё при следующем перезапуске.

## Заголовки ответа подписки

`GET /v1/users/{id}/subscription` возвращает адрес; сам ответ, который тянет клиент, несёт
то, что приложение показывает, не разбирая профиль:

| Заголовок | Значение |
| --- | --- |
| `Profile-Title` | название, base64 после префикса `base64:` |
| `Profile-Update-Interval` | часы между обновлениями; нет вовсе, если в панели задано «никогда» |
| `Subscription-Userinfo` | `upload=…; download=…; total=…; expire=…` в байтах и в секундах Unix; `total=0` — без лимита, `expire=0` — без конца |
| `Profile-Web-Page-Url` | страница пользователя, пока она есть |
| `support-url` | ссылка поддержки или Telegram, если задана |
| `Announce` | объявление оператора с префиксом `base64:`; Happ и v2RayTun печатают его строкой |
| `Moved-Permanently-To` | куда переехала эта подписка, токен пользователя уже подставлен |

`Moved-Permanently-To` — это переезд домена: задайте адрес один раз в **Настройки →
Подписки**, с `{token}` там, где должен стоять токен
(`https://new.example.com/sub/{token}`), и с этого момента каждый клиент, читающий заголовок,
обновляется оттуда — пользователю не нужно импортировать ссылку заново. Клиенты, которые
заголовок игнорируют, продолжают работать через старый адрес. Очистите поле, когда панель
снова тот дом, с которым клиенты и должны говорить.

При включённой авто-маршрутизации Happ и INCY получают ещё `routing` (сам deeplink, не его
URL) и `routing-enable: 1`; Clash и Mihomo вместо этого получают правила внутри YAML.

## MCP (ИИ-ассистенты)

Панель отдаёт этот API ассистенту по самому протоколу Model Context Protocol.
Устанавливать нигде ничего не нужно: ассистент, которому достаточно URL:

```
$BASE/v1/mcp/<api-key>
```

Ключ едет в пути, потому что такие диалоги принимают только URL и ничего больше:
**адрес и есть учётные данные**, такой же секрет, как ключ внутри него, и он
перестаёт работать в момент отзыва ключа. Соберите его вручную из двух значений,
которые даёт *Настройки → API*, — базового адреса, показанного там, и ключа в момент
создания (он больше не показывается).

Набор инструментов — это права ключа: ассистенту предлагаются ровно те инструменты,
что стоят за маршрутами, которые ключ может вызвать, а вызов любого другого отвечает
«unknown tool». Для ассистента, который должен только смотреть, создайте ключ без
единой отметки на запись — тогда ассистент, действующий по неверно понятой фразе, не
сможет удалить клиента, что бы его ни попросили.

Транспорт — Streamable HTTP протокола MCP: одно сообщение JSON-RPC на `POST`, ответ —
`application/json`; уведомления получают `202` без тела; `GET` — `405` (у этого
эндпоинта нет инициируемого сервером потока). Вызовы исполняются против
собственного REST API панели в том же процессе, поэтому несут те же права, тот же
журнал и те же формы ошибок, что и любой другой клиент `/v1`.

### Размер ответа

Вызов списка без `limit` получает **50 строк**, а не 100, как по умолчанию в REST:
ассистент платит за каждую строку в контексте. Попросите больше явно — и получите,
включая `limit=0` (всё).

Сверху стоит жёсткий потолок в **512 КБ на вызов**. Ответ больше него укорачивается
целыми строками, и `meta` говорит об этом — `limit` становится числом фактически
возвращённых, а `total` по-прежнему сообщает, сколько их всего, поэтому листание по
`limit`/`offset` добирает остальное. Результат остаётся валидным JSON.

**Бэкапы не предлагаются как инструменты вообще.** `GET /v1/backup` — потому что
его тело это tar-архив, который ассистент не прочитает, а `GET /v1/backup/info` —
потому что знать, что содержал бы дамп, полезно только тому, кто собирается его
сделать, — это работа оператора, выполняемая из панели, где файл действительно
куда-то попадает. Восстановления в `/v1` нет ни в каком виде: оно живёт в панели за
сессией и повторно введённым паролем, поэтому никакой ключ — и никакой ассистент с
ним — не может вернуть бэкап обратно.

Список инструментов генерируется из документа OpenAPI выше, поэтому он никогда не
расходится с API: эндпоинт, добавленный в `/v1`, становится инструментом без того,
чтобы кто-то помнил о его регистрации, а удалённый исчезает. Это касается и
половины с настройками — ассистент, которому позволяет его ключ, может читать и
менять настройки, переписывать маршрутизацию сервера, делать и откатывать точки
сохранения конфигурации и перезапускать Xray.

Каждый инструмент несёт аннотации, по которым клиент решает, спрашивать ли своего
человека сначала (`readOnlyHint`, `destructiveHint`). Какие записи считаются
разрушительными, **объявляется маршрутом**, а не угадывается по его формулировке, —
переписанное предложение не должно иметь возможности отключить предупреждение, и
вызовы, которые перенаправляют трафик, перезапускают Xray, откатывают конфигурацию
или переводят панель в режим обслуживания, отмечены все. Ответы приходят текстом, а
когда панель ответила JSON — ещё и как `structuredContent`; один ответ ограничен,
чтобы один вызов не мог заполнить контекст ассистента, — просите страницу поменьше
(`limit`/`offset`), а не всё сразу.

## Примеры

Создать пользователя:

```bash
curl -sS -X POST "$BASE/v1/users" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"alice","data_limit":0,"expire_at":0}'
```

Получить ссылку подписки пользователя:

```bash
curl -sS "$BASE/v1/users/5" -H "Authorization: Bearer $KEY" \
  | jq -r '.data.sub_url'
```

Удалить пользователя:

```bash
curl -sS -X DELETE "$BASE/v1/users/5" -H "Authorization: Bearer $KEY"
```

# Вебхуки

Вместо опроса API можно заставить панель **присылать** события жизненного цикла на
ваш собственный HTTP-эндпоинт. Настройте их в панели → **Настройки → API →
Вебхуки** (добавьте URL получателя и отметьте нужные события — не отметить ни
одного = все) либо через сам API: `POST /v1/webhooks`.

Адреса вебхуков, в отличие от исходящих запросов API, могут быть `http` **или**
`https` и **могут указывать на приватный/localhost-хост** — получатель часто
оказывается внутренним сервисом самого оператора, а каждая доставка — слепой POST
(тело ответа никогда не читается).

| `incident.resolved` | его разрешили или работы отметили завершёнными; окно, которое просто закрывается по `ends_at`, ничего не шлёт |
| `incident.deleted` | его удалили; `data` — инцидент в том виде, каким он был |
| `broadcast.sent` | рассылка ушла — одна доставка на рассылку: `data.id`, `data.text`, `data.buttons`, `data.audience`, `data.group_id` (только когда рассылка сужена до группы доступа), `data.media_kind`/`data.media_name`, `data.telegram_recipients` (чаты, в которые её шлёт бот), `data.users` (`id`, `external_id`) — аккаунты из аудитории, до которых бот не достаёт, кроме тех, кто выключил рассылки в боте. С подпиской на это событие рассылки работают при выключенном боте (только текст) |

## Формат доставки

Каждая доставка — это HTTP `POST` с телом JSON:

```json
{
  "id": "3f1c…",                 // уникальный id доставки
  "event": "user.created",
  "created_at": 1767225600,
  "data": { "id": 7, "name": "alice", "status": "active", "enabled": true,
            "expire_at": 0, "data_limit": 0, "plan_id": 0,
            "external_id": "", "telegram_id": 0, "mailing": true, "lang": "ru" }
}
```

`data` — это объект пользователя (`id`, `name`, `status`, `enabled`, `expire_at`,
`data_limit`, `plan_id`, те id, по которым вы знаете пользователя, — `external_id`,
`""` когда его нет, и `telegram_id`, 0 когда его нет, — `mailing` и `lang`, `""`
когда неизвестен) для каждого события о пользователе — `user.*`, `plan.*`,
`balance.adjusted`, `referral.reward` (приглашающий), `promo.*` — плюс поля,
которые таблица событий перечисляет для него; заказ на оплату для `payment.*`, с
`data.user` (тем объектом пользователя, каким его оставил заказ) и
`data.user_balance_kop` (его баланс сейчас; собственный `balance_kop` заказа — это
часть цены, которую покрыл баланс); заявка (`request_id`, `name`, `telegram_id` или
`external_id`) для `registration.requested` и `registration.rejected`; и рассылка
для `broadcast.sent`.

Заголовки:

```
Content-Type: application/json
User-Agent: RosPanel-Webhook/1
X-RosPanel-Event: user.created
X-RosPanel-Signature: sha256=<hex HMAC-SHA256 of the raw body>
```

## Проверка подписи

У каждого вебхука есть секрет (показан в панели). Пересчитайте HMAC по **сырому
телу запроса** и сравните за постоянное время:

```python
import hmac, hashlib

def verify(secret: str, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

```js
import crypto from "node:crypto";

function verify(secret, body, header) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(body).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(header));
}
```

## Повторы и доставка

Верните статус `2xx`, чтобы подтвердить. Ответ не-`2xx` или ошибка соединения
повторяются с растущей задержкой (примерно 10 с, 30 с, 2 мин, 10 мин — до 5
попыток), затем доставка отбрасывается. Ожидающие доставки хранятся в базе панели,
поэтому массовое действие на тысячи пользователей отправляет каждое событие, а
перезапуск отправляет то, что ждало. Доставки могут приходить **не по порядку** и,
при повторе или после перезапуска, **более одного раза** — считайте поле `id`
ключом идемпотентности. Кнопка **Test** в панели отправляет доставку `ping`, чтобы
вы могли подтвердить доступность и проверку подписи. Статус последней доставки
показан рядом с каждым вебхуком.
