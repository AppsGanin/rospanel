# واجهة RosPanel REST API

**مرجع تفاعلي:** [Swagger UI](reference.md) — جميع نقاط النهاية، معروضة من مستند OpenAPI نفسه.


تتيح واجهة REST API الخارجية لنظام محيط (خدمة فوترة، متجر على Telegram، سكربت تزويد) إدارة اللوحة عبر HTTP باستخدام مفتاح API. وهي تستدعي المنطق الداخلي نفسه الذي تستدعيه لوحة الإدارة، فلا ينفصل أحدها عن الآخر.

## تمكين API

افتح اللوحة → **Settings → API**. إنشاء أول مفتاح يشغل الواجهة ويولد عنوان URL أساسيا ثابتا يتعذر تخمينه:

```
https://<your-host>/<api_path>/v1
```

المقطع `<api_path>` منفصل عن مسار اللوحة المخفي، لذا فإن تدوير سر اللوحة لا يكسر أي تكامل. ويمكنك تدوير مسار API أو تعطيله من الصفحة نفسها (التدوير يغير عنوان URL الأساسي، وتبقى المفاتيح تعمل تحت العنوان الجديد).

## التوثيق التفاعلي والمواصفة المقروءة آليا

تنشر واجهة API مواصفة OpenAPI 3.0 الخاصة بها، مولدة من شيفرة الخادم (المخططات مستخرجة من أنواع Go الفعلية، فلا تنفصل عنها أبدا):

```
GET $BASE/openapi.json    → the OpenAPI 3.0 document
GET $BASE/docs            → Swagger UI (try endpoints in the browser)
```

يقدم كلاهما دون مفتاح (عنوان URL الأساسي نفسه هو السر). افتح `…/docs`، وانقر **Authorize**، وألصق مفتاحا، ثم استدع أي نقطة نهاية مباشرة. وجه Postman أو `openapi-generator` أو أي مولد عملاء إلى `…/openapi.json` لتوليد عميل ذي أنواع. (هيكل Swagger UI يحمل من CDN، أما المواصفة التي يعرضها فمحلية بالكامل.)

## المصادقة

يجب أن يحمل كل طلب مفتاحا أنشئ في **Settings → API**. يظهر المفتاح الخام **مرة واحدة** عند الإنشاء — احفظه فورا؛ فلا يبقى منه بعد ذلك سوى بادئته. أرسله كرمز bearer:

```
Authorization: Bearer rp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

(يقبل أيضا `X-API-Key: <key>`.) المفاتيح الملغاة تتوقف عن العمل فورا.

المفتاح الغائب أو غير الصالح يعيد `401`. والواجهة محدودة المعدل لكل عنوان IP.

يكون للمفتاح **وصول كامل** أو **طرق API المؤشرة له** (`GET /v1/users`، `POST /v1/signup`، …) عند إنشائه، ويمكن تغيير ذلك لاحقا. وهو يستدعي تلك الطرق بالضبط؛ وأي شيء آخر يجيب بـ `403` مع `"code": "forbidden"`، ونقطة نهاية MCP تسرد تلك الأدوات فقط. ولا أحد يؤشر طريقة لا يحق له استدعاؤها بنفسه، والمالك وحده يمنح الوصول الكامل (أو النسخ الاحتياطية). والمفتاح الذي أنشئ قبل إمكانية تأشير الطرق يظل يصل إلى ما تفتحه أذوناته، حتى يجرى تعديله.
يتحقق `PATCH /v1/settings` و`PATCH /v1/nodes/{id}` من كل حقل مقابل قسمه (DNS والخروج يحتاجان `routing.manage`، والشبكات الموثوقة وإعدادات الفحص تحتاج `security.manage`).

الوصول الكامل يبلغ ما يبلغه المالك وحده في اللوحة — بما في ذلك النسخ الاحتياطية (`/v1/backup`) وجدولة النسخ المحلي — لذا لا يستطيع إلا المالك إنشاء مفتاح كهذا أو إلغاؤه.

## غلاف الاستجابة

النجاح:

```json
{ "data": { ... } }
```

الخطأ:

```json
{ "error": { "code": "bad_request", "message": "name is required" } }
```

الرموز الشائعة: `bad_request` (400)، `unauthorized` (401)، `not_found` (404)، `unsupported_media_type` (415)، `internal` (500).

المدخلات التي ترفضها اللوحة تحمل حقلين إضافيين — سبب الرفض، ومعاملات ذلك السبب:

```json
{ "error": {
    "code": "bad_request",
    "key": "err.planHasUsers",
    "message": "the plan is assigned to 12 users — move them to another plan first",
    "args": { "count": 12 }
} }
```

يبقى `code` الفئة العريضة التي تتفرع عليها لإعادة المحاولة؛ و`key` هو السبب المحدد المستقر الذي تتفرع عليه للسلوك — لا تطابق على `message` أبدا، فمن الحر إعادة صياغته. و`message` بالإنجليزية دائما (اللوحة تترجم الرموز نفسها في المتصفح، باللغة التي اختارها المسؤول)؛ ويتيح `args` للعميل صياغة نصه الخاص دون تحليل النثر. ويغيب كلاهما حين لا يكون وراء الفشل رمز (جسم مشوه، مسار مجهول).

## أجسام الطلبات

الحقل الذي لا تعرفه نقطة النهاية خطأ، لا شيء يتجاهل:

```json
{ "error": {
    "code": "bad_request",
    "message": "unknown field \"groups\" — see GET /v1/openapi.json for the fields this endpoint accepts"
} }
```

قبول الجسم وإسقاط الحقل بهدوء أسوأ من رفضه: فالمستدعي الذي يرسل `{"groups": [2,4]}` إلى نقطة نهاية تتوقع `group_ids` يستلم نجاحا دون أي تغيير في العضوية، ولا يكتشف ذلك إلا عند قراءته القيمة في المرة التالية. لذا تحقق من الإملاء مقابل المواصفة — فهي مولدة من الشيفرة، فلا يمكنها سرد حقل لا تقرأه اللوحة.

لا تعلم هناك `required` إلا الحقول التي تتطلبها نقطة النهاية فعلا. وما عدا ذلك يجوز حذفه ويحتفظ بقيمته الافتراضية الموثقة؛ ولن تحتاج أبدا إلى إرسال كائن كامل لتغيير شيء واحد.

### التعديلات المتزامنة

لا يوجد إصدار ولا `If-Match` على الكتابات: فالمستدعيان اللذان يغيران الكائن نفسه يحل الأمر بينهما بأسبقية الكتابة الأخيرة، ولا يعلم أي منهما. وهذا يهم أكثر حيث تحمل الكتابة حقولا لم تقصد تغييرها — فتعديل عقدة يعيد إرسال العقدة كاملة، فيمكن لتغيير توجيه مكتوب من هنا أن يطمس اسما وضعه أحدهم في اللوحة قبل ثانية.

عمليا نادرا ما يضر، لأن نقاط النهاية التي تعدل جزئيا (`PATCH /v1/settings`، `PATCH /v1/users/{id}`) تطبق الحقول التي يحملها الجسم فقط، فلا يتصادم مستدعيان يمسان حقولا *مختلفة*. وإذا كنت تؤتمت تعديلات على الكائن نفسه من أكثر من مكان، فاقرأه بعد الكتابة بدلا من افتراض أن قيمتك ثبتت.

## ترقيم الصفحات

كل نقطة نهاية للقوائم تأخذ `?limit` و`?offset` وتجيب بكتلة `meta`:

```json
{ "data": [ … ], "meta": { "total": 1043, "offset": 0, "limit": 100 } }
```

القيمة الافتراضية لـ `limit` هي **100** والحد الأقصى **1000**؛ و`limit=0` (أو سالب) يعني «كل شيء بدءا من `offset`»، وهو طلب مقصود لا الافتراضي — فالافتراضي غير المحدود هو ما يجعل تكاملا يعمل بلا مشكلة عاما كاملا ثم ينتهي وقته على لوحة كبرت. ويحصي `total` الصفوف بعد التصفية وقبل النافذة، فيستطيع المستدعي ترقيم الصفحات دون تخمين.

أما السجلات (`/v1/events`، `/v1/admin-audit`) فلها ترقيم مختلف، بالمؤشر (`?before=<oldest id held>`): صفوفها تتزحزح مع وصول صفوف جديدة، والترقيم بالإزاحة سيقفز فوق مدخلات أو يكررها.

## نقاط النهاية

يكتب عنوان URL الأساسي أدناه `$BASE` (مثل `https://vpn.example.com/ab12cd34/v1`).

### الحالة الصحية

```
GET $BASE/health → { "data": { "status": "ok" } }
```

#### فحص الحيوية (بلا مفتاح API)

`GET $BASE/healthz` هو نقطة النهاية الوحيدة التي لا تحتاج مفتاحا — وجه إليها مراقب الجهوزية أو موازن الحمل. وهي تجيب **503** (لا 200) حين لا يكون Xray يعمل: فقد تكون اللوحة بخير، لكن العقدة لا تحمل أي حركة VPN، وهذا ما تريد أن ينبهك إليه.

```
GET $BASE/healthz
200 → { "data": { "status": "ok",       "xray": "running", "xray_started_at": 1752230400 } }
503 → { "data": { "status": "degraded", "xray": "down",    "xray_started_at": 0 } }
```

وجودها تحت مسار API لا في جذر الخادم مقصود: فـ `/healthz` بلا مصادقة في الجذر سيجيب JSON لأي ماسح ويكشف اللوحة، فيبطل الطعم. ومسار API ثابت عبر تدوير السر، فيبقى المراقب الموجه إليه عاملا.

### المستخدمون

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/users` | سرد المستخدمين (تصفية + ترقيم)؛ `?telegram_id=` أو `?sub_token=` أو `?external_id=` يعثر على واحد. |
| `POST` | `/v1/users` | إنشاء مستخدم. |
| `POST` | `/v1/signup` | تسجيل عميل من نظام خارجي أو من بوتك وفق قواعد التسجيل الذاتي (انظر أدناه). |
| `POST` | `/v1/users/bulk` | تطبيق إجراء واحد على مستخدمين كثيرين دفعة واحدة. |
| `GET` | `/v1/users/{id}` | جلب مستخدم واحد. |
| `PATCH` | `/v1/users/{id}` | تحديث الاسم / الحدود / الانتهاء أو مدة تبدأ من أول اتصال / حد الأجهزة / حد السرعة / مفعل / `external_id` الخاص بالنظام الخارجي / `mailing` (البث والرسائل التلقائية مفعلة أو معطلة — مفتاح البوت يظهر الشيء نفسه) / `lang` (`ru` أو `en` أو `zh` أو `ar`، أو `""` لما يبلغ عنه Telegram). |
| `DELETE` | `/v1/users/{id}` | حذف مستخدم. |
| `POST` | `/v1/users/{id}/reset` | تصفير عدادات حركة المرور للمستخدم. |
| `POST` | `/v1/users/{id}/reset-period` | تعيين فترة التصفير التلقائي. |
| `POST` | `/v1/users/{id}/rotate-sub` | إصدار رابط اشتراك جديد (الرابط القديم يموت). |
| `POST` | `/v1/users/{id}/plan` | تطبيق خطة أسعار على المستخدم. |
| `POST` | `/v1/users/{id}/plan/cancel` | إلغاء اشتراك مدفوع الآن. |
| `GET` | `/v1/users/{id}/connections` | سرد عناوين IP المصدرية / الأجهزة الحديثة للمستخدم: `last_seen`، و`count` (مشاهدات، واحدة كل 45 ثانية على الأكثر)، و`approx_seconds` (حد أدنى للوقت النشط)، و`banned` (محجوب في الجدار الناري الآن). |
| `GET` | `/v1/users/{id}/devices` | سرد التثبيتات المرتبطة بـ HWID، مع الحد الذي تحتسب عليه. |
| `POST` | `/v1/users/{id}/devices/unbind` | تحرير جهاز مرتبط واحد (أو الكل)، مع إفراغ الفتحة. |
| `GET` | `/v1/users/{id}/events` | سجل المستخدم الخاص (مرقم). |
| `GET` | `/v1/users/{id}/abuse` | مطابقات قائمة الحجب للمستخدم (`limit`، الافتراضي 20). |
| `GET` | `/v1/users/{id}/happ-link` | اشتراك المستخدم كرابط `happ://crypt4/` مشفر. |

**الإنشاء** — `name` مطلوب؛ وما عدا ذلك اختياري ويطبق على الحساب الجديد في الاستدعاء نفسه:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0,
  "device_limit": 3, "speed_limit": 20000, "plan_id": 2, "group_ids": [4] }
```

**الأجهزة** هي التثبيتات المرتبطة بترويسة الاشتراك `x-hwid` (انظر *Settings → Subscriptions* في اللوحة). وتحمل القائمة الحد إلى جانب الكشف، فيجيب استدعاء واحد عن «هل هذا المستخدم ممتلئ»:

```json
{ "data": { "devices": [ { "hwid": "…", "os": "iOS", "os_version": "26.5.2",
    "model": "iPhone 15 Pro Max", "app": "Happ/1.0", "ip": "203.0.113.7",
    "first_seen": 1786500000, "last_seen": 1786568000 } ],
  "limit": 3, "enabled": true } }
```

التحرير يأخذ معرفا واحدا أو الكل، ويجيب بعدد الفتحات التي أفرغت:

```json
{ "hwid": "…" }        →  { "data": { "removed": 1 } }
{ "all": true }        →  { "data": { "removed": 3 } }
```

الجهاز الذي لم يربط قط يعيد `404`، لا نجاحا صامتا. والفتحة المفرغة متاحة فورا: يقبل الجلب التالي من تثبيت جديد.

`speed_limit` حد لعرض النطاق لكل مستخدم بوحدة **kbit/s** (0 = بلا حد)، ويطبق في الاتجاهين. وتفرضه نواة المضيف على العناوين التي يتصل منها المستخدم، لا Xray — لذا يتقاسم كل من هم خلف عنوان NAT واحد الحد نفسه، ومع Hysteria2 يظهر الحد كفقد حزم لا كتباطؤ سلس. وخطة الأسعار تحمل `speed_limit` خاصا بها وتبطش بحد المستخدم عند تطبيقها، تماما كما تفعل بحدود حركة المرور والأجهزة. ويمكن لمجموعة وصول أن تحمل `speed_limit` أيضا، وحين يحمله أحد مجموعات المستخدم، **يكون حد المجموعة هو النافذ** — فيبقى حقل المستخدم (حد خطته أو حد مضبوط يدويا) محفوظا لكنه متجاوز؛ انظر *المجموعات*.

**مدة تبدأ من أول اتصال** — بدلا من `expire_at`، أرسل `hold_seconds`: طول مدة لا تسري حتى يتصل المستخدم أول مرة. وأول اتصال تسجله اللوحة يضبط `expire_at` على تلك اللحظة زائد `hold_seconds` ويعيد `hold_seconds` إلى `0` (ويسجله السجل بوصفه `user.term_started`). والاثنان متعارضان — فالجسم الذي يحمل `expire_at` غير صفري و`hold_seconds` معا يرفض. والمدة المنتظرة للبدء 3650 يوما على الأكثر.

```json
{ "name": "gift-card-17", "hold_seconds": 2592000 }
```

في `PATCH`، يضع `hold_seconds` المستخدم في الانتظار (ويستبدل أي تاريخ)، و`0` يزيل المدة المعلقة؛ و`expire_at: 0` يعني *أبدا*، ويزيل المدة المعلقة أيضا. و`PATCH` لا يذكر أيا منهما يترك المدة على حالها تماما — بما في ذلك مدة بدأت قبل لحظة. و`extend` في `/v1/users/bulk` يمدد المدة المعلقة بعدد الأيام المعطى، وتطبيق خطة يستبدلها بمدة الخطة. ويحمل كائن المستخدم المدة المعلقة بوصفها `hold_seconds` (0 حين لا توجد).

**رابط Happ** — يجيب `GET /v1/users/{id}/happ-link` بـ `{ "data": { "link": "happ://crypt4/…" } }`: عنوان URL لاشتراك المستخدم مشفرا بالمفتاح الذي يحمله تطبيق Happ، ويضيفه Happ دون إظهار العنوان أبدا. والرابط `""` حين يكون `sub_happ_crypt` معطلا (انظر *إعداد الخادم*). وهو استدعاء منفصل لا حقلا في المستخدم: فكل رابط تشفير RSA-4096، والحشو عشوائي، فيعيد استدعاءان رابطين مختلفين للاشتراك نفسه.

`plan_id` يعيد كتابة `data_limit` و`expire_at` بقيم الخطة — فالخطة *هي* الحدود — بينما يطبق `device_limit` الصريح بعدها ويفوز. وإذا فشل أحد الإضافات، لا يتراجع عن الحساب (فقد تكون بيانات الاعتماد في يد أحدهم فعلا): يعيد الاستدعاء الخطأ ويبقى المستخدم عند ما بلغه. ويجيب `201` بالمستخدم كما انتهى عليه فعلا.

**إلغاء اشتراك** — ينقل المستخدم إلى الخطة المجانية فورا (فيضيع الوقت المدفوع المتبقي)، أو ينهي وصوله حين لا خطة مجانية مهيأة. وهو مختلف عن تطبيق الخطة المجانية يدويا: يسجل هذا بوصفه `plan.cancelled`، وهو الحدث الذي يتفاعل معه تكامل الفوترة.

**السرد** — معاملات الاستعلام: `status` (`active` / `disabled` / `expired` / `limited` / `device_limited`)، و`search` (جزء من الاسم)، و`limit`، و`offset` (`limit<=0` = الكل من `offset`). وتضيف الاستجابة كتلة `meta`:

```json
{ "data": [ ... ], "meta": { "total": 42, "offset": 0, "limit": 20 } }
```

**الإجراء الدفعي** — الجسم:

```json
{ "ids": [1, 2, 3], "action": "extend", "days": 30 }
```

`action` واحد من `enable` و`disable` و`delete` و`reset` و`extend` (`days` مطلوب لـ `extend` فقط). الاستجابة: `{ "data": { "affected": 3 } }`.

**فترة التصفير** — الجسم: `{ "period": "monthly" }` (`none` / `daily` / `weekly` / `monthly` / `yearly`).

**الإنشاء** — الجسم:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0 }
```

`data_limit` بالبايت (0 = بلا حد)؛ و`expire_at` طابع زمني Unix (0 = أبدا). و`data` في الاستجابة هو كائن المستخدم الكامل، بما في ذلك `sub_url`، وروابط المشاركة `vless` / `reality` / `hysteria2` للقنوات المدمجة، و`links` — كل قناة لدى المستخدم على هذا الخادم، بما فيها المداخل المخصصة، ولكل منها الاسم الذي سيعرضه العميل.

**التعديل الجزئي** — أرسل الحقول التي تريد تغييرها فقط:

```json
{ "name": "alice2", "data_limit": 107374182400, "expire_at": 1767225600, "device_limit": 3, "enabled": true }
```

**تطبيق خطة** — الجسم:

```json
{ "plan_id": 2, "extend_from_current": false }
```

| الطريقة | المسار | الوصف |

يمكن للخطة أن تسمي مجموعات الوصول التي تمنحها (`"group_ids": [3]`): فمن يوضع على الخطة — بطلب مدفوع، أو بـ `POST /v1/users/{id}/plan`، أو عند التسجيل — ينضم إلى تلك المجموعات ويخرج منها عند تغير الخطة. والعضويات المسندة مباشرة عبر `POST /v1/users/{id}/groups` تبقى محفوظة؛ ولا يسترد إلا ما منحته الخطة. والقائمة الفارغة تعني أن الخطة لا تقول شيئا عن الوصول.

**إنشاء طلب** — الجسم `{ "user_id": 5, "plan_id": 2 }`. تحمل الاستجابة الطلب، ومتى كان مزود دفع مهيأ تحمل أيضا `pay_url` مستضافا لإرسال المستخدم إليه:

```json
{ "data": { "order": { ... }, "pay_url": "https://..." } }
```

الطلب اليدوي — بلا `provider`، أو بـ `"manual"` — يعيد `pay_url` فارغا وينتظر `/confirm`؛ ويرفض ما دام الدفع اليدوي معطلا. والمال الذي تقبضه بنفسك — Telegram Stars في بوتك، أو صفحة دفعك — هو `"provider": "external"`، أيا كان إعداد الدفع اليدوي: `"paid": true` يؤكده في الاستدعاء نفسه، أو `/confirm` لاحقا — وإلى ذلك الحين يبقى معلقا، و`/cancel` يسقطه؛ ويحفظ `external_ref` معرف دفعتك بوصفه `provider_id`.
ويحتسب في الإيراد كأي دفعة. إنشاء الطلب **ليس** متساوي الأثر (idempotent) بالنسبة للمفتاح، لكنه لا يكدس التكرارات أيضا: الطلب الذي ما زال معلقا للمستخدم والخطة والمزود أنفسهم يعاد استخدامه بدلا من فتح طلب ثان، فيعيد الاستدعاء المعاد الطلب الموجود أصلا.

**إعدادات الفوترة** — الكائن كاملا، ويستبدل عند الكتابة (لا يوجد تحديث جزئي: «لا خطة مجانية» حالة حقيقية ويجب أن تفرق عن «غير محدد»):

```json
{ "enabled": true, "free_plan_id": 1, "trial_plan_id": 2, "payment_note": "card 1234",
  "manual": true, "manual_label": "", "wallet": true, "topup_min": 100,
  "topup_max": 15000,
  "ref_mode": "percent", "ref_percent": 10, "ref_days": 7, "ref_first": false }
```

تعيين خطة بوصفها المجانية أو التجريبية يجعلها مجانية أيضا ويعيد تطبيقها على كل من هم عليها فعلا — وهي القاعدة نفسها التي تفرضها اللوحة. و`manual` يعرض الدفع اليدوي إلى جانب المزودين، و`manual_label` تسمية زر الدفع الخاص به (فارغة = الصياغة الافتراضية)، و`payment_note` النص الذي يعرض على المستخدم الذي يدفع يدويا.

يتيح `wallet` للمستخدمين الاحتفاظ برصيد (تعبئات، والدفع للخطط منه، والتجديد منه)؛ و`topup_min` و`topup_max` أصغر تعبئة وأكبرها بالروبل (`topup_max` افتراضيا 15000، وبحد أقصى 1000000). و`ref_mode` ما يكسبه الداعي حين يدفع أحد من دعاهم مالا: `off`، أو `percent` (نسبة `ref_percent` % من الدفعة، شاملة التعبئات، إلى رصيد الداعي — تحتاج `wallet`)، أو `days` (`ref_days` يوما على خطته، لخطة اشتريت بمال)؛ و`ref_first` يدفع فقط عن أول دفعة كهذه. وعند تركها، يحتفظ `wallet` و`topup_min` و`topup_max` و`ref_mode` و`ref_percent` و`ref_days` و`ref_first` بقيمها المحفوظة.

**الطلبات والرصيد** — `amount_rub` في الطلب هو المال الواجب دفعه دائما. وحين يغطي رصيد المستخدم جزءا من السعر، يكون `balance_kop` ذلك الجزء (بالكوبيك)، و`amount_rub` الباقي؛ وتأكيد الطلب يضع المال على الرصيد ويخصم السعر كاملا منه مع الخطة. و`kind` هو `plan` أو `topup` (وللتعبئة `plan_id` 0). والخطة المشتراة من الرصيد وحده تظهر طلبا مدفوعا بـ `provider` يساوي `balance` و`amount_rub` 0 — وهي ليست إيرادا. ويظهر `discount_rub` و`promo_code` رمز خصم. وحين يغطي الرصيد السعر كاملا، يجيب `POST /v1/billing/orders` بـ `err.payFromBalance`؛ فأرسل `"from_balance": true` بدلا من ذلك لشراء الخطة من الرصيد. والمال الذي يصل لطلب ملغى سلفا (استبدله دفع أحدث بالرمز الترويجي نفسه، أو كنس مهملا، أو ألغي يدويا) يحتسب كأي دفعة أخرى — ويقبل `POST /v1/billing/orders/{id}/confirm` طلبا ملغى أيضا: فتحصل على الخطة، أو، مع تشغيل المحفظة، يذهب المال إلى الرصيد حين لا يمكن منح الخطة بعد الآن (خطة أخرى اشتريت في الأثناء، خطة مدى الحياة محفوظة سلفا) ويصير الطلب `topup`. ولا يجوز للمستخدم أن يكون لديه أكثر من 3 تعبئات غير مدفوعة مفتوحة خلال الساعة الأخيرة.

**رموز الخصم** — `kind` هو `percent` / `amount` (خصم على دفعة المستخدم التالية، و`value` نسبة أو روبل؛ و`plan_ids` يحصره في تلك الخطط، و`first_only` فيمن لم يشتر خطة قط)، أو `days` (`value` يوما على `plan_id`، أو على خطة المستخدم المدفوعة النشطة حين يكون `plan_id` 0) أو `balance` (`value` روبل على الرصيد). و`max_uses` 0 بلا حد، و`expires_at` 0 أبدا؛ ولكل مستخدم أن يستخدم رمزا مرة واحدة. والأرقام غير حساسة لحالة الأحرف.

**عدة مدد** — `"periods": 3` في `POST /v1/billing/orders` يشتري ثلاث مدد من الخطة دفعة واحدة، بالخصم الذي تسميه `periods` في إعدادات الفوترة (`[{"periods": 3, "percent": 10}]`)؛ والعدد الذي لا عرض له يرفض. وتكون المدة بهذا العدد من المدد، والحصة التي لا تعيد الخطة ملأها في دورتها تملأ من جديد كل مدة.

**الاسترداد** — `POST /v1/billing/orders/{id}/refund` مع `{ "cancel_plan": false }` يعيد سعر الطلب (المال وجزء الرصيد) إلى رصيد المستخدم، مرة واحدة؛ و`cancel_plan` يخصم أيضا الأيام التي دفع الطلب ثمنها من المدة (وتنتهي الخطة فقط حين لا يبقى منها شيء). يحتاج تشغيل المحفظة. والاسترداد أو رد الدفع (chargeback) الذي يبلغ عنه نظام الدفع يعلم الطلب بـ `refund_source: "provider"` من تلقاء نفسه: فيخرج من الإيراد، ويسترد ما اشتراه، ولا يمكن استرداده إلى الرصيد بعد ذلك.

**استعادة المتسربين** — `"winback": {"enabled": true, "after_days": 7, "percent": 20, "valid_days": 7}` في إعدادات الفوترة: بعد ذلك العدد من الأيام من انقضاء مدة مدفوعة، يحصل المستخدم على رمز أحادي الاستخدام بذلك الخصم، مرتبط بدفعته التالية ومرسل في البوت.

**استبيان المغادرة** — `"churn_survey": true` في إعدادات الفوترة: بعد يوم من انقضاء مدة مدفوعة يسأل بوت المستخدم عن سبب عدم التجديد، وتسأل صفحة الاشتراك الشيء نفسه ما دام متسربا. والأسباب: `price` و`quality` و`not_needed` و`competitor` و`other` (مع تعليق). وإجابة واحدة لكل تسرب. ولوحة تحكم من عندك تسألها أيضا: يحمل `GET /v1/users/{id}/subscription` الحقل `churn` ما دام هناك ما يسأل عنه، ويأخذ `POST /v1/users/{id}/churn` الإجابة (`source` يساوي `api`؛ والإجابة اللاحقة تستبدل السبب). ويحمل `GET /v1/billing/funnel` الإجابات تحت `churn`:
`{"total": 12, "reasons": {"price": 5, ...}, "comments": [{"user_id": 7, "user_name": "...",
"reason": "other", "comment": "...", "source": "bot", "created_at": ...}]}`.

**الرصيد** — يأخذ `POST /v1/users/{id}/balance` الجسم `{ "amount_kop": 10000, "note": "..." }` (بأي إشارة؛ ولا يمكن أن ينزل الرصيد تحت الصفر) ويجيب بـ `{ "balance_kop": ... }`. ويجيب `GET /v1/users/{id}/wallet` بـ `{ "wallet": {...}, "history": [...], "ref_link": "..." }` — و`ref_link` رابط دعوة المستخدم، ما دام برنامج الإحالة وبوت المستخدم مفعلين.

**البيع من بوتك** — يسرد `GET /v1/users/{id}/quotes` ما يمكن للمستخدم شراؤه الآن (خطته الحالية فقط ما دامت المدفوعة سارية) مع قيمة لكل مدة: `total_rub` بعد رمز خصمه، و`balance_kop` الذي يغطيه الرصيد، و`money_rub` المتبقي للدفع. ثم `POST /v1/billing/orders` مع `from_balance` حين يكون `money_rub` صفرا (أضف `expect_expire_at` — وهو `expire_at` الذي عرضته — كي لا يشتري طلب معاد مدة ثانية)، أو مع `provider` للباقي. والتعبئة هي `{"user_id": 5, "kind": "topup", "amount_rub": 300}` (مع `provider`، أو بلا شيء لدفعة يدوية). ويأخذ كلاهما `lang` (`ru`/`en`/`zh`/`ar`، لتعليمات الدفع اليدوي) و`return_url` (حيث تعيد الدفعة المستضافة الدافع؛ ورابط اشتراك المستخدم عند حذفه — صفحتك أنت، حين تهيأ واحدة).

**بوتك أو لوحة تحكم المستخدمين** — يبقى المفتاح على خادمك، ولا يدخل متصفحا أبدا. أشر الطرق التي يستدعيها: إنشاء المستخدمين وربط Telegram، وفتح الطلبات، ورموز الخصم، والداعين، والتجديد — واترك خارجها تأكيد الطلب وتصحيح الرصيد والاستردادات، فهي تنقل مالا دون أن يصل. وفي كل رسالة اعثر على المستخدم: `GET /v1/users?telegram_id=<id>` (بحث مفهرس؛ والقائمة الفارغة تعني قادما جديدا). والقادم الجديد هو `POST /v1/users` مع `plan_id` (الخطة التجريبية أو المجانية — فالمستخدم بلا خطة لا يحصل على كتلة دفع)، ثم `POST /v1/users/{id}/telegram` مع `{"chat_id": <id>}`، وحين حمل `/start` الخاص به رمز دعوة، `POST /v1/users/{id}/referrer` مع `{"ref_code": "r_…"}` (بـ `r_` أو بدونها) — مرة واحدة، قبل أول دفعة له. ورمز دعوة المستخدم نفسه هو `ref_code` في `GET /v1/users/{id}/wallet` (و`ref_link` أيضا، ما دام بوت المستخدم في اللوحة مفعلا). ولوحة التحكم التي تدخل الناس برابط اشتراكهم تجدهم بـ `?sub_token=`.
وفي `GET /v1/users/{id}/subscription` كل ما تعرضه صفحة الاشتراك — الحالة، و`blocks` (ما تضيفه الإضافات إلى الصفحة: `{type: text|markdown|notice|button, text, label, url}`)، وحركة المرور، والمدة، و`sub_url`، واستيراد بنقرة واحدة لكل تطبيق (`apps`)، وكل إعداد (`links`)، وتنزيل Clash (`clash_url`)، وإعدادات WireGuard العادية (`wg`: `{name, conf_url, qr_url}`، و`awg` كذلك)، ووكيل Telegram لكل خادم (`telegram`: `{name, link, web_link, qr_url}` — و`link` هو `tg://proxy` الذي يضيفه بنقرة واحدة)، والأجهزة، وكتلة الدفع (`billing`)، وألوان المشغل (`brand`)، و`terms_url` / `privacy_url` (وثائق المشغل، ما دام لها نص — و`GET /v1/legal` يحمل النص نفسه)، و`tg_link` — رابط بوت المستخدم الذي يربط الحساب بـ Telegram الذي فتح فيه (وينقله إليه حين `tg_linked`؛ وغائب ما دامت مفاتيح Settings → Telegram لا تعرض شيئا، وصالح 15 دقيقة) — مصاغا بـ `?lang`؛ والإجراءات تمر عبر نقاط النهاية أعلاه. ويحتفظ بإعدادات الاشتراك التي تحتفظ بها الصفحة: `links` فارغ ما دامت الصفحة لن تسرد أي إعداد (`show_configs` معطل، أو HWID مطلوب — فالرابط الخام سيتجاوز حد الأجهزة)، و`clash_url` غائب ما دام زر Clash في الصفحة معطلا أو تحت HWID مطلوب، وزر Happ هو الرابط المشفر حين يكون ذلك مفعلا، و`maintenance` هو وضع الصيانة في اللوحة. و`churn` هو استبيان المغادرة الذي يطرح — `{question, reasons: [{key, label}]}`، مصاغا بـ `?lang` — ولا يحضر إلا ما دامت مدة المستخدم المدفوعة قد انقضت ولم يجب؛ فأرسل `key` المختار إلى `POST /v1/users/{id}/churn`.

**الوثائق القانونية** — يعيد `GET /v1/legal` (بأي مفتاح) اتفاقية المستخدم وسياسة الخصوصية للمشغل، المكتوبتين في *Settings → Branding → Documents*: `{"terms": {...}, "privacy": {...}}`، ولكل منهما `markdown`، و`html` (بصيغة HTML جاهزة؛ وHTML الخام في المصدر يسقط)، و`url` (صفحته العامة، "" ما دامت الوثيقة فارغة)، و`updated_at` (0 = لم تضبط قط). اعرضهما على صفحاتك، أو اربط `url`.

**التسجيل من نظام خارجي** — يسجل `POST /v1/signup` مع `{"external_id": "ann@example.com"}` عميلا بمعرف النظام الخارجي نفسه وفق القواعد التي يلتزمها بوت المستخدم: التسجيل المغلق يرفض (`err.signupClosed`)، ووضع الدعوة يريد `invite` (`err.signupBadInvite`)، والإشراف يسجل طلبا، ويحصل الحساب على الخطة التجريبية أو المجانية كتسجيل البوت. وحساب واحد لكل `external_id` — يقارن حرفيا، فاجعل البريد الإلكتروني بأحرف صغيرة أولا — لذا يعيد التسجيل مرة أخرى الحساب نفسه (`200`، و`"status": "existing"`، و`user_id` خاصته؛ والحساب كاملا فقط لمفتاح يملك `users.view`) بدلا من تجربة ثانية. ويجب أن يمرر النظام الخارجي معرفا تحقق منه هو فقط (بريد مؤكد): فمن يمرره يحصل على ذلك الحساب. والحساب الجديد يجيب `201 "created"` مع الحساب، والطلب `202 "pending"` مع `request_id` (والسؤال مرة أخرى وهو منتظر لا يسجل شيئا). واختياريا: `name` (المعرف الخارجي عند حذفه)، و`source` (وسم القمع)، و`ref` (رمز دعوة؛ والمجهول يتجاهل)، و`lang` (`ru` أو `en` أو `zh` أو `ar`، يمنح للحساب — فورا، أو عند موافقة المشغل)، و`ip` — عنوان العميل، لحد تسجيل واحد في الدقيقة لكل عنوان (ولكل /64 في IPv6) ولكل معرف، و20 في الدقيقة إجمالا؛ وفوق ذلك تكون الإجابة `429` مع `Retry-After`. أشر مفتاح النظام الخارجي على `POST /v1/signup` (مع ما يعرضه ويبيعه) لا على `POST /v1/users`: فلا يستطيع عندئذ إنشاء مستخدم بشروطه. ويحمل `user.registered` و`registration.rejected` الحقل `external_id`، ويجد `GET /v1/users?external_id=` الحساب مرة أخرى.

**التسجيل من بوتك** — `POST /v1/signup` مع `{"telegram_id": 123456789}` بدلا من `external_id` (أحدهما أو الآخر) يسجل مستخدم Telegram وفق القواعد التي تلتزمها اللوحة لـ Telegram: يعود حسابه (`"existing"`)، ويستعاد حساب فك ربطه، وترفضه قائمة الحجب المشتركة (`err.signupBlacklisted`)، وتجربة واحدة لكل Telegram إلى الأبد — فالحساب المحذوف لا يكسب ثانية — ويربط Telegram بالحساب الجديد. ويعمل `name` و`source` و`ref` و`invite` و`ip` كما أعلاه — تسجيل واحد في الدقيقة لكل Telegram، و20 في الدقيقة إجمالا مشتركة مع تسجيلات `external_id`؛ وتحت الإشراف يكون الطلب لصاحب Telegram، وموافقته تربطه. **مرر فقط معرف Telegram أعطاكه Telegram** — مرسل رسالة إلى بوتك، أو `initData` في Mini App تحققت منه — لا معرفا كتبه عميل أبدا: فمن يمرر معرفا يسجل ذلك Telegram، وينفق تجربته الواحدة، ويمسك الحساب المرتبط به.

والعميل الذي جاء من البوت أو من Mini App لديه حساب سلفا: اربط تسجيل الدخول في النظام الخارجي به عبر `PATCH /v1/users/{id}` `{"external_id": "ann@example.com"}` بدلا من تسجيله من جديد — من صفحة وصل إليها برابط اشتراكه (`?sub_token=` يجد الحساب)، فيكون المعرف له. والمعرف الذي يملكه حساب آخر يرفض (`err.externalIDTaken`)؛ و`""` يزيله.

**الترحيل** — الجسم `{ "to_plan_id": 3 }`، والاستجابة `{ "data": { "migrated": 12 } }`. يطبق حدود الخطة الهدف ومدتها ومجموعات وصولها على كل مستخدم في الخطة المصدر. وهذا هو السبيل الوحيد لإفراغ خطة قبل حذفها.

**المزودون** — يعيد `GET /v1/payments` كل مزود في السجل مع استمارة إعداداته: الحقول التي يأخذها، وقيمها الحالية، وأي الأسرار مضبوطة (لا قيمها أبدا)، و`webhook_url` الذي تلصقه في لوحة المزود. وقائمة الحقول خاصة بكل مزود ومولدة من السجل، لذا هذه الحمولة حرة الشكل عن قصد. ويأخذ `POST /v1/payments` الجسم `{ "key": "yookassa", "enabled": true, "config":
{...} }`؛ والسر المتروك فارغا يحتفظ بقيمته المحفوظة.

`GET /v1/billing/providers` ديناميكي — يعيد أي طرق دفع فعلتها في اللوحة (بطاقات، SBP، عملات مشفرة، …)، لكل منها `key`، و`manual` أولا حين يكون الدفع اليدوي مفعلا. وذلك الـ `key` هو ما تمرره `provider` عند فتح طلب.

### العقد (Nodes)

إدارة أسطول الخوادم. خادم اللوحة المحلي هو العقدة `0`؛ والباقي **عقد** بعيدة تحمل استقصاء طويلا (long-poll) صادرا نحو اللوحة. وتتزامن المستخدمون والحدود إلى كل عقدة مفعلة تلقائيا، ويمكن تعديل كل خادم على حدة.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/nodes` | سرد الخوادم (اللوحة المحلية هي العقدة `0`) مع الحالة وحركة مرور اليوم. |
| `POST` | `/v1/nodes` | تسجيل عقدة — يعيد أمر التثبيت بسطر واحد (ورمز الانضمام يعرض مرة واحدة). |
| `GET` | `/v1/nodes/{id}` | جلب عقدة واحدة. |
| `PATCH` | `/v1/nodes/{id}` | تعديل الاسم / المضيف / البروتوكول / التوجيه / تجاوزات DNS وخروج WARP-Opera. |
| `DELETE` | `/v1/nodes/{id}` | حذف عقدة (فتتوقف عن خدمة المستخدمين). |
| `POST` | `/v1/nodes/{id}/enabled` | تمكين عقدة أو تعطيلها. |
| `POST` | `/v1/nodes/{id}/regen-join` | إصدار أمر تثبيت جديد (يلغي رمز العقدة الحالي). |
| `POST` | `/v1/nodes/{id}/update` | طلب تحديث ذاتي للعقدة إلى أحدث إصدار. |
| `POST` | `/v1/nodes/update-all` | طلب التحديث الذاتي من كل عقدة متصلة (بالتتابع). |
| `POST` | `/v1/nodes/{id}/proxy` | تهيئة وكيل النظام لذلك الخادم (`id` 0 = الرئيسي). |
| `POST` | `/v1/nodes/{id}/placement` | تعديل موضع ذلك الخادم وحد حركة المرور فيه (`id` 0 = الرئيسي). |
| `GET` | `/v1/nodes/{id}/health` | التشخيصات الذاتية لخادم واحد. |

| `GET` | `/v1/reach` | البلدان، والفحوص لكل بلد، وفترة المراقبة وحد ذلك الفحص. |
| `POST` | `/v1/reach` | ضبطها؛ و`token` (Globalping) المحذوف يحتفظ بالمحفوظ، و`""` يمسحه. |
| `GET` | `/v1/alerts` | قواعد التنبيه؛ و`firing` يحصي التنبيهات المفتوحة الآن. |
| `GET` | `/v1/alerts/metrics` | المقاييس التي يمكن لقاعدة أن تراقبها، مع وحداتها. |
| `GET` | `/v1/alerts/events` | تاريخ الإطلاق، الأحدث أولا (`limit`، و`before` = معرف للمتابعة تحته)؛ و`resolved_at` 0 = ما زال مطلقا. |

| `POST` | `/v1/alerts/{id}` | استبدال إعدادات قاعدة. |
| `DELETE` | `/v1/alerts/{id}` | حذف قاعدة؛ ويبقى تاريخها. |
| `GET` | `/v1/nodes/{id}/logs` | أحدث أسطر سجل الخادم (0 هو الخادم الرئيسي). |
| `GET` | `/v1/logs` | أحدث أسطر سجل اللوحة نفسها. |

**تسجيل عقدة** — الجسم `{ "name": "NL #1", "host": "nl1.example.com" }`. تحمل الاستجابة معرف العقدة، ورمز الانضمام الأحادي، وأمر التثبيت الجاهز على خادم Ubuntu جديد:

```json
{
  "data": {
    "id": 3,
    "join_token": "rpn_…",
    "install_command": "curl -Ls https://.../install.sh | sudo bash -s -- --join '…#rpn_…'"
  }
}
```

يضمن رمز الانضمام مرة واحدة وينتهي خلال 24 ساعة؛ و`/regen-join` يصدر جديدا.

**الموضع** — أين يقع الخادم في الاشتراكات، وكم من حركة المرور يجوز أن يحمل. وهو تعديل جزئي: لا تتغير إلا الحقول المرسلة. وتقبل `PATCH /v1/nodes/{id}` الحقول نفسها؛ وهذا المسار يبلغ الرئيسي أيضا (`id` 0)، الذي لا صف عقدة له. والجواب هو الموضع كما هو محفوظ.

```json
{ "country": "NL", "sort_weight": 10, "capacity": 300, "hide_when_full": true,
  "traffic_limit": 1099511627776, "traffic_period": "month", "traffic_reset_day": 14,
  "hide_when_over": false }
```

`traffic_limit` بالبايت لكل `traffic_period` (`month` أو `day`؛ 0 = بلا حد). و`traffic_reset_day` (1–31) هو اليوم الذي يبدأ فيه الحد الشهري من جديد، ليوافق اليوم الذي تحاسب منه الاستضافة؛ والشهر الخالي من ذلك اليوم يبدأ في آخر يوم له، ويحفظ `1` بوصفه القيمة الافتراضية `0`. ومسح الحد يمسح معه مدته ويوم إعادته و`hide_when_over`.

**وكيل النظام** — مستمع SOCKS5 و/أو HTTP يعيد التوجيه على ذلك الخادم، لحركة ليست من عميل VPN: كاشط، أو بوت، أو لوحة أخرى تسلسل خروجها إلى هنا. ولا يفتحه اعتماد مستخدم، ولا تحكمه مجموعة وصول، ولا يظهر في اشتراك أبدا. وتخرج الحركة تحت توجيه ذلك الخادم، فينطبق WARP وOpera وقنوات الوكيل تماما كما تنطبق على عملاء VPN.

```json
{ "socks_enabled": true, "socks_port": 1080,
  "http_enabled": true,  "http_port": 3128,
  "accounts": [ { "user": "scraper", "pass": "…" },
                { "user": "bot",     "pass": "…" } ] }
```

`accounts` القائمة الكاملة في كل مرة — وسبيل حذف أحدها هو إرسال القائمة دونه. ويجب أن تكون أسماء الدخول فريدة وخالية من النقطتين الرأسيتين والمسافة (فالنقطتان الفاصل في `user:pass`)، ويلزم حساب كامل واحد على الأقل متى كان أحد المستمعين مفعلا: فالوكيل المفتوح على منفذ عام يعثر عليه الماسحون خلال ساعات، ويصير حينئذ مرحل بريد مزعج لغيرك بعنوان IP هذا الخادم. والبروتوكول المفعل بلا منفذ يحصل على 1080 (SOCKS) / 3128 (HTTP). ولكل خادم حساباته ومنافذه **الخاصة** — فالعقدة لا ترث من الرئيسي أبدا، لذا فسر دخول مسرب يفتح جهازا واحدا. والاستجابة هي التهيئة المحفوظة، فيعرف المستدعي الذي أرسل `{"socks_enabled": true}` فقط أي منفذ نال.

### المداخل المخصصة

مداخل يعرفها المشغل عدا القنوات المدمجة الثلاث، ومجموعة واحدة لكل خادم (الخادم `0` = الرئيسي). وكل منها مستمع عام، لذا يتحقق من الإنشاء/التحديث **على الجهاز الهدف** (`xray -test` + فحص ربط المنفذ) قبل حفظه.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/servers/{id}/inbounds` | سرد المداخل المخصصة لخادم واحد (`id` = معرف الخادم، و`0` = الرئيسي). |
| `POST` | `/v1/servers/{id}/inbounds` | إنشاء مدخل مخصص على ذلك الخادم. |
| `POST` | `/v1/inbounds/{id}` | تحديث مدخل مخصص (بمفتاح معرف المدخل نفسه). |
| `DELETE` | `/v1/inbounds/{id}` | حذف مدخل مخصص. |

**الإنشاء / التحديث** — يحاكي الجسم محرر المداخل في اللوحة: `name`، و`protocol` (`vless` / `trojan` / `hysteria2` / `shadowsocks` / `turn-vk` / `wg`)، و`transport` (`tcp` / `ws` / `xhttp` / `grpc` / `httpupgrade`)، و`port`، و`security` (`none` / `tls` / `reality`) مع المفاتيح المطابقة (وجهة REALITY ومفاتيحها، والبصمة، وpath/host، ونطاق hop في Hysteria2)، إضافة إلى كتل متقدمة اختيارية (`extra` في XHTTP، وتمويه HTTP على TCP، و`sockopt`، ومفاتيح TLS إضافية). وقائمة الحقول الكاملة — وأي التركيبات صالحة — في `openapi.json` / Swagger.
`shadowsocks` هو Shadowsocks-2022 (`method` يختار AEAD؛ ومفتاح الخادم مولد، ومفتاح كل مستخدم مشتق من UUID) — متعدد المستخدمين، فتعمل إحصاءات كل مستخدم وحصصه، لكن العملاء الحديثين فقط (sing-box، mihomo، v2rayN، Shadowrocket، Streisand) يتكلمونه.
`turn-vk` (سابقا `wireguard`، ولا يزال مقبولا في الإدخال) هو WireGuard خلف مرحل TURN: `port` منفذ UDP العام الذي يستمع عليه المرحل، و`turn_link` رابط مكالمة VK اختياري (`https://vk.com/call/join/…`) يمنح لتطبيقات المستخدمين؛ ومفتاح الخادم، ومنفذ الاسترجاع الذي يستمع عليه Xray (`wg_public_key`، و`wg_local_port` في الاستجابة)، ومفتاح تمويه Free Turn Proxy (لا يعاد أبدا) مولدة. وهو ليس في أي صيغة اشتراك — يستورده المستخدمون في تطبيق من صفحة الاشتراك (`vkturnproxy://`، و`freeturn://`، و`wingsv://`) أو ينزلون `<sub>/wg/<inbound id>.conf` من صفحة الاشتراك.
`wg` هو WireGuard العادي: مدخل WireGuard الخاص بـ Xray على `port` العام UDP، يبلغه أي عميل WireGuard قياسي مباشرة. ومفتاح الخادم مولد (`wg_public_key` في الاستجابة)؛ والنقل والأمان ثابتان، و`turn_link` لا ينطبق. والمستخدمون أقران بهوية النفق التي لديهم لـ AmneziaWG. وهو ليس في أي صيغة اشتراك أيضا — ينزل المستخدمون `<sub>/wg/<inbound id>.conf` (أو `.png`، النص نفسه كرمز QR) من صفحة الاشتراك.
`enc_mode` يشغل VLESS Encryption على مدخل `vless` — `native` أو `xorpub` أو `random` (شكل المصافحة على السلك)، وفارغ للإيقاف؛ والمفاتيح مولدة (`encryption`، نصف العملاء، في الاستجابة). ومعه يجوز أن يسير `tcp` مع `security: none`.
`cdn_host` (و`cdn_port`، و443 حين 0) يضع مدخل `vless` / `trojan` على `ws` / `httpupgrade` / `xhttp` خلف CDN: فتشير الروابط إلى ذلك النطاق عبر TLS، ويبلغ CDN منفذ المدخل نفسه (عاديا مع `security: none`)، ويثق المدخل بـ X-Forwarded-For الخاص به.
`pin_cert` (TLS، وليس خلف CDN) يجعل العملاء يتحققون من شهادة الخادم ببصمتها لا باسمها، فيجوز أن يكون `sni` أي نطاق — نطاقا في قائمة سماح المشغل، مثلا.
وصيغتان لا يستطيع المخطط أن يسميهما إلا `string`: `reality_dest` اسم مضيف مجرد (`www.microsoft.com` — وصيغة `host:port` ترفض)، و`hop_interval` نطاق بالثواني (`"5-10"`، لا `"30"`).
و`data` في الاستجابة هو المدخل المحفوظ؛ والتهيئة المرفوضة (منفذ مربوط سلفا، تركيبة غير صالحة، عقدة غير متصلة) تعيد `400` مع السبب. والمداخل التي لا يستطيع عميل تمثيلها تسقط بصمت من اشتراكات Clash/sing-box بدلا من إصدارها معطوبة.

يمكن لمجموعة وصول أن تعنون مدخلا برمز المنح `inbound:<id>` (انظر **المجموعات**).

ينشر `GET /v1/inbounds/catalog` ما يمكن جمعه مع ما — كل بروتوكول × نقل، وأوضاع `security` التي يسمح بها كل منها، وأي صيغ الاشتراك لا تستطيع حمله، وقيم التعداد التي تقبلها الحقول المتقدمة. وهو الجدول نفسه الذي يستخدمه محرر اللوحة، فلا يستطيع عميل يبني المداخل منه إنشاء مدخل يرفضه المتحقق.

### المجموعات

تحكم مجموعات الوصول أي الاتصالات يجوز للمستخدم استخدامها. والمستخدم في **لا** مجموعة يبلغ كل شيء؛ والمستخدم في مجموعة أو أكثر يبلغ **اتحاد** منح مجموعاته. ولا تشارك إلا المجموعات التي **تحد الوصول** (`limits_access` أدناه): فالمستخدم الذي تترك مجموعاته كلها الوصول مفتوحا يبلغ كل شيء أيضا. والإنفاذ **على الخادم** — فاعتماد قناة غير مسموح بها لا يصل إلى Xray، ولا يكتفى بإخفائه — لذا لا يعرض `links` في كائن المستخدم، ولا الاشتراك، ولا رابط مبني يدويا، إلا ما منح.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/groups` | سرد المجموعات، ولكل منها `grants` و`member_ids` وعدد الأعضاء. |
| `POST` | `/v1/groups` | إنشاء مجموعة. |
| `POST` | `/v1/groups/{id}` | تحديث مجموعة (الاسم، والمنح، وحد السرعة). |
| `DELETE` | `/v1/groups/{id}` | حذف مجموعة (والأعضاء المتروكون في لا مجموعة تحد الوصول يعودون إلى غير المقيد). |
| `POST` | `/v1/groups/{id}/members` | استبدال أعضاء المجموعة. |
| `POST` | `/v1/users/{id}/groups` | استبدال عضوية مستخدم واحد. |

**الإنشاء / التحديث** — الجسم:

```json
{ "name": "VIP", "grants": ["builtin:0:vless", "builtin:0:reality", "inbound:7"],
  "speed_limit": 20000 }
```

يحد `speed_limit` سرعة الأعضاء بوحدة **kbit/s** (0 = لا تضع المجموعة حدا). وحين يضبط فإنه **يتقدم** على الحد الذي تمنحه تعرفة العضو أو بطاقته؛ وعضو مجموعات متعددة محدودة يحصل على **أعلاها**. ولا يرخي خنق قائمة الحجب به أبدا — فيطبق الأشد من الاثنين. وإذا حذف في التحديث، يحفظ الحد.

**رمز المنح** يسمي اتصالا واحدا:

- `builtin:<server_id>:<lane>` — قناة مدمجة، حيث `<lane>` هي `vless` أو `xhttp` أو `reality`
  أو `hysteria2` أو `naive` أو `trusttunnel` أو `anytls` أو `mieru` أو `awg` أو `mtproto`، و`<server_id>` هي `0` للرئيسي أو معرف عقدة
  من `GET /v1/nodes`.
- `inbound:<id>` — مدخل مخصص، بمعرف المدخل نفسه من `GET /v1/servers/{id}/inbounds`.

مصفوفة `grants` الفارغة تعني أن المجموعة **لا تحد الوصول**: فمحفوظة على هذا النحو تكون طبقة لحد سرعتها وحده، ويحتفظ أعضاؤها بكل اتصال. وتحمل الاستجابة ذلك بوصفه `limits_access` — يحسم عند حفظ المجموعة، لا يقرأ من قائمة المنح. وتكنس المنح تلقائيا أيضا حين يحذف المدخل أو العقدة أو الخادم الخارجي الذي تسميه، والمجموعة التي تفقد آخر منحها بهذه الطريقة تبقى `limits_access: true`: فيبلغ أعضاؤها لا شيء بدلا من كل شيء فجأة. احفظها من جديد بلا منح لتفتحها. والمجموعات التي وجدت قبل هذا السلوك تظل تحد الوصول حتى تحفظ من جديد. و`data` في الاستجابة هي المجموعة.

**تحديد الأعضاء** — الجسم `{ "user_ids": [1, 2, 3] }`؛ يستبدل الأعضاء جميعا.

**تحديد مجموعات مستخدم** — الجسم `{ "group_ids": [4, 5] }`؛ يستبدل عضوية المستخدم كاملة. والمصفوفة الفارغة تزيل المستخدم من كل مجموعة (→ غير مقيد).

المنح التي تشير إلى مدخل أو عقدة محذوفة تكنس تلقائيا، وهي غير ضارة إلى ذلك الحين.

**من أين تأتي الرموز** — يسرد `GET /v1/groups/targets` كل خادم مع الاتصالات التي يمكن لمجموعة منحها، ولكل منها رمزه الجاهز:

```json
{ "data": [
  { "server_id": 0, "server_name": "Мастер",
    "lanes": [ { "lane": "vless", "label": "VLESS-TCP-TLS",
                 "token": "builtin:0:vless", "enabled": true } ],
    "inbounds": [ { "id": 7, "name": "WS резерв",
                    "token": "inbound:7", "enabled": true } ] }
] }
```

القنوات والمداخل المعطلة مشمولة، فيمكن تجهيز منح قبل تشغيل الاتصال. وتجميع تلك الرموز يدويا يعمل أيضا — لكن الخطأ المطبعي لا يمنح شيئا، بصمت، وهذا بالضبط ما تمنعه نقطة النهاية هذه.

### إعداد الخادم

نقاط النهاية أعلاه تشغل لوحة؛ وهذه تهيئ واحدة. وكل ما هنا يحاكي شاشة في اللوحة ويستدعي الشيفرة نفسها خلفها، فالقيمة التي ترفضها الواجهة ترفض هنا أيضا.

وثمة أمران غائبان عن قصد. **المسؤولون ومفاتيح API** بلا نقاط نهاية: فمفتاح قادر على سك المفاتيح يحول تسريبا واحدا إلى وصول دائم متجدد ذاتيا، وذلك القرار موضعه خلف جلسة تطالب بكلمة مرور. و**مسار اللوحة السري** لا يعيده أي مسار `/v1` — فهو طبقة التعتيم أمام اللوحة، لا إعدادا يقرأ.

```
GET   $BASE/v1/settings                        → the operational knobs
PATCH $BASE/v1/settings                        → change some of them
GET   $BASE/v1/servers/{id}/routing            → routing, DNS and egress backends
POST  $BASE/v1/servers/{id}/routing            → change them
POST  $BASE/v1/servers/{id}/xray-restart       → restart that server's Xray
GET   $BASE/v1/config/snapshots                → config save-points
POST  $BASE/v1/config/snapshots                → take one
POST  $BASE/v1/config/snapshots/{id}/rollback  → restore the server config from one
DELETE $BASE/v1/config/snapshots/{id}          → forget one
```

يطبق `PATCH /v1/settings` **الحقول التي يحملها الجسم فقط**. وكل غائب يترك على حاله، وهذا ما يجعله آمنا: تقرأ الكائن، وتغير قيمة واحدة، وترسل تلك القيمة وحدها — فإعادة إرسال الشيء كله ستطبق من جديد أيضا أي تغيير أجراه مشغل آخر في الأثناء. والحقول المجمعة (`hwid_*`، و`local_backup_*`) تحفظ بكتابة واحدة داخليا، فتنطبق على الصف الحالي بدلا من تصفير أشقائها.

```bash
curl -X PATCH $BASE/v1/settings -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"maintenance_mode":true}'
```

```json
{ "data": {
  "xray_dns": "https://dns.example/dns-query\n1.1.1.1",
  "decoy_template": "coming-soon",
  "decoy_templates": ["coming-soon", "YouTube", "…"],
  "maintenance_mode": true,
  "probe_detect": true, "probe_block": false,
  "watchdog_enabled": true, "watchdog_restarts": 0,
  "user_autodelete_days": 0,
  "hwid_enabled": false, "hwid_require": true,
  "hwid_fallback_limit": 0, "hwid_ttl_days": 30,
  "device_count_mode": "auto",
  "local_backup_cron": "", "local_backup_keep": 7,
  "sub_path": "sub", "warp_enabled": false, "warp_registered": true,
  "sub_order_mode": "manual", "sub_happ_crypt": false, "sub_page_url": "",
  "trusted_nets": ["198.51.100.0/24", "203.0.113.10/32"]
} }
```

`sub_order_mode` هو كيفية ترتيب الاشتراك للخوادم: `manual` (الوزن، ثم القائمة)، أو `nearest`، أو `load`، أو `nearest_load`، أو `random` — ترتيب جديد في كل جلب، فيتوزع العملاء الذين يتصلون بالمدخل الأول على الأسطول؛ ويسري الإخفاء عند الامتلاء والإخفاء عند التجاوز معا. و`sub_happ_crypt` يجعل زر Happ في صفحة الاشتراك، و`GET /v1/users/{id}/happ-link`، يسلمان رابط `happ://crypt4/` مشفرا بدلا من العنوان العادي. و`sub_page_url` صفحة اشتراكك أنت: فالمتصفح الذي يفتح رابط اشتراك يعاد توجيهه إليها (`302`)، و`{token}` مستبدل برمز المستخدم — مثل `https://example.com/cabinet?sub={token}`، ثم يجد `GET /v1/users?sub_token=` المستخدم. والتطبيقات التي تجلب الاشتراك، وتنزيلات `?format=`، لا تعاد توجيهها؛ و`""` يعيد صفحة اللوحة. والرابط إلى مسار اشتراك هذه اللوحة نفسها يرفض (`err.subPageLoop`) ولا يتبع تحت أي اسم يبلغ به اللوحة؛ والرمز المجهول لا يعاد توجيهه أبدا؛ وزر «افتح صفحة الاشتراك» في بطاقة المستخدم يفتح صفحة اللوحة نفسها عبر رابط موقع صالح ساعة. و`trusted_nets` هي عناوين IP والشبكات التي لا تحجبها اللوحة من تلقاء نفسها — لا لتخمين كلمة مرور SOCKS/HTTP، ولا لمسح اللوحة، ولا تحت سياسة المصدر (فالرفض يظل مسجلا في السجل). وإرسالها يستبدل القائمة كاملة؛ وتحفظ المدخلات كبادئات (`198.51.100.7/24` تصبح `198.51.100.0/24`)، وترفض الشبكات الأوسع من /8 في IPv4 أو /32 في IPv6، وترفع الحجبات القائمة فعلا داخل القائمة. و`sub_order_mode` المجهول، أو `sub_page_url` أو مدخل `trusted_nets` السيئ، يرفض قبل كتابة أي حقل من الجسم.

يحدد `device_count_mode` ما يحصيه حد الأجهزة للمستخدم. و`auto` (الافتراضي) يحصي عناوين المصدر المتمايزة خلال الدقيقتين الأخيرتين — وهو الشيء الوحيد الذي يحد عدد الأماكن التي يستخدم فيها اشتراك واحد *في الوقت نفسه* — ويقطع المستخدم فقط بعد أن يتجاوز الحد باستمرار دقيقتين ونصفا، كي يمر تغير شبكة أو تبديل حامل لعنوانه دون أن يمسه شيء. و`hwid` يتوقف عن عد العناوين كليا، فيترك كشف التثبيتات المرتبطة حدا وحيدا، ويتخلى عن إنفاذ التزامن مقابل ذلك: فـ HWID يحد من يجوز له جلب اشتراك لا من يجوز له الاتصال. و`both` مقبول للصفوف المكتوبة قبل انطواء الوضعين ويعمل عمل `auto`. وأي شيء آخر يرفض بدلا من السقوط بصمت إلى الافتراضي.

و`active_devices` في المستخدم هو العدد الخام للعناوين المرئية في النافذة، ويبلغ عنه سواء كان هناك إنفاذ أم لا؛ ولا يصير `status` مساويا `device_limited` إلا بعد أن يقع القطع فعلا.

وثلاثة من هذه لها أثر لا تحمله قاعدة البيانات وحدها — فاستمارة التمويه، وكشف الماسحات، ووضع الصيانة تستشار في كل طلب — لذا تبدلها API حيا تماما كما تفعل اللوحة. و`decoy_template` المجهول يرفض قبل كتابة أي شيء؛ ومدخل `xray_dns` الذي ليس IP ولا `host:port` ولا URL ولا `localhost` يرفض كما ترفضه اللوحة، لأن خادم DNS لا يستطيع Xray تحليله يجعل كل إعادة توليد للتهيئة لاحقا تفشل.

**التوجيه** لكل خادم، والخادم `0` هو جهاز اللوحة نفسه — بالترقيم نفسه الذي يستخدمه `/v1/servers/{id}/inbounds`. و`GET` و`POST` يتكلمان الشكل نفسه:

```json
{ "data": {
  "routing": { "block_ads": true, "block_bittorrent": false, "lanes": [], "…": null },
  "xray_dns": "1.1.1.1",
  "warp_enabled": false,
  "opera_enabled": false,
  "opera_country": "EU"
} }
```

الحقل المحذوف **يترك دون تغيير**؛ و`routing`، حين يحضر، يستبدل مجموعة القواعد كاملة. والانفصال مقصود: فدمج *قوائم* القواعد لا معنى له يستطيع المستدعي توقعه (هل قائمة أقصر تحذف قواعد أم تتركها؟)، أما إطفاء مصدر خروج بصمت لأن جسما لم يذكره فهو كيف تبدأ الحركة النفقية بالخروج من عنوان IP الخادم نفسه. لذا أرسل `routing` لتغيير القواعد، وسم فقط مصادر الخروج التي تعني تحريكها فعلا.

**التتابع** قناة مصادرها العلوية خوادمنا نحن بدلا من وسطاء: يتصل المستخدمون بهذا الخادم ويخرجون عبر الخوادم في `via`، كل منها عبر أحد اتصالاته المدمجة.

```json
{ "id": "nl", "name": "Through NL", "enabled": true,
  "urls": [], "manual": [], "domains": [], "ips": [],
  "via": [ { "server": 0, "bridge": "reality" }, { "server": 3, "bridge": "hysteria2" } ] }
```

`server` معرف خادم (`0` هو جهاز اللوحة نفسه)، وليس هذا الخادم أبدا. و`bridge` هو اتصال المخرج الذي يبلغه التتابع: `reality` (الافتراضي)، أو `vision`، أو `hysteria2`، ويجب أن يكون مفعلا هناك. وكل خادم في `/v1/nodes` (و`/v1/nodes/{id}`) يسردها:

```json
"bridges": [
  { "bridge": "reality",   "name": "VLESS-XHTTP-REALITY", "enabled": true },
  { "bridge": "vision",    "name": "VLESS-TCP-TLS",       "enabled": true },
  { "bridge": "hysteria2", "name": "HYSTERIA-UDP",        "enabled": false }
]
```

`name` هو ما يسمي به ذلك الخادم الاتصال (فقد يكون المشغل أعاد تسميته)؛ ولا يستخدم إلا المفعل. وضع القناة أخيرا في `routing_order` لإرسال كل ما عداها عبرها.

تشتق اللوحة اعتماد الجسر بنفسها وتدخله إلى المخارج من عناوين هذا الخادم فقط؛ وتحسب حركة المستخدم مرة واحدة، هنا. وحركة القناة لا تخرج من هذا الخادم أبدا: ومع عدم الحكم على أي مخرج بأنه حي فإنها تذهب إلى واحد مع ذلك، ومع غياب أي مخرج تسقط. والقناة المتتابعة لا تأخذ `urls` ولا `manual`: فمصادرها العلوية هي المخارج وحدها.
والرفضات: `err.cascadeSelf`، و`err.cascadeNoServer`، و`err.cascadeLaneOff` (الاتصال معطل على ذلك المخرج)، و`err.cascadeLoop` (تتابعات مخرج تعود إلى هنا)، و`err.laneBadBridge`. ولا تفحص إلا القنوات الجديدة أو المتغيرة بالحفظ، فلا يعيق مخرج ذهب لاحقا تعديلات أخرى. وعلى المخرج، يرفض إطفاء اتصال يستخدمه تتابع بـ `err.cascadeExitLaneOff`، ويرفض إطفاء الخادم أو حذفه بـ `err.cascadeExitInUse`.

**اللقطات** تلتقط تهيئة الخادم كلها — البروتوكولات، والمنافذ، وREALITY، والتوجيه، والخروج، وDNS، والطعم، والمداخل المخصصة — في نقطة حفظ واحدة. والتراجع يستعيدها كلها *عدا* الشهادة والنطاق، فلا يمكن لتراجع أن يكسر الشهادة الحية، ويأخذ أولا نقطة حفظ تلقائية للحالة الحالية، فيكون التراجع نفسه قابلا للتراجع. وهو يعيد توليد Xray ويعيد تشغيله؛ ولأن العقد ترث حقول الرئيسي، فإعادة التشغيل تلك تشمل الأسطول كله وتقطع كل اتصال حي.

```bash
curl -X POST $BASE/v1/config/snapshots -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"label":"before the egress change"}'
```

ويحمل الجواب نقطة الحفظ التي صنعها ذلك الاستدعاء، بمعرفها الخاص — لا «الأحدث»، فقد تكون لقطة شخص آخر إن وقع إنشاء في الأثناء.

و`xray-restart` مباشر للخادم `0` ومصطف لعقدة تلتقطه في مزامنتها التالية — فـ `200` هناك يعني *مقبولا*، لا *منفذا*.

### الإحصاءات

```
GET $BASE/v1/stats/series?user_id=5&from=2026-01-01&to=2026-01-31        → daily traffic
GET $BASE/v1/stats/nodes?user_id=5&from=2026-01-01&to=2026-01-31         → totals per server
GET $BASE/v1/stats/nodes/series?user_id=5&from=2026-01-01&to=2026-01-31  → daily, per server
GET $BASE/v1/stats/users?from=2026-01-01&to=2026-01-31                   → per-user totals
```

`user_id` يحصر `series` و`nodes` و`nodes/series` في حساب واحد؛ احذفه لرقم يشمل اللوحة كلها. و`users` بلا `user_id` — فهو يجيب لكل مستخدم أصلا. و`from`/`to` بصيغة `YYYY-MM-DD` في المنطقة الزمنية المهيأة في اللوحة، وكلاهما افتراضيا **آخر 30 يوما** — فالنافذة المحذوفة نافذة، لا طلب لعدم شيء. والنطاق المشوه أو المعكوس يعيد 400 لا إجابة فارغة.

كل يوم في النطاق حاضر، بما فيه الذي لم يحمل شيئا:

```json
{ "data": [
  { "day": "2026-01-01", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-02", "up": 0, "down": 0 },
  { "day": "2026-01-03", "up": 46059475, "down": 1488367869 }
] }
```

اليوم الهادئ لا يكتب صفا داخليا، فالتاريخ المحفوظ قائمة أيام مزدحمة لا سلسلة؛ وهذه النقاط تملأ الفجوات، لأن الفجوة والصفر شكلان مختلفان لأي شيء يحسب متوسطا متحركا.

و`nodes` يفصل الحركة نفسها بحسب الخادم الذي حملها، الأكثر ازدحاما أولا — `series` يخبرك كم، وهذا يخبرك أين. و`node_id` يساوي `0` لخادم اللوحة نفسه؛ وتستخرج الأسماء لك، بما فيها الخوادم المحذوفة منذ ذلك الحين (فصفوف حركتها تعيش أطول منها).

```json
{ "data": [
  { "node_id": 2, "name": "NL", "up": 46059475, "down": 1488367869 },
  { "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 }
] }
```

و`nodes/series` البعدان معا — صف واحد لكل يوم لكل خادم، فيرسم استدعاء واحد خطا لكل خادم:

```json
{ "data": [
  { "day": "2026-01-01", "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-01", "node_id": 2, "name": "NL",     "up": 46059475, "down": 1488367869 },
  { "day": "2026-01-02", "node_id": 0, "name": "Мастер", "up": 0,        "down": 0 },
  { "day": "2026-01-02", "node_id": 2, "name": "NL",     "up": 12000000, "down": 340000000 }
] }
```

الخوادم التي لم تحمل شيئا في النافذة كلها تترك خارجا كليا؛ والتي تظهر لها صف لكل يوم.

من أين جاءت الاتصالات، لا كم حملت:

```
GET $BASE/v1/stats/countries  → recent connections grouped by country
GET $BASE/v1/stats/asns       → the same, grouped by network operator
```

كلاهما يحصي **عناوين المصدر المتمايزة** ونشاطها خلال نافذة الاحتفاظ بالاتصالات، الأكثر ازدحاما أولا. و`asn` يساوي `0` و`org` فارغ لعنوان لا يغطيه أي جدول توجيه (خاص أو غير موجه):

```json
{ "data": [
  { "asn": 15169, "org": "GOOGLE", "ips": 23, "hits": 2548 },
  { "asn": 13335, "org": "CLOUDFLARENET", "ips": 4, "hits": 61 }
] }
```

كل جواب يحسب من جدول الاتصالات كله، فيخزن كلاهما في ذاكرة مؤقتة نحو نصف دقيقة — فاستدعاءان في الثانية يحصلان على الأرقام نفسها، وتبقي اللوحة اتصال قاعدة بياناتها الواحد لكل ما عدا ذلك.

### أي الإجماليات تعني ماذا

توجد عائلتان من العدادات وهما تجيبان عن سؤالين مختلفين. والخلط بينهما يبدو تماما كخلل في العد المزدوج:

| الرقم | المصدر | يصفره |
|---|---|---|
| `total_up` / `total_down` في `/v1/summary` | عدادات حصة المستخدمين | تصفير حركة المرور، أو خطة تقلب المدة |
| `/v1/stats/series`، `/v1/stats/nodes` | تاريخ حركة المرور اليومي | لا شيء — يتراكم |

فإجماليات الملخص هي **الاستخدام في فترة الحصة الحالية**، وهو ما يقاس عليه حد البيانات، وهي *أصغر* عادة من التاريخ على المدى نفسه. وهذا ليس حركة مرور ضائعة: بل عدادات مستخدم أعيد تصفيرها بينما بقي تاريخه. فاحسب الفاتورة من عدادات الحصة، وأبلغ من التاريخ، ولا تتوقع أن يتفق الاثنان.

```
GET $BASE/v1/stats/abuse?limit=50   → recent blocklist matches across the fleet
```

### السجلات

أثران للقراءة فقط. **الأحداث** ما جرى للمستخدمين؛ و**تدقيق المسؤول** ما فعله المسؤولون ومفاتيح API باللوحة — بما في ذلك كل ما أجري عبر واجهة API هذه، منسوبا إلى اسم المفتاح.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/events` | أحداث المستخدمين، قابلة للتصفية. |
| `GET` | `/v1/events/catalog` | مفاتيح الأحداث التي يمكن أن يحملها صف. |
| `GET` | `/v1/admin-audit` | أثر المسؤولين. |
| `GET` | `/v1/admin-audit/catalog` | فئاته والأفعال في كل منها. |

كلاهما يرقم **إلى الوراء**: مرر `before=<id of the oldest row you hold>` واقرأ `next_before` من الاستجابة — و`0` تعني أنك بلغت النهاية. والمعرفات متزايدة، فيبقى المؤشر مستقرا بينما تهبط صفوف جديدة في الأعلى.

```json
{ "data": { "events": [ { "id": 812, "user_id": 5, "action": "plan.cancelled", … } ],
            "next_before": 780 } }
```

يأخذ `/v1/events` الحقل `action` (مفتاحا واحدا من الفهرس)، و`actor` (`admin` / `user` /
`system` / `api`)، و`user_id`، وزوج الترقيم. ويأخذ `/v1/admin-audit` الحقل `category`
(يتوسع إلى الأفعال التي يحملها)، و`action`، و`actor`، وزوج الترقيم. و`action` أو `category` المجهول يعيد `400`، لا صفحة فارغة — فمرشح لا يطابق شيئا بصمت لا يفرق عن فترة هادئة.

### Webhooks

النصف الدافع (push) من التكامل، قابل للتهيئة من التكامل نفسه.

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/webhooks` | سرد النقاط المهيأة. |
| `GET` | `/v1/webhooks/events` | مفاتيح الأحداث التي يمكن لـ webhook أن يشترك فيها. |
| `POST` | `/v1/webhooks` | إضافة نقطة. |
| `POST` | `/v1/webhooks/{id}` | تحديث واحدة (الكائن كاملا). |
| `DELETE` | `/v1/webhooks/{id}` | حذف واحدة. |
| `POST` | `/v1/webhooks/{id}/test` | إرسال تسليم تجريبي. |

الجسم: `{ "url": "https://…", "events": ["user.created"], "enabled": true }`. ومصفوفة `events` الفارغة تعني **كل** الأحداث. و`enabled` اختياري عند الإنشاء (افتراضيا مفعل). وتوصف صيغة التسليم والتوقيع وسياسة الإعادة تحت **Webhooks** أدناه.

التسليم التجريبي يجيب `200` حتى حين تفشل النقطة — فالاستدعاء نجح، والتسليم هو النتيجة: `{ "data": { "status": 502, "ok": false, "error": "…" } }`.

### التسجيلات

طابور التسجيل الخاضع للإشراف (لا معنى له إلا ما دام التسجيل الذاتي في وضع الإشراف — و`moderation` يقول أهو كذلك). والطلب طلب محادثة Telegram (`chat_id`) أو عميل نظام خارجي (`external_id`، من `POST /v1/signup`).

| الطريقة | المسار | الوصف |
| --- | --- | --- |
| `GET` | `/v1/registrations` | التسجيلات المعلقة. |
| `POST` | `/v1/registrations/{id}/approve` | إنشاء الحساب وربط محادثة Telegram أو معرف النظام الخارجي به. |
| `POST` | `/v1/registrations/{id}/reject` | إسقاط الطلب. |

### المراقبة

```
GET $BASE/v1/summary          → users / online / traffic totals / xray + cert status
GET $BASE/v1/system           → live CPU / RAM / disk / network / VPN throughput
GET $BASE/v1/system/auto-update       → {"cron": "0 4 * * *", "nodes": true, "last_at": …, "last": "latest"}
POST $BASE/v1/system/auto-update {"cron": "0 4 * * *"}  ("" turns it off; the nodes always follow)
GET $BASE/v1/health/report    → full self-diagnostics (xray, config, TLS, geo, egress lanes)
GET $BASE/v1/nodes/{id}/health → one server's diagnostics (id 0 = the master)
POST $BASE/v1/nodes/{id}/reach → {"host": …, "port": 443, "countries": [{"code": "RU", "ok": 9, "blocked": 1, "failed": 0, "probes": […]}]}
POST $BASE/v1/reach {"countries": ["RU", "CN", "IR"], "probes": 10, "every": 60, "threshold": 50}  (every 0 = only on demand)
GET $BASE/v1/nodes/{id}/logs   → a node's recent log lines
GET $BASE/v1/logs              → the panel's own log lines
GET $BASE/v1/backup/info       → what a backup taken now would contain
GET $BASE/v1/backup            → download that backup (.tar.gz body, not JSON)
GET $BASE/v1/metrics           → Prometheus exposition (text, not JSON)
```

#### الحوادث والصيانة (صفحة الحالة)

```
GET    $BASE/v1/incidents                → {"incidents": [...], "servers": [{"id": 0, "name": "Main"}, ...]}
POST   $BASE/v1/incidents                {"kind": "maintenance", "title": "Works on NL", "body": "…",
                                          "node_ids": [2], "starts_at": 1767225000, "ends_at": 1767236000,
                                          "notify": true, "lang": "en"}          → 201 {"incident": {...}}
POST   $BASE/v1/incidents/{id}           same body: rewrite it (whether it is resolved is kept)
POST   $BASE/v1/incidents/{id}/updates   {"stage": "identified", "body": "Found it", "notify": true}
POST   $BASE/v1/incidents/{id}/resolve   {"note": "Fixed", "notify": true}       (body optional)
POST   $BASE/v1/incidents/{id}/compensate {"hours": 3, "notify": true}         (users.manage)
DELETE $BASE/v1/incidents/updates/{id}
DELETE $BASE/v1/incidents/{id}
```

`kind` هو `incident` (مفتوح حتى الحل) أو `maintenance` (مجدول قبل `starts_at`، وجار حتى `ends_at` — و0 يعني حتى الحل). و`node_ids` الفارغة تعني الخدمة كلها؛ والمعرفات هي التي تسردها `servers`. و`hide_in_sub` (للصيانة فقط) يخرج الخوادم المسماة من الاشتراكات ما دامت النافذة جارية — إلا أن يترك ذلك اشتراكا بلا خادم. و`stage` في التحديث هو `investigating` أو `identified` أو `monitoring` (للحوادث فقط) أو `update` (للاثنين، وهو الافتراضي)؛ و`note` المعطاة مع الحل تغلق المسار بوصفها خطوة `resolved`. و`notify` يرسله إلى كل مستخدم له اشتراك نشط عبر بوت المستخدم ويحتاج إذن البث؛ وحين يتعذر خروجه تحفظ الحادثة مع ذلك ويقول `notify_error` لماذا. والصيانة التي لم تبدأ لا يمكن حلها — حركها أو احذفها.

و`compensate` يعيد وقتا عن مدخل منته، مرة واحدة: تضاف `hours` (1–2160) إلى اشتراك كل مستخدم مفعل كانت مدته سارية حين بدأ ومن يجوز له استخدام خادم يسميه. ومن كانت له مدة سارية يسجل لحظة بدء المدخل (حين ينشر، أو حين تفتح نافذة صيانة؛ `snapshot_at`)، فالمستخدم الذي جدد لاحقا لا ينال شيئا. والمدة التي نفدت منذ ذلك الحين تحصل على الساعات من الآن؛ والمد التي لا نهاية لها تترك. ثم تحمل الحادثة `compensated_at` و`compensated_seconds` و`compensated_users`؛ و`notify` يبلغ كلا من أولئك المستخدمين عبر بوت المستخدم ويحتاج إذن البث.

`/v1/metrics` هدف كشط لـ Prometheus، مصادق عليه بمفتاح API نفسه:

```yaml
scrape_configs:
  - job_name: rospanel
    scheme: https
    metrics_path: /<api-path>/v1/metrics
    authorization:
      credentials: rp_...
    static_configs:
      - targets: ["vpn.example.com"]
```

وهو ينشر أعداد المستخدمين، وحركة المرور الكلية واليومية، والإنتاجية الحية، وحالة Xray والشهادة، وCPU/RAM/القرص لجهاز اللوحة نفسه.

ولكل خادم أيضا سلسلته الخاصة، موسومة بـ `node` و`node_id` (والرئيسي `node_id="0"`): `rospanel_node_online`، و`rospanel_node_enabled`،
و`rospanel_node_xray_running`، و`rospanel_node_last_seen_seconds`،
و`rospanel_node_traffic_today_bytes{direction=…}`، إضافة إلى الجهاز تحته —
`rospanel_node_cpu_percent`، و`rospanel_node_memory_bytes{state=…}`،
و`rospanel_node_disk_bytes{state=…}` و`rospanel_node_host_uptime_seconds`. والعقدة التي لم تبلغ قط (أو التي يسبق وكيلها هذه الحقول) ليس لها عينات ببساطة، وهو ما ينبغي أن تعنيه فجوة في رسم بياني — لا صف أصفار يقرأ كجهاز عاطل.

وثمة **لا سلاسل لكل مستخدم** عن قصد: فلوحة بألف مستخدم تنتج ألف سلسلة زمنية لكل مقياس.

و`/v1/nodes/{id}/logs` يجاب عنه من الاستقصاء الطويل التالي للعقدة، فقد تعيد عقدة استنهضت للتو الدفعة السابقة — و`at` هو زمن Unix الذي جمعت فيه الأسطر.

و`/v1/backup` يدفق الأرشيف نفسه (`Content-Type: application/gzip`)، فهو نقطة النهاية الوحيدة خارج غلاف `{"data": …}` — وجه إليه مجدولا لتحفظ نسخا خارج الجهاز. و**الاستعادة غير مكشوفة عن قصد**: فهي تهيأ على القرص وتطبق عند التشغيل التالي، فلو كانت عبر API لكانت طلبا يستبدل كل شيء بصمت عند إعادة التشغيل التالية.

## ترويسات استجابة الاشتراك

يعيد `GET /v1/users/{id}/subscription` العنوان؛ أما الاستجابة التي يجلبها العميل فعلا فتحمل ما يعرضه التطبيق دون تحليل الملف:

| الترويسة | المعنى |
| --- | --- |
| `Profile-Title` | العنوان، بترميز base64 بعد البادئة `base64:` |
| `Profile-Update-Interval` | عدد الساعات بين التحديثين؛ ولا تُرسل إن ضُبطت اللوحة على «أبدا» |
| `Subscription-Userinfo` | `upload=…; download=…; total=…; expire=…` بالبايتات وبثواني يونكس؛ `total=0` بلا حد، و`expire=0` بلا نهاية |
| `Profile-Web-Page-Url` | صفحة المستخدم، ما دامت متاحة |
| `support-url` | رابط الدعم أو تلغرام، إن كان مضبوطا |
| `Announce` | إعلان المشغّل ببادئة `base64:`؛ يعرضه Happ وv2RayTun سطرا |
| `Moved-Permanently-To` | العنوان الذي انتقل إليه هذا الاشتراك، وقد أُدرج رمز المستخدم فيه |

`Moved-Permanently-To` هو انتقال النطاق: اضبط العنوان مرة واحدة في **الإعدادات ← الاشتراكات**، وضع `{token}` حيث يجب أن يقع الرمز (`https://new.example.com/sub/{token}`)، ومنذ ذلك الحين يتحدّث كل عميل يقرأ الترويسة من هناك — دون أن يستورد المستخدم رابطه من جديد. والعملاء الذين يتجاهلون الترويسة يواصلون العمل عبر العنوان القديم. امسح الحقل متى صارت اللوحة هي العنوان الذي ينبغي أن يخاطبه العملاء.

وعند تشغيل التوجيه التلقائي يتلقى Happ وINCY أيضا `routing` (الـ deeplink نفسه، لا عنوانه) و`routing-enable: 1`؛ أما Clash وMihomo فيتلقيان القواعد داخل ملف YAML بدلا من ذلك.

## MCP (مساعدو الذكاء الاصطناعي)

تقدم اللوحة واجهة API هذه إلى مساعد عبر بروتوكول Model Context Protocol نفسه. ولا شيء يثبت في أي مكان: مساعد يقبل عنوان URL:

```
$BASE/v1/mcp/<api-key>
```

المفتاح يسافر في المسار لأن تلك الحوارات تقبل عنوان URL ولا شيء غيره: **العنوان هو الاعتماد**، بسرية المفتاح الذي فيه بالضبط، ويتوقف عن العمل لحظة إلغاء ذلك المفتاح. ابنه يدويا من القيمتين اللتين تعطيك إياهما *Settings → API* — العنوان الأساسي المعروض هناك، ومفتاح في لحظة إنشائه (فلا يعرض مرة أخرى).

صندوق الأدوات هو أذونات المفتاح: يعرض على المساعد بالضبط الأدوات التي تقف خلف مسارات يستطيع المفتاح استدعاءها، وأي استدعاء لغيرها يجيب «أداة مجهولة». ولمساعد ينبغي أن ينظر فقط، أنشئ مفتاحا بلا تأشير أي كتابة — فالمساعد الذي يتصرف على جملة أسيء فهمها لن يستطيع حينئذ حذف عميل، أيا كان ما يطلب منه.

النقل هو Streamable HTTP في MCP: رسالة JSON-RPC واحدة لكل `POST`، يجاب عنها بـ `application/json`؛ والإشعارات تحصل على `202` وبلا جسم؛ و`GET` يعيد `405` (فنقطة النهاية هذه بلا تدفق يبدأه الخادم). وتوجه الاستدعاءات إلى واجهة REST API الخاصة باللوحة داخل العملية نفسها، فتحمل الأذونات نفسها، وأثر التدقيق نفسه، وأشكال الأخطاء نفسها، كأي عميل آخر لـ `/v1`.

### حجم الاستجابة

استدعاء القوائم بلا `limit` يحصل على **50 صفا**، لا الافتراضي 100 في REST: فالمساعد يدفع ثمن كل صف في سياقه. اطلب أكثر صراحة فتحصل عليه، بما في ذلك `limit=0` (كل شيء).

وفوق ذلك سقف صارم هو **512 KB لكل استدعاء**. والاستجابة التي تتجاوزه تقصر بصفوف كاملة، ويقول `meta` ذلك — فيصير `limit` العدد المعاد فعلا بينما يظل `total` يبلغ عن عدد الموجود، فتبلغ البقية بالترقيم على `limit`/`offset`. وتبقى النتيجة JSON صالحا.

**واجهة النسخ الاحتياطي غير معروضة أداة إطلاقا.** `GET /v1/backup` لأن جسمه أرشيف tar لا يستطيع المساعد قراءته، و`GET /v1/backup/info` لأن معرفة ما ستحتويه نسخة لا تنفع إلا من هو على وشك أخذها — وهو عمل المشغل، يؤدى من اللوحة حيث يقع الملف في مكان فعلا. والاستعادة ليست في `/v1` بأي شكل: فهي في اللوحة خلف جلسة وكلمة مرور تعاد كتابتها، فلا مفتاح، ولا مساعد يحمل مفتاحا، يستطيع إعادة نسخة احتياطية.

قائمة الأدوات مولدة من وثيقة OpenAPI أعلاه، فلا تنفصل عن API أبدا: فنقطة نهاية تضاف إلى `/v1` تصير أداة دون أن يتذكر أحد تسجيلها، والمحذوفة تختفي. ويشمل ذلك نصف التهيئة — فمساعد يسمح مفتاحه بذلك يستطيع قراءة الإعدادات وتغييرها، وإعادة كتابة توجيه خادم، وأخذ نقاط حفظ التهيئة والتراجع عنها، وإعادة تشغيل Xray.

وكل أداة تحمل التعليقات التي يستخدمها العميل ليقرر هل يسأل إنسانه أولا (`readOnlyHint`، و`destructiveHint`). وأي الكتابات تعد مدمرة **يعلنه المسار**، لا يخمن من صياغته — فجملة معاد كتابتها يجب ألا تستطيع إطفاء تحذير، والاستدعاءات التي تعيد توجيه حركة المرور، أو تعيد تشغيل Xray، أو تتراجع عن التهيئة، أو تدخل اللوحة في الصيانة، كلها موسومة. وتعود الأجوبة نصا، وحين أجابت اللوحة بـ JSON تعود `structuredContent` أيضا؛ والجواب الواحد محدود السقف كي لا يستطيع استدعاء واحد ملء سياق المساعد — فاطلب صفحة أصغر (`limit`/`offset`) لا الشيء كله.

## أمثلة

إنشاء مستخدم:

```bash
curl -sS -X POST "$BASE/v1/users" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"alice","data_limit":0,"expire_at":0}'
```

جلب رابط اشتراك مستخدم:

```bash
curl -sS "$BASE/v1/users/5" -H "Authorization: Bearer $KEY" \
  | jq -r '.data.sub_url'
```

حذف مستخدم:

```bash
curl -sS -X DELETE "$BASE/v1/users/5" -H "Authorization: Bearer $KEY"
```

# Webhooks

بدلا من استطلاع API، يمكنك أن تجعل اللوحة **تدفع** أحداث دورة الحياة إلى نقطة HTTP عندك. هيئها في اللوحة → **Settings → API →
Webhooks** (أضف عنوان URL للمستقبل وأشر الأحداث التي تريد — بلا تأشير = الكل)، أو عبر API نفسها: `POST /v1/webhooks`.

أهداف webhook، بخلاف الجلبات الصادرة في API، يجوز أن تكون `http` **أو** `https`، و**يجوز أن تشير إلى مضيف خاص/localhost** — فالمستقبل غالبا خدمة داخلية للمشغل نفسه، وكل تسليم POST أعمى (ولا يقرأ جسم الاستجابة أبدا).

## الأحداث

| الحدث | يطلق عندما |
| --- | --- |
| `user.created` | ينشأ مستخدم (من اللوحة أو API) |
| `user.deleted` | يحذف مستخدم |
| `registration.requested` | ينتظر تسجيل المشغل (الإشراف): `data.request_id`، و`data.name`، و`data.telegram_id` أو `data.external_id` |
| `user.registered` | يسجل مستخدم نفسه: بوت مستخدم Telegram، أو Mini App، أو `POST /v1/signup` (`external_id` أو `telegram_id`)؛ و`data.telegram_id` حين يكون Telegram مربوطا عندئذ (تسجيل بـ `telegram_id`، أو موافقة إشراف — `data.moderated`، و`data.request_id`) — وتسجيل البوت أو Mini App يربطه بعدها مباشرة، في `user.telegram_linked` |
| `registration.rejected` | يغلق تسجيل خاضع للإشراف دون حساب خاص به (`telegram_id` أو `external_id`): و`data.reason` هو `operator` (رفض) أو `has_account` (ووفق عليه، لكن لـ Telegram أو `external_id` حساب سلفا — `data.user_id`) |
| `user.expired` | ينقضي اشتراك |

## صيغة التسليم

كل تسليم هو `POST` عبر HTTP بجسم JSON:

```json
{
  "id": "3f1c…",                 // unique delivery id
  "event": "user.created",
  "created_at": 1767225600,
  "data": { "id": 7, "name": "alice", "status": "active", "enabled": true,
            "expire_at": 0, "data_limit": 0, "plan_id": 0,
            "external_id": "", "telegram_id": 0, "mailing": true, "lang": "ru" }
}
```

`data` هو كائن المستخدم (`id`، و`name`، و`status`، و`enabled`، و`expire_at`، و`data_limit`،
و`plan_id`، والمعرفات التي تعرف المستخدم بها — `external_id`، و`""` حين لا يوجد، و
`telegram_id`، و0 حين لا يوجد — و`mailing`، و`lang`، و`""` حين يكون مجهولا) لكل حدث عن مستخدم — `user.*`، و`plan.*`،
و`balance.adjusted`، و`referral.reward` (الداعي)، و`promo.*` — زائد الحقول التي يسردها جدول
الأحداث لها؛ وطلب الدفع لـ `payment.*`، مع `data.user` (كائن المستخدم ذلك، كما تركه الطلب)
و`data.user_balance_kop` (رصيده الآن؛ و`balance_kop` في الطلب نفسه هو جزء السعر الذي غطاه الرصيد)؛ والطلب (`request_id`، و`name`، و`telegram_id`
أو `external_id`) لـ `registration.requested` و`registration.rejected`؛ والبث
لـ `broadcast.sent`.

الترويسات:

```
Content-Type: application/json
User-Agent: RosPanel-Webhook/1
X-RosPanel-Event: user.created
X-RosPanel-Signature: sha256=<hex HMAC-SHA256 of the raw body>
```

## التحقق من التوقيع

لكل webhook سر (يعرض في اللوحة). أعد حساب HMAC على **جسم الطلب الخام** وقارن في زمن ثابت:

```python
import hmac, hashlib

def verify(secret: str, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

```js
import crypto from "node:crypto";

function verify(secret, body, header) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(body).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(header));
}
```

## الإعادات والتسليم

أعد حالة `2xx` للإقرار. والاستجابة غير 2xx أو خطأ الاتصال يعاد مع تراجع متزايد (نحو 10s، و30s، و2m، و10m — حتى 5 محاولات)، ثم يسقط. والتسليمات المعلقة تحفظ في قاعدة بيانات اللوحة، فإجراء دفعي بآلاف المستخدمين يرسل كل حدث، وإعادة التشغيل ترسل ما كان منتظرا. ويمكن أن تصل التسليمات **بغير ترتيب**، وعند الإعادة أو بعد إعادة التشغيل **أكثر من مرة** — فاعتبر حقل `id` مفتاح منع التكرار. وزر **Test** في
اللوحة يرسل تسليم `ping` لتؤكد بلوغ النقطة والتحقق من التوقيع. وتعرض حالة آخر تسليم بجانب كل webhook.
