# RosPanel REST API

**مرجع تعاملی:** [Swagger UI](reference.md) — همهٔ نقاط پایانی، از همان سند OpenAPI.


API بیرونی REST به یک سیستم پیرامونی (سرویس صورت‌حساب، فروشگاه تلگرامی، اسکریپت راه‌اندازی) اجازه می‌دهد پنل را با یک کلید API از طریق HTTP مدیریت کند. این API همان منطق درونی را فراخوانی می‌کند که پنل مدیریت فراخوانی می‌کند، پس این دو هرگز از هم فاصله نمی‌گیرند.

## فعال‌سازی API

پنل را باز کنید → **تنظیمات → API**. با ساختن نخستین کلید، این سطح روشن می‌شود و یک نشانی پایهٔ پایدار و غیرقابل‌حدس ساخته می‌شود:

```
https://<your-host>/<api_path>/v1
```

بخش `<api_path>` از مسیر پنهان پنل جداست، بنابراین چرخاندن راز پنل هرگز یکپارچه‌سازی‌ها را نمی‌شکند. از همان صفحه می‌توانید مسیر API را بچرخانید یا خاموش کنید (چرخاندن، نشانی پایه را عوض می‌کند؛ کلیدها زیر نشانی تازه به کار خود ادامه می‌دهند).

## مستندات تعاملی و مشخصات ماشین‌خوان

API مشخصات OpenAPI 3.0 خودش را منتشر می‌کند که از کد سرور ساخته می‌شود (اسکیماها از انواع واقعی Go بازتاب می‌یابند، پس هرگز عقب نمی‌مانند):

```
GET $BASE/openapi.json    → سند OpenAPI 3.0
GET $BASE/docs            → Swagger UI (endpointها را در مرورگر بیازمایید)
```

هر دو بدون کلید سرو می‌شوند (خودِ نشانی پایه راز است). `…/docs` را باز کنید، **Authorize** را بزنید، یک کلید وارد کنید و هر endpoint را زنده فراخوانی کنید. Postman / `openapi-generator` / هر تولیدکنندهٔ کلاینت را به `…/openapi.json` نشانه بگیرید تا یک کلاینت تایپ‌دار بسازید. (پوستهٔ Swagger UI از یک CDN بارگذاری می‌شود؛ مشخصاتی که نشان می‌دهد کاملاً محلی است.)

## احراز هویت

هر درخواست باید کلیدی را همراه داشته باشد که در **تنظیمات → API** ساخته شده است. کلید خام **یک‌بار** هنگام ساخت نشان داده می‌شود — همان لحظه ذخیره کنید؛ بعد از آن فقط پیشوندش نگه داشته می‌شود. آن را به‌صورت توکن bearer بفرستید:

```
Authorization: Bearer rp_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

(`X-API-Key: <key>` هم پذیرفته می‌شود.) کلیدهای لغوشده همان لحظه از کار می‌افتند.

کلید نبودن یا نامعتبر بودن `401` می‌دهد. این سطح برای هر IP محدودیت نرخ دارد.

یک کلید یا **دسترسی کامل** دارد یا **همان متدهای API که هنگام ساخت برایش تیک خورده‌اند** (`GET /v1/users`، `POST /v1/signup`، …) که بعداً قابل تغییر است. کلید دقیقاً همان‌ها را فراخوانی می‌کند؛ هر چیز دیگر با `403` و `"code": "forbidden"` پاسخ می‌گیرد و endpoint مربوط به MCP فقط همان ابزارها را فهرست می‌کند. هیچ‌کس متدی را تیک نمی‌زند که خودش اجازهٔ فراخوانی‌اش را ندارد، و فقط مالک دسترسی کامل (یا پشتیبان‌گیری) می‌دهد. کلیدی که پیش از تیک‌خور بودن متدها ساخته شده، تا ویرایش نشود به همان چیزی می‌رسد که مجوزهایش باز می‌کنند. `PATCH /v1/settings` و `PATCH /v1/nodes/{id}` هر فیلد را با بخش خودش می‌سنجند (DNS و خروجی به `routing.manage` نیاز دارد، شبکه‌های مورد اعتماد و تنظیمات کاوش به `security.manage`).

دسترسی کامل به همان چیزی می‌رسد که فقط مالک در پنل می‌رسد — پشتیبان‌ها (`/v1/backup`) و زمان‌بندی پشتیبان محلی هم شامل آن است — پس فقط مالک می‌تواند چنین کلیدی بسازد یا لغو کند.

## قالب پاسخ

موفق:

```json
{ "data": { ... } }
```

خطا:

```json
{ "error": { "code": "bad_request", "message": "name is required" } }
```

کدهای رایج: `bad_request` (400)، `unauthorized` (401)، `not_found` (404)، `unsupported_media_type` (415)، `internal` (500).

ورودی‌ای که پنل رد می‌کند دو فیلد دیگر هم دارد — دلیل رد شدن، و پارامترهای آن دلیل:

```json
{ "error": {
    "code": "bad_request",
    "key": "err.planHasUsers",
    "message": "the plan is assigned to 12 users — move them to another plan first",
    "args": { "count": 12 }
} }
```

`code` همان دستهٔ کلی برای انشعاب زدن در تلاش دوباره می‌ماند؛ `key` دلیل مشخص و پایدار برای انشعاب زدن در رفتار است — هرگز روی `message` تطبیق ندهید، چون آزاد است که بازنویسی شود. `message` همیشه انگلیسی است (پنل همان کدها را در مرورگر و به زبانی که مدیر انتخاب کرده ترجمه می‌کند)؛ `args` به کلاینت اجازه می‌دهد بدون تجزیهٔ متن، عبارت خودش را بسازد. هر دو وقتی خطا کدی پشتش ندارد (بدنهٔ بدشکل، مسیر ناشناس) غایب‌اند.

## بدنهٔ درخواست‌ها

فیلدی که endpoint تعریف نمی‌کند خطاست، نه چیزی که نادیده گرفته شود:

```json
{ "error": {
    "code": "bad_request",
    "message": "unknown field \"groups\" — see GET /v1/openapi.json for the fields this endpoint accepts"
} }
```

پذیرفتن بدنه و بی‌صدا انداختن فیلد بدتر از رد کردن آن است: فراخواننده‌ای که `{"groups": [2,4]}` را به endpointی می‌فرستد که `group_ids` می‌خواهد، پاسخ موفق می‌گیرد و هیچ تغییری در عضویت رخ نمی‌دهد، و هر وقت بعداً مقدار را بخواند تازه می‌فهمد. پس املا را با مشخصات بسنجید — آن از کد ساخته می‌شود، پس نمی‌تواند فیلدی را فهرست کند که پنل نمی‌خواند.

فقط فیلدهایی که endpoint واقعاً لازم دارد آنجا `required` علامت خورده‌اند. بقیه را می‌توان حذف کرد و پیش‌فرض مستند خود را نگه می‌دارند؛ برای تغییر یک چیز هرگز لازم نیست شیء کامل بفرستید.

### ویرایش‌های هم‌زمان

روی نوشتن‌ها هیچ نسخه یا `If-Match` وجود ندارد: دو فراخواننده که یک شیء را عوض می‌کنند، آخرین نوشتن برنده است و به هیچ‌کدام اطلاع داده نمی‌شود. این بیشتر جایی مهم است که یک نوشتن فیلدهایی را می‌آورد که قصد تغییرشان را نداشته — ویرایش یک نود کل نود را دوباره می‌فرستد، پس تغییری در مسیریابی که از اینجا نوشته شود می‌تواند نامی را بازنویسی کند که کسی یک ثانیه پیش‌تر در پنل گذاشته است.

در عمل به‌ندرت گزنده است، چون endpointهایی که وصله می‌زنند (`PATCH /v1/settings`، `PATCH /v1/users/{id}`) فقط فیلدهای بدنه را اعمال می‌کنند، پس دو فراخواننده که فیلدهای *متفاوت* را لمس می‌کنند به هم نمی‌خورند. اگر ویرایش یک شیء را از بیش از یک جا خودکار می‌کنید، پس از نوشتن دوباره بخوانید، نه اینکه فرض کنید مقدارتان چسبیده است.

## صفحه‌بندی

هر endpoint فهرست `?limit` و `?offset` می‌گیرد و با یک بلوک `meta` پاسخ می‌دهد:

```json
{ "data": [ … ], "meta": { "total": 1043, "offset": 0, "limit": 100 } }
```

`limit` پیش‌فرض **۱۰۰** است و سقفش **۱۰۰۰**؛ `limit=0` (یا منفی) یعنی «همه از `offset` به بعد»، که درخواستی آگاهانه است نه پیش‌فرض — پیش‌فرض بی‌کران همان چیزی است که یکپارچه‌سازی یک سال خوب کار می‌کند و بعد روی پنلی که رشد کرده با تایم‌اوت روبه‌رو می‌شود. `total` ردیف‌ها را پس از فیلتر و پیش از پنجره می‌شمارد، پس فراخواننده می‌تواند بدون حدس صفحه‌بندی کند.

دفترهای رویداد (`/v1/events`، `/v1/admin-audit`) جور دیگری صفحه‌بندی می‌شوند، با نشانگر (`?before=<oldest id held>`): ردیف‌هایشان با رسیدن ردیف‌های تازه جابه‌جا می‌شود و offset باعث می‌شود مدخل‌ها جاافتاده یا تکرار شوند.

## Endpoints

نشانی پایه در ادامه `$BASE` نوشته می‌شود (مثلاً `https://vpn.example.com/ab12cd34/v1`).

### سلامت

```
GET $BASE/health → { "data": { "status": "ok" } }
```

#### کاوش زنده‌بودن (بدون کلید API)

`GET $BASE/healthz` تنها endpointی است که کلید نمی‌خواهد — یک پایشگر uptime یا یک load balancer را به آن نشانه بگیرید. وقتی Xray اجرا نمی‌شود **503** می‌دهد (نه 200): ممکن است پنل سالم باشد، اما نود هیچ ترافیک VPNی حمل نمی‌کند و همین چیزی است که می‌خواهید برایش هشدار بگیرید.

```
GET $BASE/healthz
200 → { "data": { "status": "ok",       "xray": "running", "xray_started_at": 1752230400 } }
503 → { "data": { "status": "degraded", "xray": "down",    "xray_started_at": 0 } }
```

عمداً زیر مسیر API است و نه در ریشهٔ سرور: یک `/healthz` بدون احراز هویت روی ریشه به هر اسکنری JSON جواب می‌داد، پنل را لو می‌داد و طعمه را بی‌اثر می‌کرد. مسیر API در چرخش راز پایدار است، پس پایشگری که به اینجا نشانه رفته به کار خود ادامه می‌دهد.

### کاربران

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/users` | فهرست کاربران (فیلتر + صفحه‌بندی)؛ `?telegram_id=`، `?sub_token=` یا `?external_id=` یکی را پیدا می‌کند. |
| `POST` | `/v1/users` | ساخت کاربر. |
| `POST` | `/v1/signup` | ثبت‌نام کاربر از یک سیستم بیرونی یا ربات خودتان، زیر قواعد خودثبت‌نامی (پایین را ببینید). |
| `POST` | `/v1/users/bulk` | اعمال یک عمل روی چند کاربر هم‌زمان. |
| `GET` | `/v1/users/{id}` | گرفتن یک کاربر. |
| `PATCH` | `/v1/users/{id}` | به‌روزرسانی نام / محدودیت‌ها / انقضا یا دوره‌ای که از نخستین اتصال شروع می‌شود / محدودیت دستگاه / محدودیت سرعت / فعال بودن / `external_id` سیستم بیرونی / `mailing` (ارسال‌های همگانی و پیام‌های خودکار روشن یا خاموش — کلید ربات همان را نشان می‌دهد) / `lang` (`ru`، `en`، `zh`، `ar`، یا `""` برای آنچه تلگرام گزارش می‌کند). |
| `DELETE` | `/v1/users/{id}` | حذف کاربر. |
| `POST` | `/v1/users/{id}/reset` | صفر کردن شمارنده‌های ترافیک کاربر. |
| `POST` | `/v1/users/{id}/reset-period` | تعیین دورهٔ صفر شدن خودکار. |
| `POST` | `/v1/users/{id}/rotate-sub` | صدور نشانی تازهٔ اشتراک (پیوند قدیمی از کار می‌افتد). |
| `POST` | `/v1/users/{id}/plan` | اعمال یک طرح بر کاربر. |
| `POST` | `/v1/users/{id}/plan/cancel` | لغو فوری اشتراک پرداختی. |
| `GET` | `/v1/users/{id}/connections` | فهرست IPها / دستگاه‌های مبدأ اخیر کاربر: `last_seen`، `count` (تعداد مشاهده‌ها، حداکثر یکی در ۴۵ ثانیه)، `approx_seconds` (کران پایین زمان فعال) و `banned` (همین حالا روی فایروال انداخته شده). |
| `GET` | `/v1/users/{id}/devices` | فهرست نصب‌های مقیدشده با HWID، همراه سقفی که در آن شمرده می‌شوند. |
| `POST` | `/v1/users/{id}/devices/unbind` | آزاد کردن یک دستگاه مقید (یا همه)، و آزاد شدن جای آن. |
| `GET` | `/v1/users/{id}/events` | دفتر رویداد خود کاربر (صفحه‌بندی‌شده). |
| `GET` | `/v1/users/{id}/abuse` | تطبیق‌های فهرست سیاه برای کاربر (`limit`، پیش‌فرض ۲۰). |
| `GET` | `/v1/users/{id}/happ-link` | اشتراک کاربر به‌صورت پیوند رمزنگاری‌شدهٔ `happ://crypt4/`. |

**ایجاد** — `name` لازم است؛ بقیه اختیاری‌اند و در همان فراخوانی روی حساب تازه اعمال می‌شوند:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0,
  "device_limit": 3, "speed_limit": 20000, "plan_id": 2, "group_ids": [4] }
```

**دستگاه‌ها** همان نصب‌هایی هستند که با سرآیند اشتراک `x-hwid` مقید می‌شوند (در پنل ببینید: *تنظیمات → اشتراک‌ها*). فهرست، سقف را کنار سیاهه می‌آورد، پس یک فراخوانی به این پرسش پاسخ می‌دهد که «آیا این کاربر پر است؟»:

```json
{ "data": { "devices": [ { "hwid": "…", "os": "iOS", "os_version": "26.5.2",
    "model": "iPhone 15 Pro Max", "app": "Happ/1.0", "ip": "203.0.113.7",
    "first_seen": 1786500000, "last_seen": 1786568000 } ],
  "limit": 3, "enabled": true } }
```

آزاد کردن یا یک شناسه می‌گیرد یا همه را، و با تعداد جای آزادشده پاسخ می‌دهد:

```json
{ "hwid": "…" }        →  { "data": { "removed": 1 } }
{ "all": true }        →  { "data": { "removed": 3 } }
```

دستگاهی که هرگز مقید نشده `404` است، نه موفقیت بی‌صدا. جای آزادشده همان لحظه در دسترس است: نخستین دریافت از یک نصب تازه پذیرفته می‌شود.

`speed_limit` سقف پهنای باند هر کاربر بر حسب **kbit/s** است (۰ = بی‌کران) و در هر دو جهت اعمال می‌شود. این سقف را هستهٔ میزبان روی نشانی‌هایی اعمال می‌کند که کاربر از آن‌ها متصل است، نه Xray — بنابراین همهٔ کسانی که پشت یک نشانی NAT هستند یک سقف را شریک می‌شوند، و در Hysteria2 سقف خود را به‌صورت افت بسته نشان می‌دهد، نه کندی نرم. یک طرح سقف `speed_limit` خودش را دارد و هنگام اعمال، سقف کاربر را بازنویسی می‌کند، درست همان‌طور که با محدودیت ترافیک و دستگاه می‌کند. یک گروه دسترسی هم می‌تواند `speed_limit` داشته باشد، و وقتی یکی از گروه‌های کاربر آن را دارد، **سقف همان گروه به اجرا درمی‌آید** — فیلد خود کاربر (سقف طرحش یا سقفی که دستی گذاشته شده) نگه داشته می‌شود اما نادیده گرفته می‌شود؛ ببینید *گروه‌ها*.

**دوره‌ای که از نخستین اتصال شروع می‌شود** — به‌جای `expire_at` مقدار `hold_seconds` را بفرستید: طول دوره‌ای که تا نخستین اتصال کاربر اجرا نمی‌شود. نخستین اتصالی که پنل ثبت می‌کند `expire_at` را برابر آن لحظه به‌علاوهٔ `hold_seconds` می‌گذارد و `hold_seconds` را به `0` برمی‌گرداند (دفتر رویداد آن را `user.term_started` ثبت می‌کند). این دو ناسازگارند — بدنه‌ای که هم `expire_at` غیرصفر و هم `hold_seconds` داشته باشد رد می‌شود. دوره‌ای که در انتظار شروع است حداکثر ۳۶۵۰ روز است.

```json
{ "name": "gift-card-17", "hold_seconds": 2592000 }
```

در `PATCH`، `hold_seconds` کاربر را روی حالت انتظار می‌گذارد (هر تاریخی را جایگزین می‌کند) و `0` دورهٔ در انتظار را برمی‌دارد؛ `expire_at: 0` یعنی *هرگز* و دورهٔ در انتظار را هم برمی‌دارد. `PATCH`ی که هیچ‌کدام را نام نبرد، دوره را دقیقاً همان‌طور که هست می‌گذارد — از جمله دوره‌ای که همین لحظه شروع شده است. `extend` در `/v1/users/bulk` دورهٔ در انتظار را به تعداد روزهای داده‌شده بلندتر می‌کند، و اعمال یک طرح آن را با دورهٔ خود طرح عوض می‌کند. شیء کاربر دورهٔ در انتظار را به‌صورت `hold_seconds` حمل می‌کند (۰ وقتی چنین دوره‌ای نیست).

**پیوند Happ** — `GET /v1/users/{id}/happ-link` پاسخ می‌دهد `{ "data": { "link": "happ://crypt4/…" } }`: نشانی اشتراک کاربر رمزنگاری‌شده با کلیدی که برنامهٔ Happ حمل می‌کند، و Happ آن را بدون اینکه هرگز نشانی را نشان دهد اضافه می‌کند. تا وقتی `sub_happ_crypt` خاموش است (ببینید *پیکربندی سرور*)، پیوند `""` است. یک فراخوانی جدا و نه یک فیلد روی کاربر: هر پیوند یک رمزنگاری RSA-4096 است و padding تصادفی است، پس دو فراخوانی پیوندهای متفاوتی برای یک اشتراک برمی‌گردانند.

`plan_id` مقدار `data_limit` و `expire_at` را با مقادیر خود طرح بازنویسی می‌کند — یک طرح *همان* محدودیت‌هاست — در حالی که `device_limit` صریح پس از آن اعمال می‌شود و برنده است. اگر یکی از بخش‌های اضافی شکست بخورد، حساب بازگردانده نمی‌شود (ممکن است اعتبارنامه‌ها همین حالا در دست کسی باشند): فراخوانی خطا را برمی‌گرداند و کاربر تا همان‌جایی که کار پیش رفته باقی می‌ماند. با `201` و کاربری که واقعاً به آنجا رسیده پاسخ می‌دهد.

**لغو اشتراک** — کاربر را فوراً به طرح رایگان می‌برد (زمان پرداختی باقی‌مانده از دست می‌رود)، یا وقتی طرح رایگانی پیکربندی نشده دسترسی او را پایان می‌دهد. این با اعمال دستی طرح رایگان فرق دارد: به‌صورت `plan.cancelled` ثبت می‌شود که همان رویدادی است که یک یکپارچه‌سازی صورت‌حساب به آن واکنش می‌دهد.

**فهرست** — پارامترهای پرس‌وجو: `status` (`active` / `disabled` / `expired` / `limited` / `device_limited`)، `search` (زیررشته‌ای از نام)، `limit`، `offset` (`limit<=0` = همه از `offset` به بعد). پاسخ یک بلوک `meta` هم اضافه می‌کند:

```json
{ "data": [ ... ], "meta": { "total": 42, "offset": 0, "limit": 20 } }
```

**همگانی** — بدنه:

```json
{ "ids": [1, 2, 3], "action": "extend", "days": 30 }
```

`action` یکی از `enable`، `disable`، `delete`، `reset`، `extend` است (`days` فقط برای `extend` لازم است). پاسخ: `{ "data": { "affected": 3 } }`.

**دورهٔ صفر شدن** — بدنه: `{ "period": "monthly" }` (`none` / `daily` / `weekly` / `monthly` / `yearly`).

**ایجاد** — بدنه:

```json
{ "name": "alice", "data_limit": 0, "expire_at": 0 }
```

`data_limit` بر حسب بایت است (۰ = بی‌کران)؛ `expire_at` یک برچسب زمانی یونیکس است (۰ = هرگز). پاسخ `data` شیء کامل کاربر است، شامل `sub_url`، پیوندهای اشتراک `vless` / `reality` / `hysteria2` مربوط به خطوط داخلی، و `links` — هر خطی که کاربر روی این سرور دارد، با دربازه‌های سفارشی، هر یک با نامی که کلاینت نمایش می‌دهد.

**وصله** — فقط فیلدهایی را بفرستید که می‌خواهید عوض شوند:

```json
{ "name": "alice2", "data_limit": 107374182400, "expire_at": 1767225600, "device_limit": 3, "enabled": true }
```

**اعمال طرح** — بدنه:

```json
{ "plan_id": 2, "extend_from_current": false }
```

یک طرح می‌تواند گروه‌های دسترسی‌ای را که می‌دهد نام ببرد (`"group_ids": [3]`): هر کس روی این طرح گذاشته شود — با یک سفارش پرداخت‌شده، با `POST /v1/users/{id}/plan`، یا هنگام ثبت‌نام — به آن گروه‌ها می‌پیوندد و با تغییر طرح از آن‌ها بیرون می‌آید. عضویت‌هایی که مستقیماً با `POST /v1/users/{id}/groups` داده شده‌اند نگه داشته می‌شوند؛ فقط آنچه طرح داده پس گرفته می‌شود. فهرست خالی یعنی طرح دربارهٔ دسترسی چیزی نمی‌گوید.

**ایجاد سفارش** — بدنه `{ "user_id": 5, "plan_id": 2 }`. پاسخ سفارش را می‌آورد و، وقتی ارائه‌دهندهٔ پرداخت پیکربندی شده باشد، یک `pay_url` میزبانی‌شده برای فرستادن کاربر به آن:

```json
{ "data": { "order": { ... }, "pay_url": "https://..." } }
```

یک سفارش دستی — بدون `provider`، یا با `"manual"` — `pay_url` خالی برمی‌گرداند و منتظر `/confirm` می‌ماند؛ تا وقتی پرداخت دستی خاموش است رد می‌شود. پولی که خودتان می‌گیرید — Telegram Stars در ربات خودتان، درگاه خودتان — `"provider": "external"` است، مستقل از تنظیم دستی: `"paid": true` آن را در همان فراخوانی تأیید می‌کند، یا `/confirm` بعداً — تا آن لحظه در حالت انتظار می‌ماند و `/cancel` آن را می‌اندازد؛ `external_ref` شناسهٔ پرداخت شما را به‌عنوان `provider_id` نگه می‌دارد. در درآمد مثل هر پرداخت دیگری شمرده می‌شود. ساختن سفارش با کلید idempotency **idempotent نیست**، اما نسخهٔ تکراری هم روی هم نمی‌گذارد: سفارشی که هنوز در انتظار است برای همان کاربر، طرح و ارائه‌دهنده دوباره استفاده می‌شود نه اینکه دومی باز شود، پس یک فراخوانی تکراری همان سفارشی را برمی‌گرداند که از قبل هست.

**تنظیمات صورت‌حساب** — کل شیء، هنگام نوشتن جایگزین می‌شود (به‌روزرسانی جزئی وجود ندارد: «طرح رایگانی نیست» یک وضعیت واقعی است و باید از «مشخص نشده» قابل تشخیص باشد):

```json
{ "enabled": true, "free_plan_id": 1, "trial_plan_id": 2, "payment_note": "card 1234",
  "manual": true, "manual_label": "", "wallet": true, "topup_min": 100,
  "topup_max": 15000,
  "ref_mode": "percent", "ref_percent": 10, "ref_days": 7, "ref_first": false }
```

تعیین یک طرح به‌عنوان طرح رایگان یا آزمایشی، آن را رایگان هم می‌کند و روی همهٔ کسانی که از قبل روی آن هستند دوباره اعمال می‌شود — همان قاعده‌ای که پنل اجرا می‌کند. `manual` پرداخت دستی را کنار ارائه‌دهنده‌ها پیشنهاد می‌دهد، `manual_label` برچسب دکمهٔ پرداخت آن است (خالی = عبارت پیش‌فرض)، و `payment_note` متنی است که به کاربرِ پرداخت‌کنندهٔ دستی نشان داده می‌شود.

`wallet` به کاربران اجازه می‌دهد موجودی نگه دارند (شارژ، پرداخت طرح از آن، تمدید از آن)؛ `topup_min` و `topup_max` کوچک‌ترین و بزرگ‌ترین شارژ به روبل هستند (`topup_max` پیش‌فرض ۱۵۰۰۰ و حداکثر ۱۰۰۰۰۰۰ است). `ref_mode` آن چیزی است که معرف وقتی کسی که دعوت کرده پول می‌پردازد به دست می‌آورد: `off`، `percent` (درصد `ref_percent` از پرداخت، شامل شارژها، روی موجودی معرف — به `wallet` نیاز دارد) یا `days` (`ref_days` روز روی طرح معرف، برای طرحی که با پول خریده شده)؛ `ref_first` فقط برای نخستین پرداخت از این نوع می‌پردازد. اگر حذف شوند، `wallet`، `topup_min`، `topup_max`، `ref_mode`، `ref_percent`، `ref_days` و `ref_first` مقادیر ذخیره‌شدهٔ خود را نگه می‌دارند.

**سفارش‌ها و موجودی** — `amount_rub` یک سفارش همیشه همان پولی است که باید پرداخت شود. وقتی موجودی کاربر بخشی از قیمت را پوشش می‌دهد، `balance_kop` همان بخش است (به کوپک) و `amount_rub` باقی آن؛ تأیید سفارش پول را روی موجودی می‌گذارد و کل قیمت را با طرح از آن برمی‌دارد. `kind` برابر `plan` یا `topup` است (یک شارژ `plan_id` صفر دارد). طرحی که فقط از موجودی خریده شود، به‌صورت سفارش پرداخت‌شده با `provider` برابر `balance` و `amount_rub` صفر ظاهر می‌شود — درآمد نیست. `discount_rub` و `promo_code` یک کد تخفیف را نشان می‌دهند. وقتی موجودی کل قیمت را پوشش می‌دهد، `POST /v1/billing/orders` پاسخ `err.payFromBalance` را می‌دهد؛ به‌جایش `"from_balance": true` بفرستید تا طرح از موجودی خریده شود. پولی که برای سفارشی می‌رسد که از قبل لغو شده (با یک پرداخت تازه با همان کد تخفیف جایگزین شده، به‌عنوان رهاشده جمع شده، یا دستی لغو شده) مثل هر پرداخت دیگری شمرده می‌شود — و `POST /v1/billing/orders/{id}/confirm` سفارش لغوشده را هم می‌پذیرد: طرح داده می‌شود، یا با روشن بودن کیف پول، پول وقتی طرح دیگر قابل دادن نیست (طرح دیگری در این فاصله خریده شده، طرح مادام‌العمر از قبل دارد) روی موجودی می‌رود و سفارش به `topup` تبدیل می‌شود. یک کاربر می‌تواند حداکثر ۳ شارژ پرداخت‌نشده در یک ساعت گذشته داشته باشد.

**کدهای تخفیف** — `kind` برابر `percent` / `amount` (تخفیف روی پرداخت بعدی کاربر، `value` به درصد یا روبل؛ `plan_ids` آن را به همان طرح‌ها محدود می‌کند، `first_only` به کسی که هرگز طرحی نخریده)، `days` (`value` روز روی `plan_id`، یا روی طرح پرداختی فعال کاربر وقتی `plan_id` صفر است) یا `balance` (`value` روبل روی موجودی) است. `max_uses` صفر یعنی بی‌کران و `expires_at` صفر یعنی هرگز؛ هر کاربر می‌تواند یک کد را یک‌بار استفاده کند. کدها به بزرگی و کوچکی حروف حساس نیستند.

**چند دوره** — `"periods": 3` روی `POST /v1/billing/orders` سه دوره از طرح را یک‌جا می‌خرد، با تخفیفی که `periods` در تنظیمات صورت‌حساب نام می‌برد (`[{"periods": 3, "percent": 10}]`)؛ عددی که پیشنهادی برایش نیست رد می‌شود. دوره به اندازهٔ همان تعداد دوره است، و سهمیه‌ای که طرح در چرخهٔ خودش پر نمی‌کند، هر دوره پر می‌شود.

**بازپرداخت** — `POST /v1/billing/orders/{id}/refund` با `{ "cancel_plan": false }` قیمت سفارش (پول و بخش موجودی) را یک‌بار به موجودی کاربر برمی‌گرداند؛ `cancel_plan` همچنین روزهایی را که سفارش برایشان پرداخت شده از دوره کم می‌کند (طرح فقط وقتی تمام می‌شود که چیزی از آن نمانده باشد). به روشن بودن کیف پول نیاز دارد. بازپرداخت یا chargebackی که سیستم پرداخت گزارش می‌کند، خودش سفارش را `refund_source: "provider"` علامت می‌زند: از درآمد خارج می‌شود، آنچه خریده بود پس گرفته می‌شود، و دیگر نمی‌توان آن را به موجودی بازگرداند.

**بازگشت کاربر** — `"winback": {"enabled": true, "after_days": 7, "percent": 20, "valid_days": 7}` در تنظیمات صورت‌حساب: آن تعداد روز پس از پایان یک دورهٔ پرداختی، کاربر یک کد یک‌بارمصرف با همان تخفیف می‌گیرد که به پرداخت بعدی‌اش می‌چسبد و در ربات فرستاده می‌شود.

**نظرسنجی ریزش** — `"churn_survey": true` در تنظیمات صورت‌حساب: یک روز پس از پایان یک دورهٔ پرداختی، ربات کاربر می‌پرسد چرا تمدید نشد، و صفحهٔ اشتراک هم همان را می‌پرسد تا وقتی در حالت ریزش می‌ماند. دلایل: `price`، `quality`، `not_needed`، `competitor`، `other` (با یادداشت). یک پاسخ برای هر ریزش. کابین خودتان هم می‌پرسد: `GET /v1/users/{id}/subscription` تا وقتی چیزی برای پرسیدن هست `churn` را می‌آورد، و `POST /v1/users/{id}/churn` پاسخ را می‌گیرد (`source` برابر `api`؛ پاسخ بعدی دلیل را جایگزین می‌کند). `GET /v1/billing/funnel` آن‌ها را زیر `churn` می‌آورد: `{"total": 12, "reasons": {"price": 5, ...}, "comments": [{"user_id": 7, "user_name": "...", "reason": "other", "comment": "...", "source": "bot", "created_at": ...}]}`.

**موجودی** — `POST /v1/users/{id}/balance` مقدار `{ "amount_kop": 10000, "note": "..." }` را می‌گیرد (هر علامتی؛ موجودی نمی‌تواند زیر صفر برود) و با `{ "balance_kop": ... }` پاسخ می‌دهد. `GET /v1/users/{id}/wallet` پاسخ می‌دهد `{ "wallet": {...}, "history": [...], "ref_link": "..." }` — `ref_link` پیوند دعوت کاربر است، تا وقتی برنامهٔ معرف و ربات کاربر روشن‌اند.

**فروش از ربات خودتان** — `GET /v1/users/{id}/quotes` فهرست می‌کند چه چیزی را کاربر همین حالا می‌تواند بخرد (تا وقتی یک طرح پرداختی در جریان است فقط طرح فعلی‌اش) و برای هر دوره: `total_rub` پس از کد تخفیف کاربر، `balance_kop` که موجودی پوشش می‌دهد و `money_rub` که باید پرداخت شود. بعد `POST /v1/billing/orders` با `from_balance` وقتی `money_rub` صفر است (به‌علاوه `expect_expire_at` — همان `expire_at` که نشان دادید — تا درخواست تکراری دورهٔ دومی نخرد)، یا با یک `provider` برای باقی. یک شارژ `{"user_id": 5, "kind": "topup", "amount_rub": 300}` است (به‌علاوه `provider`، یا بدون آن برای شارژ دستی). هر دو `lang` (`ru`/`en`/`zh`/`ar`، برای دستورهای پرداخت دستی) و `return_url` را می‌گیرند (جایی که پرداخت میزبانی‌شده پرداخت‌کننده را به آن برمی‌گرداند؛ وقتی حذف شود پیوند اشتراک کاربر — وقتی تعیین شده باشد، صفحهٔ خودتان).

**ربات یا کابین کاربری خودتان** — کلید روی سرور خودتان می‌ماند، هرگز در مرورگر. متدهایی را که فراخوانی می‌کند تیک بزنید: ساختن کاربر و پیوند دادن تلگرام، باز کردن سفارش، کدهای تخفیف، معرف‌ها، تمدید — و تأیید سفارش، تصحیح موجودی و بازپرداخت‌ها را تیک نزنید، چون پول را جابه‌جا می‌کنند بدون اینکه برسد. در هر پیام کاربر را پیدا کنید: `GET /v1/users?telegram_id=<id>` (یک جست‌وجوی ایندکس‌شده؛ فهرست خالی یعنی تازه‌وارد). تازه‌وارد یعنی `POST /v1/users` با یک `plan_id` (طرح آزمایشی یا رایگان — کاربر بدون طرح هیچ بلوک پرداختی نمی‌گیرد)، بعد `POST /v1/users/{id}/telegram` با `{"chat_id": <id>}` و، وقتی `/start` او کد دعوت داشته، `POST /v1/users/{id}/referrer` با `{"ref_code": "r_…"}` (با یا بدون `r_`) — یک‌بار، پیش از نخستین پرداختش. کد دعوت خود کاربر `ref_code` است در `GET /v1/users/{id}/wallet` (و `ref_link` هم، تا وقتی ربات کاربر پنل روشن است). کابینی که افراد را با پیوند اشتراکشان وارد می‌کند آن‌ها را با `?sub_token=` پیدا می‌کند. `GET /v1/users/{id}/subscription` هر چیزی را دارد که صفحهٔ اشتراک نشان می‌دهد — وضعیت، `blocks` (آنچه افزونه‌ها به صفحه اضافه می‌کنند: `{type: text|markdown|notice|button, text, label, url}`)، ترافیک، دوره، `sub_url`، درون‌ریزی یک‌لمسی برای هر برنامه (`apps`)، هر پیکربندی (`links`)، دانلود Clash (`clash_url`)، پیکربندی‌های سادهٔ WireGuard (`wg`: `{name, conf_url, qr_url}`، به‌صورت `awg`)، پروکسی تلگرام هر سرور (`telegram`: `{name, link, web_link, qr_url}` — `link` همان `tg://proxy` است که آن را با یک لمس اضافه می‌کند)، دستگاه‌ها، بلوک پرداخت (`billing`)، رنگ‌های اپراتور (`brand`)، `terms_url` / `privacy_url` (سندهای اپراتور، تا وقتی متن دارند — `GET /v1/legal` خودِ متن را دارد) و `tg_link` — پیوند ربات کاربر که حساب را به تلگرامی که در آن باز شده مقید می‌کند (وقتی `tg_linked` باشد به آنجا منتقلش می‌کند؛ تا وقتی کلیدهای تنظیمات → تلگرام چیزی پیشنهاد نمی‌دهند غایب است، و ۱۵ دقیقه اعتبار دارد) — با عبارت‌بندی `?lang`؛ خود عمل‌ها از endpointهای بالا انجام می‌شوند. همان تنظیمات اشتراکی را نگه می‌دارد که صفحه نگه می‌دارد: `links` تا وقتی صفحه هیچ پیکربندی فهرست نمی‌کند خالی است (`show_configs` خاموش، یا HWID لازم — پیوند خام از سقف دستگاه رد می‌شد)، `clash_url` تا وقتی دکمهٔ Clash صفحه خاموش است یا زیر HWID لازم است غایب است، دکمهٔ Happ وقتی روشن باشد پیوند رمزنگاری‌شده است، و `maintenance` حالت تعمیر پنل است. `churn` نظرسنجی خروجی است که باید بپرسید — `{question, reasons: [{key, label}]}`، با عبارت‌بندی `?lang` — فقط وقتی حاضر است که دورهٔ پرداختی کاربر به پایان رسیده و هنوز پاسخ نداده؛ `key` انتخاب‌شده را به `POST /v1/users/{id}/churn` بفرستید.

**سندهای حقوقی** — `GET /v1/legal` (هر کلیدی) توافق‌نامهٔ کاربر و سیاست حریم خصوصی اپراتور را برمی‌گرداند، که در *تنظیمات → برندینگ → سندها* نوشته شده‌اند: `{"terms": {...}, "privacy": {...}}`، هر یک با `markdown`، `html` (رندرشده؛ HTML خام در منبع انداخته می‌شود)، `url` (صفحهٔ عمومی آن، "" تا وقتی سند خالی است) و `updated_at` (۰ = هرگز تنظیم نشده). آن‌ها را در صفحه‌های خودتان نشان دهید، یا به `url` پیوند بدهید.

**ثبت‌نام از یک سیستم بیرونی** — `POST /v1/signup` با `{"external_id": "ann@example.com"}` یک کاربر را با شناسهٔ خود سیستم بیرونی، زیر همان قواعدی که ربات کاربر نگه می‌دارد ثبت می‌کند: ثبت‌نام بسته رد می‌کند (`err.signupClosed`)، حالت دعوتی `invite` می‌خواهد (`err.signupBadInvite`)، بازبینی یک درخواست ثبت می‌کند، و حساب مثل ثبت‌نام رباتی طرح آزمایشی یا رایگان می‌گیرد. یک حساب برای هر `external_id` — دقیق مقایسه می‌شود، پس ایمیل را اول کوچک کنید — بنابراین ثبت‌نام دوباره همان را برمی‌گرداند (`200`، `"status": "existing"`، `user_id` آن؛ حساب کامل فقط برای کلیدی با `users.view`) و نه یک دورهٔ آزمایشی دوم. سیستم بیرونی باید فقط شناسه‌ای بفرستد که خودش تأیید کرده (ایمیلی تأییدشده): هر کس آن را بفرستد همان حساب را می‌گیرد. حساب تازه با `201 "created"` و همان حساب پاسخ می‌دهد، یک درخواست با `202 "pending"` و `request_id` (پرسیدن دوباره در حین انتظار چیزی ثبت نمی‌کند). اختیاری: `name` (وقتی حذف شود، شناسهٔ بیرونی)، `source` (برچسب قیف)، `ref` (کد دعوت؛ ناشناس نادیده گرفته می‌شود)، `lang` (`ru`، `en`، `zh` یا `ar`، که به حساب داده می‌شود — همان لحظه، یا وقتی اپراتور تأیید کند)، و `ip` — نشانی کلاینت، برای سقف یک ثبت‌نام در دقیقه برای هر نشانی (برای IPv6 هر /64) و هر شناسه، و در کل ۲۰ در دقیقه؛ بالاتر از آن پاسخ `429` با `Retry-After` است. کلید سیستم بیرونی را برای `POST /v1/signup` (به‌علاوه آنچه نشان می‌دهد و می‌فروشد) تیک بزنید و نه `POST /v1/users`: آن‌وقت نمی‌تواند کاربری به قواعد خودش بسازد. `user.registered` و `registration.rejected` مقدار `external_id` را حمل می‌کنند، و `GET /v1/users?external_id=` حساب را دوباره پیدا می‌کند.

**ثبت‌نام از ربات خودتان** — `POST /v1/signup` با `{"telegram_id": 123456789}` به‌جای `external_id` (یکی از این دو) یک کاربر تلگرامی را زیر قواعدی که پنل برای تلگرام نگه می‌دارد ثبت می‌کند: حسابشان برمی‌گردد (`"existing"`)، حسابی که باز کرده بودند بازگردانده می‌شود، فهرست سیاه مشترک رد می‌کند (`err.signupBlacklisted`)، یک دورهٔ آزمایشی، برای همیشه، به ازای هر تلگرام (حساب حذف‌شده دورهٔ دومی به دست نمی‌آورد)، و تلگرام به حساب تازه پیوند داده می‌شود. `name`، `source`، `ref`، `invite` و `ip` مثل بالا کار می‌کنند — یک ثبت‌نام در دقیقه به ازای هر تلگرام، و ۲۰ در دقیقه در کل که با ثبت‌نام‌های `external_id` مشترک است؛ زیر بازبینی، درخواست از آنِ تلگرام است و تأییدش آن را پیوند می‌دهد. **فقط شناسهٔ تلگرامی را بفرستید که خود تلگرام به شما داده است** — فرستندهٔ پیامی به ربات شما، یا `initData` مینی‌اپ که تأیید کرده‌اید — هرگز شناسه‌ای که کلاینت تایپ کرده: هر کس شناسه‌ای بفرستد همان تلگرام را ثبت‌نام می‌کند، دورهٔ آزمایشی یک‌باره‌اش را خرج می‌کند و حساب متصل به آن را در دست می‌گیرد.

کلاینتی که از ربات یا مینی‌اپ آمده از قبل حساب دارد: ورود سیستم بیرونی را با `PATCH /v1/users/{id}` و `{"external_id": "ann@example.com"}` به همان حساب ببندید، نه اینکه دوباره ثبت‌نامش کنید — از صفحه‌ای که با پیوند اشتراکش رسیده (`?sub_token=` حساب را پیدا می‌کند)، پس شناسه مال خودش است. شناسه‌ای که حساب دیگری دارد رد می‌شود (`err.externalIDTaken`)؛ `""` آن را برمی‌دارد.

**انتقال** — بدنه `{ "to_plan_id": 3 }`، پاسخ `{ "data": { "migrated": 12 } }`. محدودیت‌ها، دوره و گروه‌های دسترسی طرح مقصد را روی هر کاربر طرح مبدأ اعمال می‌کند. این تنها راه خالی کردن یک طرح پیش از حذف آن است.

**ارائه‌دهنده‌ها** — `GET /v1/payments` هر ارائه‌دهندهٔ موجود در رجیستری را با فرم تنظیماتش برمی‌گرداند: فیلدهایی که می‌گیرد، مقادیر فعلی‌شان، اینکه کدام رازها تنظیم شده‌اند (هرگز مقدارشان) و `webhook_url`ی که باید در داشبورد ارائه‌دهنده بچسبانید. فهرست فیلدها برای هر ارائه‌دهنده جداست و از رجیستری ساخته می‌شود، پس این بدنه عمداً قالب‌آزاد است. `POST /v1/payments` مقدار `{ "key": "yookassa", "enabled": true, "config": {...} }` را می‌گیرد؛ رازی که خالی بماند مقدار ذخیره‌شده‌اش را نگه می‌دارد.

`GET /v1/billing/providers` پویاست — هر روش پرداختی را که در پنل روشن کرده‌اید برمی‌گرداند (کارت، SBP، رمزارز، …)، هر یک با یک `key`، و وقتی پرداخت دستی روشن است `manual` اول می‌آید. همان `key` چیزی است که هنگام باز کردن سفارش به‌عنوان `provider` می‌فرستید.

### نودها

مدیریت ناوگان سرورها. سرور محلی پنل نود `0` است؛ بقیه **نود**های راه‌دورند که یک long-poll خروجی به پنل نگه می‌دارند. کاربران و محدودیت‌ها خودکار به هر نود فعال همگام می‌شوند، و هر سرور را می‌توان مستقل ویرایش کرد.

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/nodes` | فهرست سرورها (پنل محلی نود `0` است) با وضعیت و ترافیک امروز. |
| `POST` | `/v1/nodes` | ثبت یک نود — دستور نصب یک‌خطی را برمی‌گرداند (توکن پیوند یک‌بار نشان داده می‌شود). |
| `GET` | `/v1/nodes/{id}` | گرفتن یک نود. |
| `PATCH` | `/v1/nodes/{id}` | ویرایش نام / میزبان / پروتکل / مسیریابی / بازنویسی‌های DNS و خروجی WARP-Opera. |
| `DELETE` | `/v1/nodes/{id}` | حذف نود (سرویس‌دهی به کاربران را متوقف می‌کند). |
| `POST` | `/v1/nodes/{id}/enabled` | روشن یا خاموش کردن نود. |
| `POST` | `/v1/nodes/{id}/regen-join` | صدور دستور نصب تازه (توکن فعلی نود را باطل می‌کند). |
| `POST` | `/v1/nodes/{id}/update` | درخواست از نود برای به‌روزرسانی خودکار به آخرین انتشار. |
| `POST` | `/v1/nodes/update-all` | درخواست از همهٔ نودهای متصل برای به‌روزرسانی خودکار (یکی پس از دیگری). |
| `POST` | `/v1/nodes/{id}/proxy` | پیکربندی پروکسی سیستمی آن سرور (`id` صفر = مستر). |
| `POST` | `/v1/nodes/{id}/placement` | ویرایش جایگاه و سقف ترافیک آن سرور (`id` صفر = مستر). |
| `GET` | `/v1/nodes/{id}/health` | خودتشخیصی یک سرور. |
| `GET` | `/v1/nodes/{id}/reach` | آخرین بررسی یک سرور از کشورهای دیگر (Globalping؛ `at` صفر = هنوز بررسی نشده). |
| `POST` | `/v1/nodes/{id}/reach` | بررسی یک سرور از کشورهای دیگر همین حالا (تا یک دقیقه طول می‌کشد). |
| `GET` | `/v1/reach` | کشورها، کاوشگرهای هر کشور، بازهٔ پایش و آستانهٔ آن بررسی. |
| `POST` | `/v1/reach` | تعیین آن‌ها؛ `token` (Globalping) اگر حذف شود مقدار ذخیره‌شده را نگه می‌دارد، `""` آن را پاک می‌کند. |
| `GET` | `/v1/alerts` | قواعد هشدار؛ `firing` هشدارهای باز همین حالا را می‌شمارد. |
| `GET` | `/v1/alerts/metrics` | سنجه‌هایی که یک قاعده می‌تواند بپاید، با واحدها. |
| `GET` | `/v1/alerts/events` | تاریخچهٔ فعال شدن‌ها، تازه‌ترین اول (`limit`، `before` = شناسه‌ای که از زیر آن ادامه دهید)؛ `resolved_at` صفر = هنوز فعال است. |
| `POST` | `/v1/alerts` | افزودن یک قاعده: `name`، `metric`، `op` (`gt` / `lt`)، `threshold`، `for_secs` (چه مدت شرط برقرار بماند تا فعال شود)، `node_id` (-1 همهٔ سرورها، 0 مستر)، `enabled`. |
| `POST` | `/v1/alerts/{id}` | جایگزینی تنظیمات یک قاعده. |
| `DELETE` | `/v1/alerts/{id}` | حذف یک قاعده؛ تاریخچه‌اش می‌ماند. |
| `GET` | `/v1/nodes/{id}/logs` | تازه‌ترین سطرهای لاگ یک نود. |

**ثبت نود** — بدنه `{ "name": "NL #1", "host": "nl1.example.com" }`. پاسخ شناسهٔ نود، توکن پیوند یک‌بارمصرف و دستور نصب آمادهٔ اجرا برای یک سرور تازهٔ Ubuntu را می‌آورد:

```json
    "id": 3,
    "join_token": "rpn_…",
    "install_command": "curl -Ls https://.../install.sh | sudo bash -s -- --join '…#rpn_…'"
  }
}
```

توکن پیوند یک‌بار در دستور جاسازی می‌شود و در ۲۴ ساعت منقضی می‌شود؛ `/regen-join` توکن تازه صادر می‌کند.

**جایگاه** — اینکه یک سرور در اشتراک‌ها کجا می‌نشیند و چه مقدار ترافیک می‌تواند حمل کند. ویرایشی جزئی است: فقط فیلدهایی که فرستاده شوند عوض می‌شوند. همین فیلدها را `PATCH /v1/nodes/{id}` هم می‌پذیرد؛ این مسیر به مستر (`id` صفر) هم می‌رسد که ردیف نود ندارد. پاسخ همان جایگاه به‌صورت ذخیره‌شده است.

```json
{ "country": "NL", "sort_weight": 10, "capacity": 300, "hide_when_full": true,
  "traffic_limit": 1099511627776, "traffic_period": "month", "traffic_reset_day": 14,
  "hide_when_over": false }
```

`traffic_limit` بر حسب بایت برای هر `traffic_period` است (`month` یا `day`؛ ۰ = بدون سقف). `traffic_reset_day` (۱ تا ۳۱) روزی است که سقف ماهانه از نو شروع می‌شود، تا با روزی که میزبان صورت‌حساب می‌کند جور باشد؛ ماهی که آن روز را ندارد از آخرین روزش شروع می‌شود، و `1` به‌صورت پیش‌فرض `0` ذخیره می‌شود. پاک کردن سقف، دوره، روز بازنشانی و `hide_when_over` را هم با آن پاک می‌کند.

**پروکسی سیستمی** — یک شنوندهٔ فوروارد SOCKS5 و/یا HTTP روی آن سرور، برای ترافیکی که کلاینت VPN نیست: یک اسکرپر، یک ربات، پنل دیگری که خروجی‌اش را اینجا زنجیر می‌کند. هیچ اعتبارنامهٔ کاربری آن را باز نمی‌کند، هیچ گروه دسترسی‌ای دروازه‌اش نیست، و هرگز در اشتراک ظاهر نمی‌شود. ترافیک زیر مسیریابی همان سرور بیرون می‌رود، پس WARP، Opera و خطوط پروکسی دقیقاً همان‌طور اعمال می‌شوند که برای کلاینت‌های VPN.

```json
{ "socks_enabled": true, "socks_port": 1080,
  "http_enabled": true,  "http_port": 3128,
  "accounts": [ { "user": "scraper", "pass": "…" },
                { "user": "bot",     "pass": "…" } ] }
```

`accounts` هر بار فهرست کامل است — راه حذف یکی این است که فهرست را بدون آن بفرستید. نام‌های کاربری باید یکتا باشند و دونقطه یا فاصله نداشته باشند (دونقطه جداکنندهٔ `user:pass` است)، و هر وقت یکی از شنونده‌ها روشن است دست‌کم یک حساب کامل لازم است: پروکسی باز روی یک پورت عمومی در چند ساعت توسط اسکنرها پیدا می‌شود و بعد به رلهٔ هرزنامهٔ کس دیگری با IP همین سرور تبدیل می‌شود. پروتکلی که بدون پورت روشن شود ۱۰۸۰ (SOCKS) / ۳۱۲۸ (HTTP) می‌گیرد. هر سرور حساب‌ها و پورت‌های **خودش** را دارد — نود هرگز حساب‌های مستر را به ارث نمی‌برد، پس یک ورود لو رفته فقط یک ماشین را باز می‌کند. پاسخ همان پیکربندی ذخیره‌شده است، پس فراخواننده‌ای که فقط `{"socks_enabled": true}` فرستاده یاد می‌گیرد چه پورتی گرفته است.

### دربازه‌های سفارشی

دربازه‌هایی که اپراتور فراتر از سه خط داخلی تعریف می‌کند، یک مجموعه برای هر سرور (سرور `0` = مستر). هر یک یک شنوندهٔ عمومی است، پس ساخت/به‌روزرسانی **روی ماشین هدف** اعتبارسنجی می‌شود (`xray -test` به‌علاوهٔ یک کاوش اتصال پورت) پیش از اینکه ذخیره شود.

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/servers/{id}/inbounds` | فهرست دربازه‌های سفارشی یک سرور (`id` = شناسهٔ سرور، `0` = مستر). |
| `POST` | `/v1/servers/{id}/inbounds` | ساخت یک دربازهٔ سفارشی روی آن سرور. |
| `POST` | `/v1/inbounds/{id}` | به‌روزرسانی یک دربازهٔ سفارشی (با شناسهٔ خود دربازه). |
| `DELETE` | `/v1/inbounds/{id}` | حذف یک دربازهٔ سفارشی. |

**ساخت / به‌روزرسانی** — بدنه ویرایشگر دربازهٔ پنل را بازتاب می‌دهد: `name`، `protocol` (`vless` / `trojan` / `hysteria2` / `shadowsocks` / `turn-vk` / `wg`)، `transport` (`tcp` / `ws` / `xhttp` / `grpc` / `httpupgrade`)، `port`، `security` (`none` / `tls` / `reality`) با کلیدهای متناظر (مقصد و کلیدهای REALITY، fingerprint، path/host، بازهٔ hop در Hysteria2)، به‌علاوهٔ بلوک‌های پیشرفتهٔ اختیاری (`extra` در XHTTP، ماسک HTTP روی TCP، `sockopt`، کلیدهای اضافی TLS). فهرست کامل فیلدها — و اینکه کدام ترکیب‌ها معتبرند — در `openapi.json` / Swagger است. `shadowsocks` همان Shadowsocks-2022 است (`method` نوع AEAD را انتخاب می‌کند؛ کلید سرور تولید می‌شود و کلید هر کاربر از UUID مشتق می‌شود) — چندکاربره است، پس آمار و سهمیهٔ هر کاربر کار می‌کند، اما فقط کلاینت‌های مدرن (sing-box، mihomo، v2rayN، Shadowrocket، Streisand) آن را می‌شناسند.
`turn-vk` (پیش‌تر `wireguard`، هنوز در ورودی پذیرفته می‌شود) همان WireGuard پشت یک رلهٔ TURN است: `port` همان پورت عمومی UDP است که رله روی آن گوش می‌دهد، `turn_link` یک پیوند تماس اختیاری VK (`https://vk.com/call/join/…`) که به برنامه‌های کاربران داده می‌شود؛ کلید سرور، پورت loopback که Xray روی آن گوش می‌دهد (`wg_public_key` و `wg_local_port` در پاسخ) و کلید ماسک Free Turn Proxy (هرگز برگردانده نمی‌شود) تولید می‌شوند. در هیچ قالب اشتراکی نیست — کاربران از صفحهٔ اشتراک آن را در یک برنامه درون‌ریزی می‌کنند (`vkturnproxy://`، `freeturn://`، `wingsv://`) یا `<sub>/wg/<inbound id>.conf` را از صفحهٔ اشتراک دانلود می‌کنند.
`wg` همان WireGuard ساده است: دربازهٔ WireGuard خود Xray روی UDP عمومی `port`، که هر کلاینت استاندارد WireGuard مستقیم به آن می‌رسد. کلید سرور تولید می‌شود (`wg_public_key` در پاسخ)؛ transport و security ثابت‌اند و `turn_link` اعمال نمی‌شود. کاربران با همان هویت تونلی که برای AmneziaWG دارند همتا می‌شوند. در هیچ قالب اشتراکی هم نیست — کاربران `<sub>/wg/<inbound id>.conf` (یا `.png`، همان متن به‌صورت QR) را از صفحهٔ اشتراک دانلود می‌کنند.
`enc_mode` روی یک دربازهٔ `vless` رمزنگاری VLESS را روشن می‌کند — `native`، `xorpub` یا `random` (شکل دست‌دادن روی سیم)، خالی برای خاموش؛ کلیدها تولید می‌شوند (`encryption`، نیمهٔ کلاینت‌ها، در پاسخ است). با آن، `tcp` می‌تواند با `security: none` برود. `cdn_host` (و `cdn_port`، ۴۴۳ وقتی ۰) یک دربازهٔ `vless` / `trojan` را روی `ws` / `httpupgrade` / `xhttp` پشت یک CDN می‌گذارد: پیوندها به آن دامنه روی TLS اشاره می‌کنند، CDN به پورت خود دربازه می‌رسد (ساده با `security: none`)، و دربازه به X-Forwarded-For آن اعتماد می‌کند. `pin_cert` (TLS، نه پشت CDN) کلاینت‌ها را وامی‌دارد گواهی سرور را با اثر انگشتش بسنجند نه با نامش، پس `sni` می‌تواند هر دامنه‌ای باشد — مثلاً یکی از فهرست مجاز اپراتور. دو قالبی که اسکیما فقط می‌تواند `string` بنامدشان: `reality_dest` یک نام میزبان تنهاست (`www.microsoft.com` — شکل `host:port` رد می‌شود)، و `hop_interval` یک بازه بر حسب ثانیه است (`"5-10"`، نه `"30"`). پاسخ `data` همان دربازهٔ ذخیره‌شده است؛ پیکربندیی که رد شود (پورت از قبل اشغال، ترکیب نامعتبر، نود آفلاین) `400` با دلیل برمی‌گرداند. دربازه‌هایی که کلاینت نمی‌تواند نمایش دهد، بی‌صدا از اشتراک‌های Clash/sing-box انداخته می‌شوند نه اینکه شکسته بیرون داده شوند.

یک دربازه با توکن `inbound:<id>` در یک گروه دسترسی نشانی‌پذیر می‌شود (ببینید **گروه‌ها**).

`GET /v1/inbounds/catalog` منتشر می‌کند که چه چیزی با چه چیزی ترکیب می‌شود — هر پروتکل × هر transport، حالت‌های `security` که هر یک اجازه می‌دهد، کدام قالب‌های اشتراک نمی‌توانند آن را حمل کنند، و مقادیر enum که فیلدهای پیشرفته می‌پذیرند. همان جدولی است که ویرایشگر پنل استفاده می‌کند، پس کلاینتی که از آن دربازه می‌سازد نمی‌تواند چیزی بسازد که اعتبارسنج ردش کند.

### گروه‌ها

گروه‌های دسترسی تعیین می‌کنند کاربر به کدام اتصال‌ها دسترسی دارد. کاربری که در **هیچ** گروهی نیست به همه چیز می‌رسد؛ کاربری که در یک یا چند گروه است به **اجتماع** آنچه گروه‌هایش می‌دهند می‌رسد. فقط گروه‌هایی که **دسترسی را محدود می‌کنند** در این حساب می‌آیند (`limits_access`، پایین را ببینید): کاربری که همهٔ گروه‌هایش دسترسی را باز می‌گذارند هم به همه چیز می‌رسد. اعمال آن **سمت سرور** است — اعتبارنامهٔ خط غیرمجاز از Xray دریغ می‌شود، نه اینکه فقط پنهان شود — بنابراین `links` در شیء کاربر، اشتراک، و هر پیوند دست‌ساز فقط همان چیزی را نشان می‌دهند که داده شده است.

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/groups` | فهرست گروه‌ها، هر یک با `grants`، `member_ids` و تعداد اعضا. |
| `POST` | `/v1/groups` | ساخت یک گروه. |
| `POST` | `/v1/groups/{id}` | به‌روزرسانی یک گروه (نام، grants، سقف سرعت). |
| `DELETE` | `/v1/groups/{id}` | حذف یک گروه (اعضایی که در هیچ گروه محدودکنندهٔ دسترسی نمی‌مانند به حالت بی‌محدودیت برمی‌گردند). |
| `POST` | `/v1/groups/{id}/members` | جایگزینی اعضای گروه. |
| `POST` | `/v1/users/{id}/groups` | جایگزینی عضویت گروهی یک کاربر. |

**ساخت / به‌روزرسانی** — بدنه:

```json
{ "name": "VIP", "grants": ["builtin:0:vless", "builtin:0:reality", "inbound:7"],
  "speed_limit": 20000 }
```

`speed_limit` سرعت اعضا را بر حسب **kbit/s** سقف می‌زند (۰ = گروه سقفی نمی‌گذارد). وقتی تنظیم شود، بر سقفی که طرح یا کارت عضو می‌دهد **اولویت** دارد؛ عضوی که در چند گروه سقف‌دار است **بالاترین** سقفشان را می‌گیرد. خفه‌سازی فهرست سیاه هرگز با آن شل نمی‌شود — سخت‌گیرانه‌ترِ آن دو اعمال می‌شود. اگر در به‌روزرسانی حذف شود، سقف نگه داشته می‌شود.

یک **توکن grant** یک اتصال را نام می‌برد:

- `builtin:<server_id>:<lane>` — یک خط داخلی، که `<lane>` برابر `vless`، `reality`، `hysteria2`، `naive`، `anytls`، `mieru`، `awg` یا `mtproto` است و `<server_id>` صفر برای مستر یا شناسهٔ نودی از `GET /v1/nodes`.
- `inbound:<id>` — یک دربازهٔ سفارشی، با شناسه‌ای از `GET /v1/servers/{id}/inbounds`.

آرایهٔ خالی `grants` یعنی گروه **دسترسی را محدود نمی‌کند**: این‌طور ذخیره شود، تنها برای سقف سرعتش یک سطح است و اعضایش همهٔ اتصال‌ها را نگه می‌دارند. پاسخ این را به‌صورت `limits_access` می‌آورد — هنگام ذخیرهٔ گروه تعیین می‌شود، نه از فهرست grant خوانده می‌شود. grantها همچنین وقتی دربازه، نود یا سرور بیرونی‌ای که نام می‌برند حذف شود خودکار پاک می‌شوند، و گروهی که این‌طور آخرین grantش را از دست بدهد `limits_access: true` را نگه می‌دارد: اعضایش به هیچ چیز نمی‌رسند، نه اینکه ناگهان به همه چیز برسند. آن را دوباره بدون هیچ grant ذخیره کنید تا باز شود. گروه‌هایی که پیش از این رفتار وجود داشته‌اند تا دوباره ذخیره نشوند به محدود کردن دسترسی ادامه می‌دهند. پاسخ `data` همان گروه است.

**تعیین اعضا** — بدنه `{ "user_ids": [1, 2, 3] }`؛ کل مجموعهٔ اعضا را جایگزین می‌کند.

**تعیین گروه‌های یک کاربر** — بدنه `{ "group_ids": [4, 5] }`؛ کل عضویت کاربر را جایگزین می‌کند. آرایهٔ خالی کاربر را از همهٔ گروه‌ها بیرون می‌آورد (← بدون محدودیت).

grantهایی که به دربازه یا نود حذف‌شده اشاره می‌کنند خودکار پاک می‌شوند، و تا آن لحظه بی‌ضررند.

**توکن‌ها از کجا می‌آیند** — `GET /v1/groups/targets` هر سرور را با اتصال‌هایی که یک گروه می‌تواند بدهد فهرست می‌کند، هر یک با توکن آمادهٔ خودش:

```json
{ "data": [
  { "server_id": 0, "server_name": "Мастер",
    "lanes": [ { "lane": "vless", "label": "VLESS-TCP-TLS",
                 "token": "builtin:0:vless", "enabled": true } ],
    "inbounds": [ { "id": 7, "name": "WS резерв",
                    "token": "inbound:7", "enabled": true } ] }
] }
```

خطوط و دربازه‌های خاموش هم آمده‌اند، پس می‌توان grant را پیش از روشن شدن اتصال آماده کرد. ساختن دستی این توکن‌ها هم کار می‌کند — اما یک غلط تایپی بی‌صدا هیچ چیزی نمی‌دهد، و این endpoint دقیقاً همین را جلوگیری می‌کند.

### پیکربندی سرور

endpointهای بالا یک پنل را به کار می‌برند؛ این‌ها یکی را پیکربندی می‌کنند. هر چیز اینجا آینهٔ صفحه‌ای در پنل است و همان کدی را فراخوانی می‌کند که پشت آن است، پس مقداری که رابط کاربری رد می‌کند اینجا هم رد می‌شود.

دو چیز عمداً غایب است. **مدیران و کلیدهای API** هیچ endpointی ندارند: کلیدی که بتواند کلید بسازد، یک افشا را به دسترسی دائمی و خودتمدیدشونده تبدیل می‌کند، و این تصمیم باید پشت یک نشست با پرسیدن گذرواژه باشد. **مسیر مخفی پنل** هرگز از هیچ مسیر `/v1` برنمی‌گردد — آن لایهٔ ابهام پیش از پنل است، نه تنظیمی برای خواندن.

```
GET    $BASE/v1/settings                        → تنظیمات عملیاتی
PATCH  $BASE/v1/settings                        → عوض کردن برخی از آن‌ها
GET    $BASE/v1/servers/{id}/routing            → مسیریابی، DNS و بک‌اندهای خروجی
POST   $BASE/v1/servers/{id}/routing            → عوض کردن آن‌ها
POST   $BASE/v1/servers/{id}/xray-restart       → راه‌اندازی دوبارهٔ Xray آن سرور
GET    $BASE/v1/config/snapshots                → نقاط ذخیرهٔ پیکربندی
POST   $BASE/v1/config/snapshots                → گرفتن یکی
POST   $BASE/v1/config/snapshots/{id}/rollback  → بازگرداندن پیکربندی سرور از یکی
DELETE $BASE/v1/config/snapshots/{id}           → فراموش کردن یکی
```

`PATCH /v1/settings` **فقط فیلدهای بدنه** را اعمال می‌کند. هر چیز غایب همان‌طور که هست می‌ماند، و همین است که خواندن شیء، عوض کردن یک مقدار و فرستادن همان یک مقدار را بی‌خطر می‌کند — فرستادن دوبارهٔ کل شیء هر تغییری را که اپراتور دیگری در این فاصله داده هم دوباره اعمال می‌کرد. فیلدهای گروه‌بندی‌شده (`hwid_*`، `local_backup_*`) در داخل با یک نوشتن ذخیره می‌شوند، پس روی ردیف فعلی هم‌پوشانی می‌کنند نه اینکه هم‌گروه‌هایشان را صفر کنند.

```bash
curl -X PATCH $BASE/v1/settings -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"maintenance_mode":true}'
```

```json
{ "data": {
  "xray_dns": "https://dns.example/dns-query\n1.1.1.1",
  "decoy_template": "coming-soon",
  "decoy_templates": ["coming-soon", "YouTube", "…"],
  "maintenance_mode": true,
  "probe_detect": true, "probe_block": false,
  "watchdog_enabled": true, "watchdog_restarts": 0,
  "user_autodelete_days": 0,

  "hwid_fallback_limit": 0, "hwid_ttl_days": 30,

  "sub_path": "sub", "warp_enabled": false, "warp_registered": true,
  "sub_order_mode": "manual", "sub_happ_crypt": false, "sub_page_url": "",
  "trusted_nets": ["198.51.100.0/24", "203.0.113.10/32"]
} }
```

`sub_order_mode` ترتیب سرورها در اشتراک را تعیین می‌کند: `manual` (وزن، بعد فهرست)، `nearest`، `load`، `nearest_load`، یا `random` — ترتیبی تازه در هر دریافت، تا کلاینت‌هایی که به نخستین مدخل وصل می‌شوند میان ناوگان پخش شوند؛ پنهان‌کردن-وقتی-پر و پنهان‌کردن-وقتی-فراتر همچنان اعمال می‌شوند. `sub_happ_crypt` باعث می‌شود دکمهٔ Happ در صفحهٔ اشتراک و `GET /v1/users/{id}/happ-link` به‌جای نشانی ساده یک پیوند رمزنگاری‌شدهٔ `happ://crypt4/` بدهند. `sub_page_url` صفحهٔ اشتراک خود شماست: مرورگری که پیوند اشتراک را باز کند به آنجا فرستاده می‌شود (`302`)، با `{token}` جایگزین‌شده با توکن کاربر — مثلاً `https://example.com/cabinet?sub={token}`، و بعد `GET /v1/users?sub_token=` کاربر را پیدا می‌کند. برنامه‌هایی که اشتراک را می‌گیرند، و دانلودهای `?format=`، فرستاده نمی‌شوند؛ `""` صفحهٔ پنل را برمی‌گرداند. پیوندی به مسیر اشتراک خود همین پنل رد می‌شود (`err.subPageLoop`) و تحت هیچ نامی که پنل با آن در دسترس است دنبال نمی‌شود؛ توکن ناشناس هرگز فرستاده نمی‌شود؛ و دکمهٔ «باز کردن صفحهٔ اشتراک» در کارت کاربر صفحهٔ خود پنل را با یک پیوند امضاشدهٔ یک‌ساعته باز می‌کند. `trusted_nets` همان IPها و شبکه‌هایی هستند که پنل خودش هرگز آن‌ها را مسدود نمی‌کند — نه برای حدس زدن گذرواژهٔ SOCKS/HTTP، نه برای اسکن پنل، نه زیر سیاست منبع (رد شدن همچنان در دفتر ثبت می‌شود). فرستادنش کل فهرست را جایگزین می‌کند؛ مدخل‌ها به‌صورت پیشوند ذخیره می‌شوند (`198.51.100.7/24` تبدیل به `198.51.100.0/24` می‌شود)، شبکه‌های گسترده‌تر از یک /8 در IPv4 یا /32 در IPv6 رد می‌شوند، و مسدودسازی‌های از قبل اعمال‌شده داخل فهرست برداشته می‌شوند. `sub_order_mode` ناشناس، `sub_page_url` بد یا مدخل بد در `trusted_nets` پیش از نوشتن هر فیلدی از بدنه رد می‌شود.

`device_count_mode` تعیین می‌کند محدودیت دستگاه کاربر چه چیزی را بشمارد. `auto` (پیش‌فرض) نشانی‌های مبدأ متمایزی را می‌شمارد که در دو دقیقهٔ گذشته دیده شده‌اند — تنها چیزی که سقف می‌گذارد یک اشتراک *هم‌زمان* در چند جا استفاده شود — و کاربر را فقط وقتی قطع می‌کند که دو دقیقه و نیم پیوسته از محدودیت فراتر مانده باشد، تا تغییر شبکه یا چرخش نشانی اپراتور بدون اینکه به او بخورد بگذرد. `hwid` شمردن نشانی‌ها را کاملاً متوقف می‌کند، سیاههٔ نصب‌های مقیدشده را تنها محدودیت می‌گذارد و برای این کار از اعمال هم‌زمانی می‌گذرد: HWID سقف می‌گذارد چه کسی می‌تواند اشتراک بگیرد، نه چه کسی می‌تواند وصل شود. `both` برای ردیف‌هایی که پیش از ادغام این دو حالت نوشته شده‌اند پذیرفته می‌شود و مثل `auto` رفتار می‌کند. هر چیز دیگری رد می‌شود، نه اینکه بی‌صدا به پیش‌فرض بیفتد.

`active_devices` روی کاربر عدد خام نشانی‌هایی است که در پنجره دیده شده و گزارش می‌شود چه چیزی در حال اعمال باشد چه نه؛ `status` فقط وقتی `device_limited` می‌شود که قطع واقعاً اعمال شده باشد.

سه تا از این‌ها اثری دارند که فقط پایگاه داده حمل نمی‌کند — قالب طعمه، تشخیص اسکنر و حالت تعمیر در هر درخواست خوانده می‌شوند — پس API آن‌ها را دقیقاً مثل پنل زنده عوض می‌کند. `decoy_template` ناشناس پیش از هر نوشتنی رد می‌شود؛ مدخل `xray_dns` که IP، `host:port`، URL یا `localhost` نباشد همان‌طور رد می‌شود که پنل ردش می‌کند، چون سرور DNSی که Xray نمی‌تواند تجزیه کند هر بازتولید پیکربندی بعدی را به شکست می‌کشاند.

**مسیریابی** به ازای هر سرور است، و سرور `0` همان ماشین خود پنل است — همان شماره‌گذاری‌ای که `/v1/servers/{id}/inbounds` استفاده می‌کند. `GET` و `POST` هر دو یک شکل دارند:

```json
{ "data": {
  "routing": { "block_ads": true, "block_bittorrent": false, "lanes": [], "…": null },
  "xray_dns": "1.1.1.1",
  "warp_enabled": false,
  "opera_enabled": false,
  "opera_country": "EU"
} }
```

فیلدی که حذف شود **بدون تغییر** می‌ماند؛ `routing` وقتی حاضر باشد، مجموعهٔ قواعد را یک‌جا جایگزین می‌کند. این تفکیک عمدی است: ادغام *فهرست‌های* قاعده معنایی ندارد که فراخواننده پیش‌بینی کند (فهرست کوتاه‌تر قواعد را حذف می‌کند یا نگه می‌دارد؟)، در حالی که خاموش کردن بی‌صدای یک بک‌اند خروجی چون بدنه نامش را نبرد، همان چیزی است که باعث می‌شود ترافیک تونل‌شده از IP خود سرور بیرون برود. پس برای تغییر قواعد `routing` را بفرستید، و فقط بک‌اندهایی را نام ببرید که واقعاً می‌خواهید جابه‌جا شوند.

یک **آبشار** خطی است که بالادست‌هایش به‌جای پروکسی، سرورهای خودمان هستند: کاربران به این سرور وصل می‌شوند و از سرورهای داخل `via` بیرون می‌روند، هر یک از طریق یکی از اتصال‌های داخلی‌اش.

```json
{ "id": "nl", "name": "Through NL", "enabled": true,
  "urls": [], "manual": [], "domains": [], "ips": [],
  "via": [ { "server": 0, "bridge": "reality" }, { "server": 3, "bridge": "hysteria2" } ] }
```

`server` یک شناسهٔ سرور است (`0` ماشین خود پنل)، هرگز همین سرور. `bridge` همان اتصال خروجی است که آبشار از طریق آن به آن می‌رسد: `reality` (پیش‌فرض)، `vision` یا `hysteria2`، و باید آنجا روشن باشد. هر سرور در `/v1/nodes` (و `/v1/nodes/{id}`) آن‌ها را فهرست می‌کند:

```json
"bridges": [
  { "bridge": "reality",   "name": "VLESS-XHTTP-REALITY", "enabled": true },
  { "bridge": "vision",    "name": "VLESS-TCP-TLS",       "enabled": true },
  { "bridge": "hysteria2", "name": "HYSTERIA-UDP",        "enabled": false }
]
```

`name` همان نامی است که آن سرور برای این اتصال به کار می‌برد (ممکن است اپراتور نامش را عوض کرده باشد)؛ فقط یکی که `enabled` است می‌تواند استفاده شود. خط را در `routing_order` آخر بگذارید تا هر چیز دیگری از آن عبور کند.

پنل اعتبارنامهٔ bridge را خودش مشتق می‌کند و آن را فقط از نشانی‌های همین سرور به خروجی‌ها راه می‌دهد؛ ترافیک کاربر یک‌بار شمرده می‌شود، اینجا. ترافیک این خط هرگز از همین سرور بیرون نمی‌رود: وقتی هیچ خروجی‌ای زنده تشخیص داده نشود باز هم به یکی می‌رود، و بدون هیچ خروجی انداخته می‌شود. خط آبشار هیچ `urls` یا `manual` نمی‌گیرد: بالادست‌هایش فقط همان خروجی‌ها هستند. رد شدن‌ها: `err.cascadeSelf`، `err.cascadeNoServer`، `err.cascadeLaneOff` (اتصال روی آن خروجی خاموش است)، `err.cascadeLoop` (آبشارهای خود یک خروجی به اینجا برمی‌گردند)، `err.laneBadBridge`. فقط خطوطی که ذخیره تازه می‌کند یا عوض می‌کند بررسی می‌شوند، پس خروجی‌ای که بعداً از میان رفته ویرایش‌های دیگر را قفل نمی‌کند. روی یک خروجی، خاموش کردن اتصالی که یک آبشار استفاده می‌کند با `err.cascadeExitLaneOff` رد می‌شود، و خاموش کردن یا حذف سرور با `err.cascadeExitInUse`.

**نقاط ذخیره** کل پیکربندی سرور را — پروتکل‌ها، پورت‌ها، REALITY، مسیریابی، خروجی، DNS، طعمه و دربازه‌های سفارشی — به‌صورت یک نقطهٔ ذخیره ثبت می‌کنند. بازگرداندن، همهٔ آن را برمی‌گرداند *جز* گواهی و دامنه، پس یک واگرد هرگز نمی‌تواند گواهی زنده را بشکند، و اول از وضعیت فعلی یک نقطهٔ ذخیرهٔ خودکار می‌گیرد، پس خود بازگرداندن هم واگردپذیر است. Xray را دوباره تولید و راه‌اندازی می‌کند؛ چون نودها فیلدهای مستر را به ارث می‌برند، آن راه‌اندازی دوباره در کل ناوگان است و هر اتصال زنده می‌افتد.

```bash
curl -X POST $BASE/v1/config/snapshots -H "Authorization: Bearer $KEY" \
     -H 'Content-Type: application/json' -d '{"label":"before the egress change"}'
```

پاسخ همان نقطهٔ ذخیره‌ای را که این فراخوانی ساخته، با شناسه می‌آورد — نه «تازه‌ترین» را، که اگر در این فاصله ساختی انجام شده باشد نقطهٔ ذخیرهٔ کس دیگری می‌بود.

`xray-restart` برای سرور `0` مستقیم است و برای نود صف می‌شود، و نود آن را در همگام‌سازی بعدی برمی‌دارد — `200` در آنجا یعنی *پذیرفته شد*، نه *انجام شد*.

### آمار

```
GET $BASE/v1/stats/series?user_id=5&from=2026-01-01&to=2026-01-31        → ترافیک روزانه
GET $BASE/v1/stats/nodes?user_id=5&from=2026-01-01&to=2026-01-31         → جمع‌ها به تفکیک سرور
GET $BASE/v1/stats/nodes/series?user_id=5&from=2026-01-01&to=2026-01-31  → روزانه، به تفکیک سرور
GET $BASE/v1/stats/users?from=2026-01-01&to=2026-01-31                   → جمع‌ها به تفکیک کاربر
```

`user_id` مقدارهای `series`، `nodes` و `nodes/series` را به یک حساب محدود می‌کند؛ برای یک رقم در سطح پنل حذفش کنید. `users` هیچ `user_id` ندارد — از قبل به تفکیک کاربر پاسخ می‌دهد. `from`/`to` به شکل `YYYY-MM-DD` در منطقهٔ زمانی پیکربندی‌شدهٔ پنل هستند و هر دو پیش‌فرض **۳۰ روز اخیر** دارند — پنجرهٔ حذف‌شده یعنی یک پنجره، نه درخواست هیچ داده‌ای. بازهٔ بدشکل یا وارونه `400` است نه پاسخ خالی.

هر روز در بازه حاضر است، از جمله روزهایی که چیزی حمل نکرده‌اند:

```json
{ "data": [
  { "day": "2026-01-01", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-02", "up": 0, "down": 0 },
  { "day": "2026-01-03", "up": 46059475, "down": 1488367869 }
] }
```

روز بی‌ترافیک در داخل هیچ ردیفی نمی‌نویسد، پس تاریخچهٔ ذخیره‌شده فهرستی از روزهای پرمشغله است نه یک سری؛ این endpointها شکاف‌ها را پر می‌کنند، چون سوراخ و صفر برای هر چیزی که میانگین متحرک حساب می‌کند دو شکل متفاوت‌اند.

`nodes` همان ترافیک را به تفکیک سروری که حملش کرده می‌شکند، پرمشغله‌ترین اول — `series` می‌گوید چقدر، این می‌گوید کجا. `node_id` برای سرور خود پنل `0` است؛ نام‌ها برایتان حل می‌شوند، از جمله سرورهایی که از آن پس حذف شده‌اند (ردیف‌های ترافیکشان از خودشان بیشتر عمر می‌کنند).

```json
{ "data": [
  { "node_id": 2, "name": "NL", "up": 46059475, "down": 1488367869 },
  { "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 }
] }
```

`nodes/series` هر دو بُعد را یک‌جا می‌دهد — یک ردیف برای هر روز برای هر سرور، پس یک فراخوانی برای هر سرور یک خط رسم می‌کند:

```json
{ "data": [
  { "day": "2026-01-01", "node_id": 0, "name": "Мастер", "up": 52711616, "down": 3901246326 },
  { "day": "2026-01-01", "node_id": 2, "name": "NL",     "up": 46059475, "down": 1488367869 },
  { "day": "2026-01-02", "node_id": 0, "name": "Мастер", "up": 0,        "down": 0 },
  { "day": "2026-01-02", "node_id": 2, "name": "NL",     "up": 12000000, "down": 340000000 }
] }
```

سرورهایی که در تمام پنجره چیزی حمل نکرده‌اند کاملاً بیرون گذاشته می‌شوند؛ آن‌هایی که می‌آیند برای هر روز یک ردیف دارند.

اینکه اتصال‌ها از کجا آمده‌اند، نه اینکه چقدر حمل کرده‌اند:

```
GET $BASE/v1/stats/countries  → اتصال‌های اخیر، گروه‌بندی‌شده بر اساس کشور
GET $BASE/v1/stats/asns       → همان، گروه‌بندی‌شده بر اساس اپراتور شبکه
```

هر دو **IPهای مبدأ متمایز** و فعالیتشان را در پنجرهٔ نگهداری اتصال می‌شمارند، پرمشغله‌ترین اول. برای نشانی‌ای که هیچ جدول مسیریابی پوشش نمی‌دهد (خصوصی یا مسیریابی‌نشده)، `asn` برابر `0` و `org` خالی است:

```json
{ "data": [
  { "asn": 15169, "org": "GOOGLE", "ips": 23, "hits": 2548 },
  { "asn": 13335, "org": "CLOUDFLARENET", "ips": 4, "hits": 61 }
] }
```

هر پاسخ از کل جدول اتصال‌ها حساب می‌شود، پس هر دو حدود نیم دقیقه در حافظه نگه داشته می‌شوند — دو فراخوانی در ثانیه همان ارقام را می‌گیرند و پنل اتصال پایگاه دادهٔ تک‌تایش را برای بقیهٔ کارها نگه می‌دارد.

### کدام جمع چه معنایی دارد

دو خانوادهٔ شمارنده وجود دارد و آن‌ها به پرسش‌های متفاوت پاسخ می‌دهند. قاطی کردنشان دقیقاً شبیه یک باگ شمارش دوباره به نظر می‌رسد:

| عدد | منبع | بازنشانی با |
|---|---|---|
| `total_up` / `total_down` در `/v1/summary` | شمارنده‌های سهمیهٔ کاربران | یک بازنشانی ترافیک، یا طرحی که دوره را می‌چرخاند |
| `/v1/stats/series`، `/v1/stats/nodes` | تاریخچهٔ ترافیک روزانه | هیچ چیز — انباشته می‌شود |

پس جمع‌های خلاصه **مصرف در دورهٔ سهمیهٔ فعلی** هستند، که محدودیت حجم داده با آن سنجیده می‌شود، و به‌طور معمول *کمتر* از تاریخچه در همان بازه‌اند. این ترافیک گم‌شده نیست: این شمارنده‌های یک کاربر است که بازنشانی شده‌اند در حالی که تاریخچه‌اش مانده است. از شمارنده‌های سهمیه صورت‌حساب کنید، از تاریخچه گزارش بدهید، و انتظار نداشته باشید این دو با هم جور باشند.

```
GET $BASE/v1/stats/abuse?limit=50   → تطبیق‌های اخیر فهرست سیاه در کل ناوگان
```

### دفترهای رویداد

دو مسیر فقط‌خواندنی. **رویدادها** همان چیزی است که برای کاربران رخ داده؛ **ممیزی مدیر** همان کاری است که مدیران و کلیدهای API با پنل کرده‌اند — از جمله هر کاری که از طریق همین API انجام شده، منسوب به نام کلید.

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/events` | رویدادهای کاربر، قابل فیلتر. |
| `GET` | `/v1/events/catalog` | کلیدهای رویدادی که یک ردیف می‌تواند حمل کند. |
| `GET` | `/v1/admin-audit` | مسیر ممیزی مدیر. |
| `GET` | `/v1/admin-audit/catalog` | دسته‌هایش و کارهای درون هر یک. |

هر دو **به عقب** صفحه‌بندی می‌کنند: `before` را برابر شناسهٔ قدیمی‌ترین ردیفی که دارید بفرستید و `next_before` را از پاسخ بخوانید — `0` یعنی به انتها رسیده‌اید. شناسه‌ها یکنوا هستند، پس نشانگر پایدار می‌ماند در حالی که ردیف‌های تازه بالای فهرست می‌نشینند.

```json
{ "data": { "events": [ { "id": 812, "user_id": 5, "action": "plan.cancelled", … } ],
            "next_before": 780 } }
```

`/v1/events` مقدار `action` (یک کلید از کاتالوگ)، `actor` (`admin` / `user` / `system` / `api`)، `user_id` و جفت صفحه‌بندی را می‌گیرد. `/v1/admin-audit` مقدار `category` (به کارهایی که دارد باز می‌شود)، `action`، `actor` و جفت صفحه‌بندی را می‌گیرد. `action` یا `category` ناشناس `400` است، نه صفحهٔ خالی — فیلتری که بی‌صدا به هیچ چیز نمی‌خورد از یک دورهٔ آرام قابل تشخیص نیست.

### Webhooks

نیمهٔ فشاری یک یکپارچه‌سازی، قابل پیکربندی از خودِ یکپارچه‌سازی.

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/webhooks` | فهرست endpointهای پیکربندی‌شده. |
| `GET` | `/v1/webhooks/events` | کلیدهای رویدادی که یک webhook می‌تواند مشترکشان شود. |
| `POST` | `/v1/webhooks` | افزودن یک endpoint. |
| `POST` | `/v1/webhooks/{id}` | به‌روزرسانی یکی (شیء کامل). |
| `DELETE` | `/v1/webhooks/{id}` | حذف یکی. |
| `POST` | `/v1/webhooks/{id}/test` | فرستادن یک تحویل آزمایشی. |

بدنه: `{ "url": "https://…", "events": ["user.created"], "enabled": true }`. آرایهٔ خالی `events` یعنی **همهٔ** رویدادها. `enabled` در ساخت اختیاری است (پیش‌فرض روشن). قالب تحویل، امضا و سیاست تلاش دوباره زیر **Webhooks** توضیح داده شده است.

یک تحویل آزمایشی حتی وقتی endpoint شکست بخورد `200` می‌دهد — فراخوانی موفق بود و خود تحویل نتیجه است: `{ "data": { "status": 502, "ok": false, "error": "…" } }`.

### ثبت‌نام‌ها

صف ثبت‌نام بازبینی‌شده (فقط وقتی معنادار است که خودثبت‌نامی در حالت بازبینی باشد — `moderation` می‌گوید هست یا نه). یک درخواست از آنِ یک چت تلگرام است (`chat_id`) یا کلاینت یک سیستم بیرونی (`external_id`، از `POST /v1/signup`).

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/v1/registrations` | ثبت‌نام‌های در انتظار. |
| `POST` | `/v1/registrations/{id}/approve` | ساخت حساب و پیوند دادن چت تلگرام یا شناسهٔ سیستم بیرونی آن. |
| `POST` | `/v1/registrations/{id}/reject` | انداختن درخواست. |

### پایش

```
GET $BASE/v1/summary          → جمع کاربران / آنلاین / ترافیک / وضعیت Xray و گواهی
GET $BASE/v1/system           → CPU / RAM / دیسک / شبکه / توان عبوری VPN به‌صورت زنده
GET $BASE/v1/system/auto-update       → {"cron": "0 4 * * *", "nodes": true, "last_at": …, "last": "latest"}
POST $BASE/v1/system/auto-update {"cron": "0 4 * * *"}  ("" خاموشش می‌کند؛ نودها همیشه تبعیت می‌کنند)
GET $BASE/v1/health/report    → خودتشخیصی کامل (Xray، پیکربندی، TLS، geo، خطوط خروجی)
GET $BASE/v1/nodes/{id}/health → تشخیصی یک سرور (id صفر = مستر)
POST $BASE/v1/nodes/{id}/reach → {"host": …, "port": 443, "countries": [{"code": "RU", "ok": 9, "blocked": 1, "failed": 0, "probes": […]}]}
POST $BASE/v1/reach {"countries": ["RU", "CN", "IR"], "probes": 10, "every": 60, "threshold": 50}  (every صفر = فقط وقتی درخواست شود)
GET $BASE/v1/nodes/{id}/logs   → تازه‌ترین سطرهای لاگ یک نود
GET $BASE/v1/backup/info       → آنچه یک پشتیبان گرفته‌شده در همین لحظه خواهد داشت
GET $BASE/v1/backup            → دانلود همان پشتیبان (بدنهٔ .tar.gz، نه JSON)
GET $BASE/v1/metrics           → خروجی Prometheus (متن، نه JSON)
```

#### رخدادها و تعمیر (صفحهٔ وضعیت)

```
GET    $BASE/v1/incidents                → {"incidents": [...], "servers": [{"id": 0, "name": "Main"}, ...]}
POST   $BASE/v1/incidents                {"kind": "maintenance", "title": "Works on NL", "body": "…",
                                          "node_ids": [2], "starts_at": 1767225000, "ends_at": 1767236000,
                                          "notify": true, "lang": "en"}          → 201 {"incident": {...}}
POST   $BASE/v1/incidents/{id}           همان بدنه: بازنویسی‌اش می‌کند (اینکه حل شده یا نه حفظ می‌شود)
POST   $BASE/v1/incidents/{id}/updates   {"stage": "identified", "body": "Found it", "notify": true}
POST   $BASE/v1/incidents/{id}/resolve   {"note": "Fixed", "notify": true}       (بدنه اختیاری)
POST   $BASE/v1/incidents/{id}/compensate {"hours": 3, "notify": true}         (users.manage)
DELETE $BASE/v1/incidents/updates/{id}
DELETE $BASE/v1/incidents/{id}
```

`kind` برابر `incident` است (تا حل شدن باز می‌ماند) یا `maintenance` (پیش از `starts_at` زمان‌بندی‌شده، و تا `ends_at` در جریان — ۰ یعنی تا حل شدن). `node_ids` خالی یعنی کل سرویس؛ شناسه‌ها همان‌هایی هستند که `servers` فهرست می‌کند. `hide_in_sub` (فقط برای تعمیر) سرورهای نام‌برده را تا وقتی پنجره در جریان است از اشتراک‌ها بیرون می‌گذارد — مگر اینکه این کار اشتراکی را بدون سرور بگذارد. `stage` یک به‌روزرسانی `investigating`، `identified` یا `monitoring` است (فقط رخدادها) یا `update` (هر دو، پیش‌فرض)؛ `note`ی که همراه resolve داده می‌شود مسیر را به‌عنوان یک گام `resolved` می‌بندد. `notify` آن را از طریق ربات کاربر به هر کاربر با اشتراک فعال می‌فرستد و به مجوز ارسال همگانی نیاز دارد؛ وقتی نتواند برود، رخداد باز هم ذخیره می‌شود و `notify_error` دلیل را می‌گوید. تعمیری که شروع نشده نمی‌تواند حل شود — جابه‌جایش کنید یا حذفش کنید.

`compensate` برای یک مدخل تمام‌شده یک‌بار زمان برمی‌گرداند: `hours` (۱ تا ۲۱۶۰) به اشتراک هر کاربر فعالی اضافه می‌شود که دوره‌اش هنگام شروع آن در جریان بوده و ممکن است از سروری که نام برده استفاده کند. اینکه چه کسی دورهٔ در جریان داشته هنگام شروع مدخل ثبت می‌شود (وقتی ارسال می‌شود، یا وقتی پنجرهٔ تعمیر باز می‌شود؛ `snapshot_at`)، پس کاربری که بعداً تمدید کرده چیزی نمی‌گیرد. دوره‌ای که از آن پس تمام شده، ساعت‌ها را از همین حالا می‌گیرد؛ دوره‌های بدون پایان دست نمی‌خورند. رخداد پس از آن `compensated_at`، `compensated_seconds` و `compensated_users` را حمل می‌کند؛ `notify` به هر یک از آن کاربران از طریق ربات کاربر خبر می‌دهد و به مجوز ارسال همگانی نیاز دارد.

`/v1/metrics` یک هدف scrape برای Prometheus است که با همان کلید API احراز هویت می‌شود:

```yaml
scrape_configs:
  - job_name: rospanel
    scheme: https
    metrics_path: /<api-path>/v1/metrics
    authorization:
      credentials: rp_...
    static_configs:
      - targets: ["vpn.example.com"]
```

این endpoint شمار کاربران، ترافیک کل عمر و ترافیک روزانه، توان عبوری زنده، وضعیت Xray و گواهی، و CPU/RAM/دیسک خود میزبان پنل را منتشر می‌کند.

هر سرور هم سری خودش را دارد، با برچسب‌های `node` و `node_id` (مستر `node_id="0"` است): `rospanel_node_online`، `rospanel_node_enabled`، `rospanel_node_xray_running`، `rospanel_node_last_seen_seconds`، `rospanel_node_traffic_today_bytes{direction=…}`، به‌علاوهٔ خود ماشین زیرش — `rospanel_node_cpu_percent`، `rospanel_node_memory_bytes{state=…}`، `rospanel_node_disk_bytes{state=…}` و `rospanel_node_host_uptime_seconds`. نودی که هرگز گزارشی نداده (یا عاملش پیش از این فیلدهاست) به‌سادگی هیچ نمونه‌ای ندارد، و این همان معنایی است که یک شکاف در نمودار باید داشته باشد — نه ردیفی از صفرها که مثل یک ماشین بی‌کار خوانده شود.

عمداً **هیچ سری به تفکیک کاربر** وجود ندارد: پنلی با هزار کاربر برای هر سنجه هزار سری زمانی تولید می‌کرد.

`/v1/nodes/{id}/logs` از long-poll بعدی نود پاسخ داده می‌شود، پس نودی که تازه بیدار شده ممکن است دستهٔ قبلی را برگرداند — `at` زمان یونیکس جمع‌آوری آن سطرهاست.

`/v1/backup` خود بایگانی را استریم می‌کند (`Content-Type: application/gzip`)، پس تنها endpointی است بیرون از قالب `{"data": …}` — یک زمان‌بند را به آن نشانه بگیرید تا نسخه‌ها بیرون از این ماشین بمانند. **بازیابی عمداً در دسترس نیست**: روی دیسک آماده می‌شود و در راه‌اندازی بعدی اعمال می‌شود، پس از طریق API درخواستی می‌بود که بی‌صدا همه چیز را در ری‌استارت بعدی جایگزین می‌کرد.

## MCP (دستیارهای هوش مصنوعی)

پنل همین API را از طریق خود Model Context Protocol به یک دستیار سرو می‌کند. هیچ چیزی لازم نیست هیچ‌جا نصب شود: دستیاری که یک URL می‌گیرد:

```
$BASE/v1/mcp/<api-key>
```

کلید در مسیر می‌آید چون آن گفتگوها فقط URL می‌پذیرند و هیچ چیز دیگر: **خودِ نشانی اعتبارنامه است**، دقیقاً به همان اندازهٔ کلید داخلش راز است، و همان لحظه‌ای که آن کلید لغو شود از کار می‌افتد. آن را دستی از دو مقدار *تنظیمات → API* بسازید — نشانی پایه‌ای که آنجا نشان داده می‌شود، و کلیدی در لحظهٔ ساختنش (دیگر هرگز نشان داده نمی‌شود).

جعبه‌ابزار همان مجوزهای کلید است: به دستیار دقیقاً همان ابزارهای پشت مسیرهایی پیشنهاد می‌شود که کلید می‌تواند فراخوانی کند، و فراخوانی هر چیز دیگر پاسخ «ابزار ناشناس» می‌دهد. برای دستیاری که فقط باید نگاه کند، کلیدی با هیچ نوشتنی تیک‌نخورده بسازید — دستیاری که بر پایهٔ یک جملهٔ بدخوانده عمل می‌کند آن‌وقت نمی‌تواند مشتری را حذف کند، هر چه از او خواسته شود.

Transport همان Streamable HTTP در MCP است: یک پیام JSON-RPC در هر `POST`، که با `application/json` پاسخ داده می‌شود؛ اعلان‌ها `202` بدون بدنه می‌گیرند؛ `GET` برابر `405` است (این endpoint جریان آغازشده از سرور ندارد). فراخوانی‌ها درون فرایند به همان REST API پنل فرستاده می‌شوند، پس همان مجوزها، همان مسیر ممیزی و همان شکل خطاها را دارند که هر کلاینت دیگری از `/v1`.

### اندازهٔ پاسخ

یک فراخوانی فهرست بدون `limit` **۵۰ ردیف** می‌گیرد، نه پیش‌فرض ۱۰۰ در REST: دستیار برای هر ردیف در زمینه هزینه می‌دهد. بیشتر را صریح بخواهید و می‌گیرید، از جمله `limit=0` (همه چیز).

بالاتر از آن یک سقف سخت **۵۱۲ کیلوبایت در هر فراخوانی** است. پاسخی که از آن فراتر برود با کل ردیف‌ها کوتاه می‌شود و `meta` این را می‌گوید — `limit` همان تعدادی می‌شود که واقعاً برگردانده شده در حالی که `total` هنوز می‌گوید چند تا وجود دارد، پس صفحه‌بندی با `limit`/`offset` به بقیه می‌رسد. نتیجه JSON معتبر می‌ماند.

**سطح پشتیبان‌گیری اصلاً به‌صورت ابزار پیشنهاد نمی‌شود.** `GET /v1/backup` چون بدنه‌اش یک tarball است که دستیار نمی‌تواند بخواند، و `GET /v1/backup/info` چون دانستن اینکه یک dump چه خواهد داشت فقط برای کسی مفید است که همین حالا می‌خواهد یکی بگیرد — کار اپراتور است، انجام‌شده از پنل، جایی که فایل واقعاً جایی می‌نشیند. بازیابی به هیچ شکلی در `/v1` نیست: در پنل پشت یک نشست و گذرواژهٔ دوباره‌واردشده است، پس هیچ کلیدی، و هیچ دستیاری که کلیدی دارد، نمی‌تواند پشتیبانی را برگرداند.

فهرست ابزارها از سند OpenAPI بالا ساخته می‌شود، پس هرگز از API عقب نمی‌ماند: endpointی که به `/v1` اضافه شود ابزار می‌شود بدون اینکه کسی یادش باشد ثبتش کند، و یکی که حذف شود ناپدید می‌شود. این شامل نیمهٔ پیکربندی هم هست — دستیاری که کلیدش اجازه می‌دهد می‌تواند تنظیمات را بخواند و عوض کند، مسیریابی یک سرور را بازنویسی کند، نقاط ذخیرهٔ پیکربندی بگیرد و برگرداند و Xray را راه‌اندازی دوباره کند.

هر ابزار همان حاشیه‌نویسی‌هایی را حمل می‌کند که کلاینت با آن‌ها تصمیم می‌گیرد اول از انسانش بپرسد یا نه (`readOnlyHint`، `destructiveHint`). اینکه کدام نوشتن‌ها ویرانگر شمرده می‌شوند **توسط خود مسیر اعلام می‌شود**، نه از عبارت‌بندی‌اش حدس زده می‌شود — یک جملهٔ بازنویسی‌شده نباید بتواند هشداری را خاموش کند، و فراخوانی‌هایی که ترافیک را تغییر مسیر می‌دهند، Xray را راه‌اندازی دوباره می‌کنند، پیکربندی را برمی‌گردانند یا پنل را به حالت تعمیر می‌برند همه علامت خورده‌اند. پاسخ‌ها به‌صورت متن برمی‌گردند و، وقتی پنل با JSON پاسخ داده، به‌صورت `structuredContent` هم؛ یک پاسخ سقف دارد تا یک فراخوانی نتواند زمینهٔ دستیار را پر کند — صفحهٔ کوچک‌تری بخواهید (`limit`/`offset`) نه همه را.

## نمونه‌ها

ساخت کاربر:

```bash
curl -sS -X POST "$BASE/v1/users" \
  -H "Authorization: Bearer $KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"alice","data_limit":0,"expire_at":0}'
```

گرفتن نشانی اشتراک یک کاربر:

```bash
curl -sS "$BASE/v1/users/5" -H "Authorization: Bearer $KEY" \
  | jq -r '.data.sub_url'
```

حذف کاربر:

```bash
curl -sS -X DELETE "$BASE/v1/users/5" -H "Authorization: Bearer $KEY"
```

# Webhooks

به‌جای پایش دوره‌ای API، می‌توانید کاری کنید که پنل رویدادهای چرخهٔ عمر را به endpoint HTTP خودتان **فشار** دهد. آن‌ها را در پنل پیکربندی کنید → **تنظیمات → API → Webhooks** (یک URL گیرنده اضافه کنید و رویدادهایی را که می‌خواهید تیک بزنید — هیچ تیکی = همه)، یا از طریق خود API: `POST /v1/webhooks`.

هدف‌های webhook، برخلاف دریافت‌های خروجی API، می‌توانند `http` **یا** `https` باشند و **می‌توانند به یک میزبان خصوصی/localhost اشاره کنند** — گیرنده اغلب سرویس داخلی خود اپراتور است، و هر تحویل یک POST کور است (بدنهٔ پاسخ هرگز خوانده نمی‌شود).

## رویدادها

| رویداد | چه وقت فعال می‌شود |
| --- | --- |
| `user.created` | یک کاربر ساخته می‌شود (پنل یا API) |
| `user.deleted` | یک کاربر حذف می‌شود |
| `registration.requested` | یک ثبت‌نام منتظر اپراتور می‌ماند (بازبینی): `data.request_id`، `data.name`، و `data.telegram_id` یا `data.external_id` |
| `user.registered` | یک کاربر خودثبت‌نامی می‌کند: ربات کاربر تلگرام، مینی‌اپ یا `POST /v1/signup` (`external_id` یا `telegram_id`)؛ `data.telegram_id` وقتی تلگرام تا آن لحظه پیوند خورده باشد (یک ثبت‌نام با `telegram_id`، یک تأیید بازبینی — `data.moderated`، `data.request_id`) — ثبت‌نام از ربات یا مینی‌اپ درست پس از آن پیوند می‌خورد، در `user.telegram_linked` |
| `registration.rejected` | یک ثبت‌نام بازبینی‌شده بدون حساب خودش بسته می‌شود (`telegram_id` یا `external_id`): `data.reason` برابر `operator` (رد شده) یا `has_account` (تأیید شده، اما تلگرام یا `external_id` از قبل حسابی دارد — `data.user_id`) |
| `user.expired` | یک اشتراک به پایان می‌رسد |
| `user.limited` | کاربر سهمیهٔ ترافیکش را تمام می‌کند |
| `user.device_limited` | کاربر از محدودیت دستگاهش فراتر می‌رود — یا دستگاهی تازه در سقف برگردانده می‌شود (`data.refused`، `data.device`) |
| `user.expiring` | یک دوره دارد تمام می‌شود — در ۱۴، ۷، ۳ و ۱ روز پیش از پایانش، هر یک یک‌بار در هر دوره (تمدید از نو شروع می‌کند؛ دوره‌ای که با روزهای کمتر داده شود فقط نزدیک‌ترین مرحله را می‌گیرد)؛ `data.stage` (۱۴، ۷، ۳ یا ۱)، `data.days_left` — روی مرحله‌هایی که می‌خواهید عمل کنید؛ با یک طرح پرداختی، موجودی می‌تواند تمدید کند، `data.auto_renew`، `data.renew_price_kop`، `data.balance_kop` |

## قالب تحویل

هر تحویل یک `POST` HTTP با بدنهٔ JSON است:

```json
{
  "id": "3f1c…",                 // unique delivery id
  "event": "user.created",
  "created_at": 1767225600,
  "data": { "id": 7, "name": "alice", "status": "active", "enabled": true,
            "expire_at": 0, "data_limit": 0, "plan_id": 0,
            "external_id": "", "telegram_id": 0, "mailing": true, "lang": "ru" }
}
```

`data` برای هر رویداد دربارهٔ یک کاربر، شیء کاربر است (`id`، `name`، `status`، `enabled`، `expire_at`، `data_limit`، `plan_id`، شناسه‌هایی که کاربر را با آن‌ها می‌شناسید — `external_id`، `""` وقتی نیست، و `telegram_id`، ۰ وقتی نیست — `mailing` و `lang`، `""` وقتی نامعلوم است) — `user.*`، `plan.*`، `balance.adjusted`، `referral.reward` (دعوت‌کننده)، `promo.*` — به‌علاوهٔ فیلدهایی که جدول رویدادها برایش فهرست می‌کند؛ سفارش پرداخت برای `payment.*`، با `data.user` (همان شیء کاربر، بدان‌گونه که سفارش ترکش کرد) و `data.user_balance_kop` (موجودی‌اش حالا؛ `balance_kop` خود سفارش بخشی از قیمت است که موجودی پوشش داده بود)؛ درخواست (`request_id`، `name`، `telegram_id` یا `external_id`) برای `registration.requested` و `registration.rejected`؛ و ارسال همگانی برای `broadcast.sent`.

سرآیندها:

```
Content-Type: application/json
User-Agent: RosPanel-Webhook/1
X-RosPanel-Event: user.created
X-RosPanel-Signature: sha256=<hex HMAC-SHA256 of the raw body>
```

## سنجش امضا

هر webhook یک راز دارد (در پنل نشان داده می‌شود). HMAC را روی **بدنهٔ خام درخواست** دوباره حساب کنید و در زمان ثابت مقایسه کنید:

```python
import hmac, hashlib

def verify(secret: str, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

```js
import crypto from "node:crypto";

function verify(secret, body, header) {
  const expected = "sha256=" + crypto.createHmac("sha256", secret).update(body).digest("hex");
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(header));
}
```

## تلاش دوباره و تحویل

برای تأیید، یک وضعیت `2xx` برگردانید. پاسخ غیر-2xx یا خطای اتصال با یک عقب‌نشینی روبه‌رشد دوباره تلاش می‌شود (تقریباً ۱۰ ثانیه، ۳۰ ثانیه، ۲ دقیقه، ۱۰ دقیقه — تا ۵ تلاش)، و بعد انداخته می‌شود. تحویل‌های در انتظار در پایگاه دادهٔ پنل نگه داشته می‌شوند، پس یک عمل همگانی روی هزاران کاربر هر رویداد را می‌فرستد، و یک ری‌استارت آنچه را منتظر بود می‌فرستد. تحویل‌ها می‌توانند **بی‌ترتیب** برسند و، در تلاش دوباره یا پس از ری‌استارت، **بیش از یک‌بار** — با فیلد `id` مثل کلید idempotency رفتار کنید. دکمهٔ **Test** در پنل یک تحویل `ping` می‌فرستد تا بتوانید دسترسی‌پذیری و سنجش امضا را تأیید کنید. وضعیت آخرین تحویل کنار هر webhook نشان داده می‌شود.
