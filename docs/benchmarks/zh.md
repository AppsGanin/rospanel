# 面板容量

**2026-11-03** 在测试主机上测得：**1 vCPU、961 MB 内存**、Ubuntu 24、RosPanel
**5.13.0**、Xray-core **26.10.21**。面板运行在独立 netns 中，限制为
`MemoryMax=620M`、`MemorySwapMax=0`、`GOMEMLIMIT=300MiB`，同一台主机上还运行着线上面板
——机器比生产环境更忙、内存更紧，所以下面的数字偏保守。负载生成器在另一台机器上，
因此它的 CPU 不计入面板。

## 20 000 用户时的延迟

预热后统计四分钟，完整混合负载，**0 错误**：11 次订阅/秒（窗口内约 2 600 次）、
1 次用户页/秒和 1 次用户卡/秒（各 240 次）、0.3 次限额修改/秒（71 次）、
0.05 次创建/秒（11 次）、2 个仪表盘。

![20 000 用户时的延迟](../img/bench/latency-20k-en.svg)

| 操作 | p50 | p95 | p99 |
|---|---:|---:|---:|
| 订阅 | 26 ms | 447 ms | 535 ms |
| 用户页 | 45 ms | 277 ms | 487 ms |
| 用户卡 | 28 ms | 277 ms | 488 ms |
| 限额修改 | 29 ms | 223 ms | 228 ms |
| 创建 | 41 ms | 59 ms | 59 ms |

## 吞吐：订阅

同样 20 000 用户，只施加订阅负载——不含管理操作、不含节点同步，客户端在另一台机器上
使用 keep-alive：

| 并发客户端 | 订阅/秒 | p50 | p95 | p99 | 错误 |
|---|---:|---:|---:|---:|---:|
| 4 | 577 | 7 ms | 9 ms | 13 ms | 0 |
| 8 | 750 | 11 ms | 14 ms | 19 ms | 0 |
| 16 | 877 | 16 ms | 32 ms | 37 ms | 0 |
| 64 | 887 | 36 ms | 41 ms | 46 ms | 0 |
| 256 | 902 | 210 ms | 531 ms | 1 s | 0 |

单个 vCPU 上约每秒 900 次订阅，此时面板只占 **17% 的一个核**。20 000 用户的线上面板
按 30 分钟刷新一次计算，大约每秒 11 次订阅——余量有两个数量级：这个规模的机器不会
先被 CPU 卡住。

## 50 000 用户

| 场景 | p50 | p95 | 错误 | 面板 RSS |
|---|---:|---:|---:|---:|
| 50k，14 次订阅/秒 | 26 ms | 437 ms | 0 | — |
| 50k，节点同步 | 56 ms | 134 ms | 0 | 300–346 MB |

读路径不随用户量增长而变慢：20k 和 50k 上订阅的 p50 都是 26 ms，节点同步稳定在
56 ms p50 / 134 ms p95 且无错误。

## 内存：如何估算机器规模

20k 完整混合负载占用 336 MB 面板内存和 160 MB Xray；50k 的订阅或节点同步模式为
346 + 247 MB。按内存而不是 CPU 估算：约每 20k 用户 1 GB（含管理操作），
或者 50k 用户（以拉取订阅和同步节点为主）。

## 这说明什么

- **单个 vCPU 不是瓶颈：** 20k 完整混合负载时平均负载 20%，每秒 900 次订阅时 17%。
  88% 的尖峰来自创建时的配置构建，而不是服务用户。
- **内存决定机器规模：** 1 GB 可承载约 20k 完整混合负载，或 50k 订阅与节点同步。
- **磁盘也不是限制：** 面板批量写入，而它所在磁盘的实测上限远高于工作负载所需（见下）。

## SQLite 写入上限

![SQLite 写入上限](../img/bench/write-en.svg)

在同一块磁盘上单独测得，用来与面板的批量写入对照：WAL、`synchronous=FULL`、单连接、
256 字节行 —— `fsync` 2 638/秒、自动提交 1 381 次写入/秒、单事务 63 386 行/秒、
`synchronous=NORMAL` 下 20 701 次写入/秒。
